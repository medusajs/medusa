# AI-Generated Content

Steps 5b and 13b: when to ask for a rewrite and when to close an AI-authored PR. AI-assisted code is allowed; only the PR's writing and the author's replies are judged.

## Step 5b — AI-Generated Writing (non-team members only)

Judge the **writing style** of the PR description and of the author's own
replies to earlier reviews (from Step 1's comments). The code is **not**
judged here: AI-assisted code is allowed.

Style signals:

- Over-explanation: long prose for a small change, restating the obvious.
- Report-style headers such as **Summary**, **Impact**, **Root Cause**,
  **Recommendation**, **Key Changes**, beyond the PR template's own sections.
- Heavy bold, with most lines or bullets starting with a bolded phrase.
- Stock filler ("This PR introduces a comprehensive...", "ensures
  robustness", "seamlessly", "In summary").
- Generic, hedged prose with few specifics: no concrete file, function,
  input, or test step the reader could verify.
- Emoji section markers.

**Tool attribution (decisive on its own):** the description or a reply
carries an AI tool's generated-by footer, such as "Generated with Claude
Code", "Generated by Claude Code", "Generated with [Claude Code](...)"
(often after a robot emoji), or the equivalent from Copilot, Cursor,
Codex, Devin, ChatGPT, or similar. That means the text itself was
generated, so emit `needs-rewrite` even without other signals. A
`Co-Authored-By: Claude` (or similar) trailer on commits is not a signal:
it marks AI-assisted code, which is allowed.

Otherwise, emit `needs-rewrite` only when the writing reads as **highly**
AI-generated: several of these signals are clearly present. One or two
signals, polished but specific prose, non-native English, or text that was
translated or proofread with AI are not enough; continue the review.

When it is highly AI-generated:

1. Check Step 13b's concrete signals against the diff (the description
   claims changes the diff doesn't contain, or references files or APIs
   that don't exist). If one is verified, emit `close-ai-authored` per
   Step 13b instead.
2. Otherwise emit:
   - `review_template: "needs-rewrite"`
   - `labels_to_add: ["requires-rewrite", "requires-more"]`, `labels_to_remove: ["initial-approval"]`
   - `summary`: one neutral line naming which text needs rewriting (the
     description, a reply, or both) and the kind of signals seen, without
     quoting it, e.g. *"The description is mostly report-style headings and
     general prose with no concrete test steps."*
   - `blocking_points`: `[]`

Then **stop** — no code analysis.

**Re-review of a PR labeled `requires-rewrite`** (from Step 1's labels):
judge the current description and replies again. If they still read as
highly AI-generated, emit `needs-rewrite` again (the downstream step does
not repeat the request or reset the timer). If they are now in the
author's own words, the rewrite is accepted: ignore the old request and
continue the review; any other template removes `requires-rewrite`.

## Step 13b — AI-authored PRs (non-team members only)

Policy: **AI-assisted code is fine; AI-authored PRs are not.** The author
must understand and own the change, and the PR description and replies
to review comments must be in the author's own words. Using AI to
translate or proofread the author's own writing is fine.

Emit `close-ai-authored` only when at least one **concrete** signal is
present, verified against the diff and the repository:

- The description doesn't match the diff: it claims changes, tests, or
  behavior the diff doesn't contain, or describes a different change.
- The PR references files, functions, APIs, options, or packages that
  don't exist in the repository or in the diff.
- The author can't answer review questions: replies to an earlier review
  are generic, ignore the question, or contradict the diff.

Never close on writing style alone (polished prose, headings, bullet
lists, emojis), on non-native English, or on a detector score or "looks
AI-generated" judgment. Writing style is handled by Step 5b, which asks
for a rewrite (`needs-rewrite`) instead of closing; when style hints stay
below Step 5b's bar, review the PR normally. When the concrete signals are
weak or ambiguous, use `needs-info` and ask the author to explain the
change and how they tested it in their own words.

## Common Mistakes

- [ ] Emitting `needs-rewrite` for a team member, on one or two style signals, or because the code looks AI-assisted — only the description and the author's replies are judged (Step 5b)
- [ ] Closing a PR on writing style instead of emitting `needs-rewrite`
- [ ] Emitting `null` for a PR labeled `requires-rewrite`, or adding `requires-rewrite` with any template other than `needs-rewrite`
