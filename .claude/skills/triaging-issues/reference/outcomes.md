# Outcome Criteria

How to choose between `fix`, `escalate`, `rewrite`, and `slop`. The other outcomes are
covered in the category flows.

## Fix Limits

Pick `fix` only when the expected change fits **all** of these:

- At most **10 files** and **500 changed lines**, not counting tests and
  `.changeset/` files. Documentation fixes (`fix_route: "docs"`) have no size
  limit.
- **No migrations** and no data model change.
- **No public API change**: no new, removed, or renamed exported symbols,
  HTTP routes, request/response fields, module service methods, workflow
  inputs/outputs, or config options.
- **No event change**: no new, removed, or renamed events or payload fields.
- Nothing under `migrations/`, any `package.json`, `.github/`, `.claude/`,
  `scripts/`, `.husky/`, `.yarn/`, `yarn.lock`, or `.env*`. A fix that needs
  these is rejected by the fix workflow and turned into an escalation, so
  pick `escalate` directly.
- The root cause is **confirmed in the code** (you found the line or
  function), and the correct behavior is unambiguous from the docs, types,
  or surrounding code.

`fix_route`:

- `bug`: the change is in source code under `packages/` (a regression test
  is expected).
- `docs`: the change is in documentation, i.e. MDX under `www/apps/`, TSDoc
  in `packages/`, OAS output, or UI specs. See `docs.md` for fix locations.

Typical `fix`: a wrong condition, a missing null check, an unhandled edge
case in one function, a missing field in a select list, a typo or wrong
example in a docs page, an outdated TSDoc description.

## Escalate (Architectural)

Pick `escalate` when the problem is real (confirmed, or credible with
evidence) and any of these apply:

- **Data model**: needs a model or migration change, new relations, or a
  change to how data is stored.
- **Public API**: changes HTTP routes, module service signatures, workflow
  or step inputs/outputs, exported types, events, or config.
- **Cross-module**: touches several modules, module links, or core
  framework packages together, or changes how modules interact.
- **Performance or security design**: needs a design decision about
  caching, query strategy, locking, auth, permissions, or input handling,
  not just a one-line guard.
- Exceeds the fix limits above, the root cause isn't confirmed, or there
  are several valid behaviors and the team must choose.
- Security vulnerabilities, data loss, or production blockers, whatever
  the size.

## AI-Generated Content

Judge the **writing style** of the author's own text: the title, the body,
and the author's comments. Ignore other users' and bots' comments. This
check runs right after the hidden-content gate and before every other
outcome, whatever the category.

If an earlier triage already accepted the issue (a bot triage comment other
than `needs-rewrite` exists and it isn't labeled `requires-rewrite`), judge
only the author's comments posted since, so the verdict doesn't flip-flop.

**Style signals:**

- Over-explanation: long preambles, restating the problem several times,
  explaining general concepts the reader already knows.
- Report-style headers, especially on a short report ("Summary", "Impact",
  "Root Cause", "Recommendation", "Proposed Solution", "Conclusion").
- Heavy bold: many bolded phrases per paragraph.
- Stock filler phrases ("comprehensive", "robust and scalable", "it is
  worth noting", "seamless", "leverage").
- Generic, hedged prose with few specifics (versions, file paths,
  commands, actual output).
- Emoji section markers (e.g. a rocket or checkmark before each heading).
- Closing pleasantries such as "I hope this helps".

**Tool attribution (decisive on its own):** the title, body, or one of the
author's comments carries an AI tool's generated-by footer, such as
"Generated with Claude Code", "Generated by Claude Code", "Generated with
[Claude Code](...)" (often after a robot emoji), or the equivalent from
Copilot, Cursor, Codex, Devin, ChatGPT, or similar. That means the text
itself was generated, so the outcome is `rewrite` even without other
signals.

Otherwise, **"highly AI-generated"** means **several** of these signals are
clearly present across the text. One signal is never enough: a header, some bold,
a translated phrase, or tidy formatting is how many people write. Never
decide from a detector score or because the writing is polished or in
non-native English.

**Substantive fabrication signals** (verify each with `Read`/`Grep`/the
scripts):

- References files, functions, APIs, config options, or packages that
  don't exist in this repository.
- Code snippets or stack traces that don't match the repository (wrong
  signatures, nonexistent modules, impossible line numbers).

| Signals present | Outcome |
|-----------------|---------|
| Several style signals, no verified fabrication | `rewrite` with `needs-rewrite`; summary names, neutrally, what makes it hard to act on (e.g. "the report is mostly general prose with no version, steps, or actual error output") |
| Several style signals **and** at least one verified fabrication | `slop` with `close-ai-slop`; summary names the concrete problems (e.g. "the referenced `CartService.recalculate` method does not exist") without accusing the author |
| Fabrication without the style signals | Judge on the merits: usually `needs-info` or `close-invalid` |
| Neither, or only one or two weak style signals | Continue the normal flow |

### Re-triage of an issue labeled `requires-rewrite`

The issue is re-triaged when the author edits it or replies. Judge the
**latest** version of the author's text: the current title and body, plus
any reply in which they restate the problem.

- Still highly AI-generated: pick `rewrite` again. The request isn't
  repeated and the 8-hour deadline isn't reset.
- Now in the author's own words: the rewrite is accepted. Ignore the old
  wording and run the normal flow on the rewritten content. The workflow
  removes `requires-rewrite` for any outcome other than `rewrite`.
- Never pick `none` for an issue labeled `requires-rewrite`: it also
  removes the label. Decide `rewrite` or a real outcome.
