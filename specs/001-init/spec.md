## Context & Motivation

The existing `undrlla` (located at `C:\Repositories\underundre-to-transfer\undrlla\`) is a Next.js Pages Router e-commerce platform for custom PC builds, IT-services, and VPN provisioning. It is mono-tenant per region (GLOBAL / EU; RU sunset per Decision 4) and operates on a centralized Hetzner/OVH-style infrastructure with Stripe / PayPal / BTCPay / SHKeeper / manual bank payment rails.

This feature defines the **complete rewrite** of undrlla onto:

1. A **Medusa v2** commerce backend (selected by weighted-criteria scoring — see `decisions/foundation-matrix.md`, average score **8.42 / 10**)
2. A **Hybrid decentralized hosting model** combining Akash Network (DePIN compute), open-source Federation distribution, and a centralized hardened "hot core" for secrets (selected by weighted-criteria scoring — see `decisions/decentralization-matrix.md`, average score **8.87 / 10**)
3. Integration with the **OmniRoute** AI gateway and **undrestrator** AI orchestrator (both reside at `C:\Repositories\underundre\underhelpers\under-ai-helpers\`)
4. A **Hybrid tenancy model** — mono-tenant + B2B workspaces today, full multi-tenant white-label when the second commercial reseller signs

The rewrite is staged to preserve every revenue-generating function of the current undrlla while removing accumulated technical debt, modernizing the AI surface, and opening a distribution model where independent operators can host their own branded instances.

## User Scenarios & Testing _(mandatory)_

### User Story 1 — B2C Migration Cutover (Priority: P1)

A retail customer browses the new undrlla v2 storefront, configures a custom PC via the AI-assisted builder, pays with their preferred method (Stripe / PayPal / BTCPay / SHKeeper / manual bank transfer), receives an order confirmation, and gets a provisioned VPN account if it was part of the order — all within the new Medusa-backed stack with **zero data loss** from the legacy store.

**Why this priority**: This is the **MVP**. Without it, the migration has no business value and the legacy undrlla cannot be sunset. Every other story depends on the commerce backbone working.

**Independent Test**: Place 10 representative orders (one per payment method × at least one PC-build, one VPN-only, one mixed) on a staging deployment that imports a snapshot of legacy production data. Each must complete with the same artifacts (order record, payment record, VPN peer config, notification) as the legacy system.

**Acceptance Scenarios**:

1. **Given** a legacy customer with order history, **When** they log in on undrlla v2 with their legacy credentials, **Then** they see their full order history, saved addresses, and active VPN peers without re-registration.
2. **Given** a customer configuring a PC on the AI builder, **When** they select incompatible components (e.g. AM5 CPU + LGA1700 motherboard), **Then** the system blocks checkout with a clear human-readable explanation generated by the AI advisor.
3. **Given** a paid order containing a 12-month VPN, **When** the BTCPay invoice settles on chain, **Then** the VPN peer is provisioned, the config is delivered (encrypted email + dashboard download), and the customer is notified via their chosen channel within 5 minutes.

### User Story 2 — AI-Augmented Purchase Flow (Priority: P2)

A customer who knows their use case but not the hardware ("I want to play Cyberpunk 2077 at 1440p Ultra under $1500") chats with the **PC-builder AI advisor**, receives a complete shortlist of 2–3 compatible builds with explanations, can swap individual components with live compatibility checking, and proceeds to checkout — without leaving the chat surface.

**Why this priority**: This is the **AI differentiator**. It transforms undrlla from "another PC store" into an AI-first storefront. It also dogfoods the OmniRoute / undrestrator stack at customer-facing scale.

**Independent Test**: Submit 30 representative customer briefs (gaming / workstation / silent-build / budget / no-compromise) and verify that each produces ≥2 valid builds, that every component combination passes the compatibility engine, that the explanation cites at least one objective benchmark (FPS, watt, dB) per build, and that latency from brief submission to first build is ≤8 seconds (P95).

**Acceptance Scenarios**:

1. **Given** the advisor produces a build, **When** the customer asks "make it quieter under $1600", **Then** the advisor swaps the cooler/fans/PSU/case to noise-optimized parts while staying within budget and re-validates compatibility.
2. **Given** a paid customer using the platform's AI quota, **When** the customer's token quota is exhausted mid-conversation, **Then** the system either degrades gracefully to a cheaper model (via OmniRoute auto-fallback) or prompts for an upgrade — never a hard 500.
3. **Given** a BYOK customer, **When** their key is invalid, **Then** the advisor surfaces a non-leaky error and prompts re-entry — without falling back to the platform's keys.

### User Story 3 — Multi-Channel Customer Support Agent (Priority: P3)

A customer messages the brand on Telegram / WhatsApp / website widget. An AI agent handles routine queries (order status, VPN reset, FAQ) end-to-end and escalates non-routine matters to a human operator with the full conversation context, while the human can take over the same channel mid-conversation.

**Why this priority**: Reduces support cost dramatically and converts a long-tail of inquiries that today go un-answered. Less critical than P1/P2 because the legacy Telegram bot already covers a baseline.

**Independent Test**: Run 50 scripted conversations across all three channels covering 5 intent buckets (status / VPN / refund / pre-sale / off-topic). Measure resolution rate without escalation (target ≥60%), correct escalation rate (≥95% precision on non-routine), and zero PII leakage in error responses.

**Acceptance Scenarios**:

1. **Given** an agent operating on customer paid AI tier, **When** token usage exceeds the customer's plan, **Then** the next message is metered and the customer is notified at 80% / 100% thresholds.
2. **Given** an escalation, **When** a human operator joins, **Then** they see the full transcript and the agent stops responding until handed back.
3. **Given** Evolution API instance crashing, **When** WhatsApp connection is lost, **Then** the system reconnects within 60 seconds and reprocesses any queued messages without duplication.

### User Story 4 — BYOK Customer AI Path (Priority: P3)

A privacy-conscious or cost-conscious customer brings their own OpenAI / Anthropic / OpenRouter / local Ollama key, the platform routes all of that customer's AI traffic through their key (zero platform cost), and the customer sees their own provider's usage in their own dashboard.

**Why this priority**: Removes a major adoption barrier for enterprise / power-user customers. Lower priority than P1/P2 because the platform-tier AI path covers the mass-market case.

**Independent Test**: Configure a BYOK key for a test tenant, run 10 representative conversations, verify that (a) no traffic uses platform keys, (b) the platform records zero billable token usage on the customer's account, (c) the customer's own provider dashboard shows matching usage.

**Acceptance Scenarios**:

1. **Given** a tenant on BYOK mode, **When** they add a second provider (e.g. Anthropic in addition to OpenAI), **Then** they can pick per-use-case routing in their dashboard.
2. **Given** a BYOK tenant exceeds their own provider's rate limit, **When** OmniRoute receives 429, **Then** the system surfaces the upstream rate-limit message to the customer without falling back to platform keys.

### User Story 5 — Akash Deployment of Primary Instance (Priority: P4)

The primary `undrlla.com` instance is deployed to Akash Network from a single SDL manifest, runs at 60–86% lower compute cost than equivalent AWS, and survives the loss of any individual Akash provider via redundancy.

**Why this priority**: Validates the decentralization thesis with real production traffic, captures the cost-reduction benefit, and produces the artifact (SDL + ops runbook) that community-operators will reuse in P3-Story-6.

**Independent Test**: Deploy a green environment on Akash, run blue-green cutover from the legacy infra, monitor for 14 days, measure compute cost vs. baseline, perform a controlled provider-kill test and verify automatic failover within target RTO/RPO.

**Acceptance Scenarios**:

1. **Given** a deployed undrlla v2 on Akash, **When** the chosen provider goes offline, **Then** traffic fails over to the redundant provider within 5 minutes P95 (resolved: per research.md A2) and no in-flight order is lost.
2. **Given** customer PII in Postgres, **When** any state is written, **Then** payment secrets and VPN master keys remain on the centralized hardened core — never on Akash.
3. **Given** the Akash deployment, **When** the SDL filters by jurisdiction, **Then** only providers in approved jurisdictions are eligible.

### User Story 6 — Community-Operator Onboarding (Priority: P4)

An independent operator clones the open-source undrlla repo, runs a single install command, configures their branding / payment merchants / VPN endpoints, and is live serving their own customers within 1 hour on the deployment target of their choice (Akash / VPS / self-hosted).

**Why this priority**: Distribution lever. Each successful community-operator multiplies undrlla's market presence without ops cost on the maintainer.

**Independent Test**: Have a non-team developer (proxy for community-operator) perform a fresh install on a clean Hetzner VPS and on an Akash deployment, measure time-to-first-paid-order and total questions asked. Target: ≤1 hour, ≤3 questions to the maintainer.

**Acceptance Scenarios**:

1. **Given** the open-source repo, **When** the operator runs the install script, **Then** all schema migrations, seed data, default settings, and configuration scaffolds are created idempotently.
2. **Given** a configured community instance, **When** the operator updates from the upstream repo, **Then** the migration runs without data loss and the customizations (branding, products, prices) are preserved.

### User Story 7 — Internal Operations Automation (Priority: P5)

When a complex ticket arrives (e.g. "my AmneziaWG keeps dropping after 30 minutes on iOS"), an internal Hermes-driven undrestrator pipeline diagnoses the WireGuard config, proposes a fix, applies the fix in a worktree, runs the relevant tests, and produces a PR for the operator to merge.

**Why this priority**: Reduces the operator's time on long-tail technical issues. Lowest priority because human operators can handle these manually for the first phase.

**Independent Test**: Run the pipeline against 20 historical real tickets (with known resolutions). Measure proposal-correctness rate (target ≥50% on first proposal) and proposal-safety rate (≥95% never proposes a destructive change without confirmation).

**Acceptance Scenarios**:

1. **Given** a ticket containing PII, **When** the pipeline runs, **Then** PII is redacted before being sent to any LLM and the redaction map stays on the hot core.
2. **Given** the pipeline proposes a fix, **When** the fix changes a production config, **Then** the operator must explicitly approve before apply.

### Edge Cases

- **Payment provider outage mid-checkout** — order should be held in `pending_payment` and resumable once the provider recovers; no silent loss of cart state.
- **Akash provider goes offline mid-request** — open connections terminate gracefully; the next request lands on the failover provider; persistent volumes are snapshotted and restorable.
- **Community-operator forks and modifies schema** — upstream migrations detect drift and refuse to run with a clear message instead of corrupting data.
- **OmniRoute exhausts all configured providers** — degrade gracefully to a cached / static response with a clearly-labeled "AI temporarily unavailable" notice; never serve a stale answer as live.
- **VPN peer creation race condition** — when two concurrent orders request the same IP pool slot, only one succeeds and the other re-allocates from the pool; no double-assignment.
- **Tenant-scope leak attempt** — a malicious authenticated request from tenant A trying to read tenant B's data must fail with 404 (not 403) so existence is not leaked.
- **BYOK key revocation mid-session** — when the customer's upstream key is revoked, the session ends gracefully with a clear message; no platform-key fallback.
- **Federation instance maintainer abandons their instance** — customers should be able to export their data via a self-service flow without depending on the maintainer.
- **Currency / locale switch with cart** — switching region clears cart with an explicit warning rather than silently re-pricing.
- **Crypto payment confirmation arrives after refund window** — the system reconciles correctly even if BTCPay sends a late settlement notification.

## Requirements _(mandatory)_

### Functional Requirements

#### Commerce Backbone

- **FR-001**: System MUST run a Medusa v2 backend as the source of truth for catalog, cart, order, inventory, fulfillment, and returns.
- **FR-002**: System MUST present a Next.js (App Router) storefront that consumes Medusa via its REST/JS-SDK and supports server components for SEO-critical pages.
- **FR-003**: System MUST support at least these payment providers concurrently: Stripe, PayPal, BTCPay Server, and manual bank transfer with operator-side reconciliation. SHKeeper deferred post-launch per Decision 4 (RU-bias rail, RU market out of scope).
- **FR-004**: System MUST migrate 100% of legacy orders, customers, products, addresses, and active VPN peer assignments from the legacy `undrlla` database with cryptographic integrity verification per record.
- **FR-005**: System MUST preserve every active customer's login credentials (or provide a transparent password-reset link flow on first v2 login).

#### Tenancy

- **FR-006**: System MUST include a `tenant_id` column on every customer-scoped table from day one, even when only the `default` tenant exists, to permit later multi-tenant activation without schema migration.
- **FR-007**: System MUST use Medusa Sales Channels as the runtime abstraction for tenant-scoped product visibility, pricing, and payment-provider configuration.
- **FR-008**: System MUST provide a workspace abstraction in the Next.js storefront so a single instance can serve more than one brand (subdomain or path-based routing).
- **FR-009**: System MUST enforce tenant scoping at the ORM layer (Prisma extension or Medusa custom-module middleware) — no route handler may bypass the tenant filter.

#### AI Surface

- **FR-010**: System MUST integrate OmniRoute as the AI gateway, deployed as a sidecar service, accessible to the application via its local HTTP endpoint.
- **FR-011**: System MUST support three AI deployment tiers per tenant: **dev** (operator's own keys for internal automation), **paid** (platform-managed keys with metered billing), and **BYOK** (customer-supplied keys with zero platform cost).
- **FR-012**: System MUST meter every AI request with at minimum: tenant, user, model, prompt-tokens, completion-tokens, cost-USD, and use-case tag.
- **FR-013**: System MUST bill metered AI usage via a usage-event pipeline compatible with OpenMeter and Killbill (or Stripe Metered as fallback).
- **FR-014**: System MUST expose a PC-builder AI advisor with access to the live catalog (RAG over Medusa products) and a compatibility engine.
- **FR-015**: System MUST route incoming Telegram, WhatsApp, and website widget conversations through a single AI agent surface with human-takeover capability.
- **FR-016**: System MUST integrate undrestrator for batch content/SEO generation (product descriptions, meta tags, multi-locale translations) on a schedule or on-demand.
- **FR-017**: System MUST integrate undrestrator pipelines for internal operations automation (ticket triage, config generation, PR proposal).

#### VPN & Services

- **FR-018**: System MUST provision VPN peers (WireGuard, AmneziaWG, and Xray) via SSH or API on order payment-capture, idempotently and with rollback on failure.
- **FR-019**: System MUST host VPN servers (WireGuard / AmneziaWG / Xray) and their master keys, peer private keys, and provisioning credentials on a centralized hardened enterprise infrastructure (dedicated Hetzner / OVH in GDPR-compatible jurisdictions). VPN servers and keys MUST NOT be hosted on Akash, on community-operator infra, or anywhere outside the operator's own controlled enterprise environment.
- **FR-020**: System MUST allocate VPN peer IPs from a per-server pool with a race-safe acquisition primitive.

#### Hosting & Deployment

- **FR-021**: System MUST package the full stack as a single `docker-compose.yml` runnable on any Linux host.
- **FR-022**: System MUST publish an Akash SDL manifest that deploys an equivalent topology to Akash Network with persistent storage for Postgres.
- **FR-023**: System MUST support a 1-command install for community-operators that bootstraps the database, applies migrations, seeds defaults, and starts services idempotently.
- **FR-024**: System MUST keep payment-provider secrets, VPN master keys, and KYC vault data on the centralized hot core, encrypted at rest with AES-256-GCM, behind dedicated hardened infrastructure.
- **FR-025**: System MUST restrict Akash provider selection (via SDL constraints) to providers located in GDPR-compatible jurisdictions (EU/EEA + UK + Switzerland + GDPR-equivalent third countries with EU adequacy decision). Non-GDPR-compatible providers MUST be excluded by default.
- **FR-026**: System MUST survive the failure of any single Akash provider without data loss via persistent-volume replication and active failover.

#### i18n / Multi-Region

- **FR-027**: System MUST support at minimum GLOBAL and EU regions (RU region explicitly out of scope — see Clarification Decision 4) with their respective currencies, payment provider sets, locales, and tax rules from day one. EU region MUST be GDPR-compliant.
- **FR-028**: System MUST drive region selection from URL/subdomain and persist the customer's chosen region across sessions.
- **FR-028a**: System MUST provide a documented migration path for legacy RU-region customers, including data export and account closure under GDPR-equivalent rights (since the v2 platform no longer serves RU as a region).

#### Observability & Security

- **FR-029**: System MUST emit structured logs (pino / consola) with tenant context on every request, persisted to Loki or equivalent.
- **FR-030**: System MUST trace every AI request via Langfuse with tenant tag and cost.
- **FR-031**: System MUST emit infrastructure metrics via Prometheus / VictoriaMetrics, alerting on per-tenant error-rate, latency, and AI-cost anomalies.
- **FR-032**: System MUST send errors to GlitchTip or Sentry-compatible sink with PII redaction at the boundary.
- **FR-033**: System MUST never log a payment secret, an AI API key, a VPN private key, or a KYC document — including in stack traces.

#### Federation & Distribution

- **FR-034**: System MUST publish the full source under a pure MIT license (resolved: pure MIT per research.md A1; monetize via managed hosting, not license restrictions).
- **FR-035**: System MUST provide first-class documentation for community-operators covering install, configure, upgrade, backup/restore, and incident response.
- **FR-036**: System MUST expose a tenant data export endpoint that produces a portable archive (orders, customers, products, payments, VPN peers) for a tenant to migrate off the platform if needed.

#### Migration

- **FR-037**: System MUST provide a migration tool that reads legacy `undrlla` Postgres and writes to Medusa v2 schema with dry-run, resumable, and verification modes.
- **FR-038**: System MUST run dual-write during cutover (legacy + v2 receive every order) for a configurable cutover window with reconciliation reporting.
- **FR-039**: System MUST support a tenant-by-tenant cutover where each tenant can switch independently from legacy to v2.
- **FR-040**: System MUST retain the legacy `undrlla` deployment in read-only mode for 1 year post-cutover for historical access, followed by 7-year cold archive (resolved: per research.md A3).

### Key Entities _(include if feature involves data)_

- **Tenant** — A workspace boundary; represents either a region (GLOBAL / RU) or a B2B reseller / white-label operator. Owns its branding, payment-provider configuration, AI tier, and Sales Channel binding.
- **Workspace** — A storefront-level grouping a customer interacts with; maps 1-to-1 to a Tenant in the mono-tenant phase, 1-to-N possible in multi-tenant phase.
- **Customer** — An end-user of a Tenant. Has order history, VPN peer assignments, AI usage events, and optionally a BYOK key vault entry.
- **Product** — A catalog item (PC component, complete build, VPN plan, IT service); scoped to one or more Sales Channels.
- **Order** — A transaction record; references Customer, Tenant, Products, PaymentTransaction, and optionally one or more VPNPeer assignments.
- **PaymentTransaction** — A provider-agnostic record of a payment attempt; references Order, payment provider, provider transaction ID, status, settlement timestamp.
- **VPNServer** — A physical/virtual server running WireGuard/AmneziaWG/Xray; has a peer pool, location metadata, capacity counter.
- **VPNPeer** — An allocated peer slot on a VPNServer; references Customer, Order, allocated IP, public key, configuration archive reference.
- **AIUsageEvent** — A metered event from OmniRoute; references Tenant, Customer, AI tier, provider, model, token counts, cost-USD, use-case tag.
- **AIKeyVault** — An encrypted store of BYOK customer keys; never serialized in logs or responses; decrypted only inside OmniRoute request paths.
- **FederationInstance** _(future)_ — A registered third-party-operated instance of undrlla; metadata only (domain, contact, opt-in catalog visibility); no shared state.
- **MigrationJournal** — A record of every entity migrated from legacy, with source ID, target ID, content hash, timestamp, and verification status.

## Decisions Summary

Two design decisions are codified as scoring matrices in this spec so any future contributor can audit, challenge, or re-run the comparison against new candidates:

### Decision 1 — Commerce Foundation

See [`decisions/foundation-matrix.md`](decisions/foundation-matrix.md) for the full 12-criterion scoring matrix.

**Winner**: **Medusa v2** with weighted average **8.42 / 10**.

| Candidate | Weighted Average |
|-----------|------------------|
| 🥇 Medusa v2 (TS, MIT, modular) | **8.42** |
| 🥈 Vendure (NestJS, MIT) | 7.95 |
| 🏅 Nextacular + custom commerce | 7.80 |
| 🥉 Saleor (Python, BSD-3) | 7.43 |

### Decision 2 — Decentralization Model

See [`decisions/decentralization-matrix.md`](decisions/decentralization-matrix.md) for the full 12-criterion scoring matrix.

**Winner**: **Hybrid (Akash + Federation + Centralized Hot Core)** with weighted average **8.87 / 10**.

| Candidate | Weighted Average |
|-----------|------------------|
| 🥇 Hybrid (Akash + Federation + Hot Core) | **8.87** |
| 🥈 Federation only (community-run instances) | 8.53 |
| 🏅 Pure Akash (DePIN compute only) | 7.66 |
| 🥉 Status quo (centralized Hetzner / AWS) | 7.35 |

### Decision 3 — Tenancy Model

**Selected**: **Hybrid tenancy** — mono-tenant + B2B workspaces today, full multi-tenant white-label when the second commercial reseller signs.

Rationale: full multi-tenant adds 3–5× engineering load (VPN per-tenant isolation, payment-key partitioning, compliance per-jurisdiction) before there is a single paying reseller. Hybrid keeps the `tenant_id` foreign-key abstraction throughout the data model so the activation cost later is bounded.

### Decision 4 — AI Tier Model

**Selected**: **3-tier** — dev (operator), paid (platform-billed), BYOK (customer-supplied).

Rationale: covers the privacy/cost spectrum without forcing customers into a single model. OmniRoute already supports per-key routing, making the multi-tier resolution a thin middleware on top of the gateway.

## Migration Roadmap (post-Phase-2; ASAP-driven, AI-augmented)

Compressed to a 4-month stretch target. AI augmentation (Hermes via undrestrator + Claude/Codex/Gemini through OmniRoute) is assumed as a force multiplier on every phase — code generation, test scaffolding, migration tooling, documentation drafts. No phase has a hard deadline; quality gates take precedence over speed.

| Phase | Stretch target | Outcome |
|-------|----------------|---------|
| **0 — Foundation** | Weeks 1–2 | Medusa v2 + Next.js (App Router) storefront + Postgres + Redis on local dev; CI green; legacy data dump anonymized for staging; Hermes/undrestrator wired for code-generation help |
| **1 — Core Commerce Parity** | Weeks 3–6 | Catalog, cart, checkout; payment providers Stripe + PayPal + BTCPay (SHKeeper deferred — was RU-bias); VPN provisioning module (port-with-clean-rewrite from legacy); i18n GLOBAL+EU; staging passes 100% of legacy regression tests on EU subset of legacy data |
| **2 — AI Surface** | Weeks 5–8 (overlaps Phase 1) | OmniRoute sidecar + PC-builder AI advisor + multi-channel support agent (Telegram + WhatsApp + widget) + content/SEO batch + 3-tier (dev/paid/BYOK) + Langfuse tracing + OpenMeter metering |
| **3 — Decentralization Activation** | Weeks 9–12 | Akash SDL manifest + GDPR-jurisdiction filter + persistent volume strategy + green deployment on Akash; centralized hot core (payment secrets + VPN master keys + KYC vault) hardened and audited; provider-failure drill |
| **4 — Cutover & RU Sunset** | Weeks 13–14 | Dual-write window for GLOBAL/EU customers; RU-region read-only freeze + GDPR-style data export offered to RU customers; reconciliation report; legacy switched to read-only |
| **5 — Federation** | Weeks 15–16 | Open-source repo published under MIT, full docs, 1-command install script, Discord/Matrix community channel, first 1–2 community-operator instances onboarded |
| **6 — Multi-Tenant Activation** _(deferred)_ | When second commercial reseller signs | Activate `tenant_id` filters end-to-end; activate per-tenant Sales Channels; enable subdomain routing; per-tenant payment-provider keys |

### AI augmentation strategy per phase

- **Hermes via undrestrator** — code generation for repeatable patterns (Medusa Module skeletons, payment provider implementations, migration scripts, test fixtures); pipeline review-loops on every PR
- **Claude / Codex / Gemini through OmniRoute** — pair-programming on complex flows (VPN provisioning, multi-tenant ORM extension, federation install script)
- **Specs to tasks pipeline** — `/speckit.full-plan` + `/speckit.tasks` to break each phase into agent-routable units; parallel worktrees via undrestrator ensemble engine
- **Documentation drafts** — first pass generated, human-edited (cuts time-to-release by ~50% on docs)

Stretch is aggressive but realistic if AI tooling does not regress and the operator stays disciplined on quality gates (no merge without `npm run validate` + tests green).
