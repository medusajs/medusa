# Order Notes & Tags Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Resurrect Medusa's dormant order-notes feature, extend notes to customers and order line items, and add a shared order-tag vocabulary with bulk apply/remove — the first sub-project of the larger "Veeqo-style order page" effort.

**Architecture:** A new minimal `note` module (`Note`: polymorphic `resource_type`/`resource_id`, no FK) provides create/list/delete for all three note surfaces through one API. A new `OrderTag` model inside the existing `order` module mirrors `ProductTag` exactly (shared vocabulary, many-to-many, bulk apply/remove via a batch endpoint). Admin dashboard UI reconnects existing dead code for order notes and adds new sections/columns for customer notes, line-item notes, a list-level notes indicator, and tags.

**Tech Stack:** Medusa v2 modules (`MedusaService`), workflows-sdk (`createStep`/`createWorkflow`), admin HTTP routes + Zod validators, JS SDK, React admin dashboard (`@medusajs/ui`, React Hook Form, Zod), Jest integration tests.

**Spec:** `docs/superpowers/specs/2026-10-21-order-notes-and-tags-design.md`

## Global Constraints

- Prettier: no semicolons, double quotes, 2-space indentation, ES5 trailing commas, parens around all arrow-function params.
- Migration files are always generated by running `yarn migration:create` from within the affected module package (`packages/modules/note`, then later `packages/modules/order`) — never hand-written. Rerun it if the model changes again before the migration is committed.
- Every changed published package gets its own `patch` changeset — never `major` — per `CLAUDE.md`.
- `Note.author_id` is always derived server-side from the authenticated admin user; the API must never trust an `author_id` value in a request body.
- Any authenticated admin may delete any note — deletion is not author-restricted (explicit v1 scope decision).
- Notes are create/delete only — no update/edit endpoint.
- No live Veeqo integration anywhere in this feature; Veeqo was only a UX reference during design.
- No emojis in code, comments, or copy.

## Review Focus

- A client sends `author_id` in the `POST /admin/notes` body, or a `resource_type` outside the allowed enum — the server must ignore the former and reject the latter, not silently store attacker-controlled data. (Task 2)
- A user types an already-existing tag's name into the create-on-type tag combobox — this must reuse the existing tag by value, not throw a raw unique-constraint error. (Task 10)
- A bulk-tag batch request includes the same tag id in both `add` and `remove` — the outcome must be deterministic (remove wins), not a race between two array operations. (Task 11)
- A bulk-tag batch request references an order id or tag id that doesn't exist — the whole batch must fail before mutating any order, not partially apply then error. (Task 11)
- The order list's batched "has notes" lookup is called with zero selected ids or a full page of ids — it must return exactly the subset that has notes without erroring on either extreme. (Task 2, consumed by Task 8)
