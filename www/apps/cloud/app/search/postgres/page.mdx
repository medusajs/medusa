# {metadata.title}

In this guide, you'll compare [Medusa Search](../page.mdx) to the [PostgreSQL Search Module Provider](!resources!/infrastructure-modules/search/providers/postgres) so you can decide which one to use for your Medusa project.

## What is Medusa Search?

Medusa Search is a managed search service for Cloud projects. It stores your search indexes outside of your database and serves search queries for them, from full-text queries with relevance ranking to vector search over embeddings.

The [Search Module](!resources!/infrastructure-modules/search) drives it through a provider that ships with Medusa. Cloud registers and configures that provider for every environment, so Medusa Search needs no setup. You declare an index definition in your codebase, and query it with [`query.search`](!docs!/learn/fundamentals/query/search).

Unlike Algolia or Meilisearch, PostgreSQL is also a Search Module Provider that Medusa ships, so this comparison is between two providers rather than between Medusa and a third-party service. Both read the same index definitions and answer the same `query.search` calls. What differs is where the index lives and which parts of a query each one can serve.

## Setup and Infrastructure

Medusa Search is part of Cloud, so there's nothing to provision. Cloud creates the search resources for every environment and passes the credentials to your Medusa application, which registers the provider for you.

The PostgreSQL provider needs no external service, since it indexes into the database your Medusa application already uses. What it does need is setup inside that database:

1. Run `db:migrate` to create the provider's tables, its extensions, and its text search configuration. The command also creates the index for every definition you declared.
2. Run `db:migrate` again after you create or change an index definition, since the physical table follows the definition.
3. Choose an engine. The default `native` engine covers full-text search, and the `lakebase` engine adds vector and hybrid search.
4. Configure a language other than English, if your catalog needs one, through the provider's `language` option.
5. Size your database for the extra work, since every search query and every index write runs against it.

Step 5 is the one that's simple to miss. The index lives beside your orders and your products, so a heavy search workload competes with checkout for the same CPU, memory, and disk. Medusa Search moves that load off your database entirely.

Both providers create their indexes through `db:migrate` rather than at application start, so neither one migrates while your application boots.

### Local Development

Medusa registers the PostgreSQL provider locally by default, so you declare an index definition and search it locally with no extra service to run.

Medusa Search runs on Cloud only, so a Cloud project uses two providers across its lifecycle: PostgreSQL locally and Medusa Search once deployed.

## Integration with Medusa

Both providers ship with Medusa and implement the same [Search Module Provider](!resources!/infrastructure-modules/search/providers) interface, so there's no integration code to write for either one. You declare an [index definition](!resources!/infrastructure-modules/search/index-definitions) in a file under `src/search`, and the module creates the index, fills it, applies events to it, and compiles your queries.

```ts title="src/search/brand.ts"
export const brandIndex = defineSearchIndex({
  name: "brand",
  entity: "brand",
  fields: search.define({
    id: search.keyword().filterable(),
    name: search.text().searchable({ weight: 3 }),
    country: search.keyword().filterable().facetable(),
  }),
  events: ["brand.created", "brand.updated"],
  async consume(event, { container }) {
    // return the documents to upsert or delete
  },
  async *seed({ container }) {
    // yield the documents that fill the index
  },
})
```

Refer to [Searching Custom Data Models](../page.mdx#searching-custom-data-models) for the full example.

## Search Capabilities

A provider that can't serve part of a request rejects it instead of answering differently. The tables below say when that rejection happens:

- **Fails at startup**: the provider throws while the Search Module creates or migrates the index, so your application doesn't boot or `db:migrate` fails.
- **Fails per query**: the provider throws for the requests that use the feature. Other requests are unaffected.
- **Ignored**: the provider accepts the request and doesn't act on the feature, so results look as if you never passed it.

Refer to [`searchable()`](!resources!/infrastructure-modules/search/index-definitions/modifiers#searchable) for how each provider reads a field's weight.

      </Table.Cell>
    </Table.Row>
  </Table.Body>
</Table>

<Note title="Don't use Medusa Search if" type="warning">

- Typo tolerance is a requirement for your storefront search.
- You need to sort by an attribute and rank by relevance in the same query.
- You need a `stats` facet, `min_score`, or `match_strategy: "all"`.
- You paginate beyond the 10,000th result.
- You can't accept an index that empties while it rebuilds.

</Note>

## Querying and Storefront Integration

{/* TODO add info about instantsearch plugin */}

Both providers answer the same [`query.search`](!docs!/learn/fundamentals/query/search) call from an API route, so your storefront code doesn't change when you switch between them:

```ts title="src/api/search-brands/route.ts"
const { data, search_result } = await query.search({
  entity: "brand",
  fields: ["id", "name", "country"],
  filters: { q: req.query.q as string },
  pagination: { take: 20 },
})
```

Neither provider supports querying from the browser, so search always runs behind your API routes. That gives you one place to enforce authorization and shape results, with no public index and no browser-side key to scope.

The difference is which options each one rejects, which is why a storefront that works locally against PostgreSQL can fail on Cloud against Medusa Search. Build against the narrower of the two, or gate the options you pass on the provider in use.

## Admin Dashboard Search

The Medusa admin dashboard's global search calls the `/admin/search` API route, which uses the Search Module for every entity that has an index and falls back to database queries for the rest. Both providers sit inside the module, so admin search works with either one.

The PostgreSQL provider has one advantage here: it works locally, so you see the indexed admin search behavior in development rather than after a deployment.

## Environments and Previews

Cloud gives each environment its own set of Medusa Search indexes, scoped by the environment's handle, so a preview environment never writes to production indexes. When you configure a base environment in the [shared previews settings](../../environments/preview/page.mdx#manage-shared-previews-settings), Cloud copies the base environment's indexes into the new preview environment along with its database.

PostgreSQL indexes need no separate arrangement, since they're tables in the database. An environment's indexes travel with its database, so a database copy brings a filled index with it and a fresh database starts with an empty one.

### Other Cloud Usage This Affects

The PostgreSQL provider changes which Cloud metrics your search workload lands on. Only Medusa Search counts toward the [Search](../../usage/page.mdx#usage-metrics-definitions) metric, so PostgreSQL search requests never appear there. They show up elsewhere instead:

- **Database Storage** grows with every index, since each one is a table in your database. A large catalog with several indexes adds gigabytes to the metric you're billed on, on top of your commerce data.
- **Compute** covers the indexing work, since the seed and the event handlers that fill an index run in your Medusa application.

Medusa Search keeps both off your database and meters the queries under Search instead. Refer to [Usage](../../usage/page.mdx) to monitor either one.

## Which One to Choose

**Choose Medusa Search if:**

- Your project runs on Cloud and you want search off your database, so a traffic spike in search doesn't slow down checkout.
- Your catalog is large enough that indexes competing with your transactional workload is a real concern.
- Filters, facets, sorting, and weighted full-text search cover your requirements.

**Choose the PostgreSQL provider if:**

- You self-host your Medusa application, since Medusa Search runs on Cloud only.
- You want vector or hybrid search that the provider serves for you on the `lakebase` engine.
- Your search volume is modest enough that your database absorbs it without a bigger tier.

You don't have to pick one for everything. The Search Module accepts more than one provider, so you can point a high-traffic storefront index at Medusa Search and keep a low-traffic admin index on PostgreSQL.
