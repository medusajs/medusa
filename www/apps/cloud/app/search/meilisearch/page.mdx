# {metadata.title}

In this guide, you'll compare [Medusa Search](../page.mdx) to Meilisearch so you can decide which one to use for your Medusa project.

<Note title="Not a Cloud user yet?">

[Sign up for Cloud](../../sign-up/page.mdx) to use Medusa Search and other Cloud features.

</Note>

## What is Medusa Search?

Medusa Search is a managed search service for Cloud projects. It stores your search indexes outside of your database and serves search queries for them, from full-text queries with relevance ranking to vector search over embeddings.

The [Search Module](!resources!/infrastructure-modules/search) drives it through a provider that ships with Medusa. Cloud registers and configures that provider for every environment, so Medusa Search needs no setup. You declare an index definition in your codebase, and query it with [`query.search`](!docs!/learn/fundamentals/query/search).

## Setup and Infrastructure

Medusa Search is part of Cloud, so there's nothing to provision. Cloud creates the search resources for every environment and passes the credentials to your Medusa application, which registers the provider for you.

Meilisearch takes considerably more work before you can run a single search:

1. Run the engine yourself, or create a Meilisearch Cloud project. Self-hosting also puts the host, the backups, the monitoring, and every version upgrade on you.
2. Provision an index for every environment, and pick a naming scheme that keeps them apart.
3. Generate a write key and a search-only key, then store both as environment variables in every Cloud environment.
4. Configure the index settings, including the order of `searchableAttributes`, the `filterableAttributes`, the `sortableAttributes`, typo tolerance, and the ranking rules.
5. Repeat steps 2 to 4 for every environment you add, and keep the settings identical across all of them.

Step 4 is the one that keeps costing you. Meilisearch stores the index settings on the instance rather than in your codebase, so they drift out of version control unless you push them from code as part of a deployment. A fresh instance with the defaults answers the same query with different relevance than your production one.

You then connect Meilisearch to Medusa, which requires creating a Search Module Provider as explained in the [Integration with Medusa](#integration-with-medusa) section.

<Note title="Self-hosting next to Cloud">

If your Medusa application runs on Cloud, a self-hosted Meilisearch instance still needs a host somewhere, and search queries then travel from your Cloud environment to that host. Factor that hop and the instance's availability into the decision, since your storefront's search depends on both.

</Note>

### Local Development

Medusa Search runs on Cloud only. In local development, Medusa registers the [PostgreSQL Search Module Provider](!resources!/infrastructure-modules/search/providers/postgres) instead, which indexes into your local database. You declare and test an index without running a search engine on your machine.

For MeiliSearch, you run the same engine locally that you run in production, so relevance behaves the same in both, and there's no second provider whose feature set you have to check against.

## Integration with Medusa

### With Medusa Search

The [Search Module](!resources!/infrastructure-modules/search) is part of Medusa, and Medusa Search is one of its providers. You declare an [index definition](!resources!/infrastructure-modules/search/index-definitions) in a file under `src/search`, and the module does the rest. It creates the index, fills it, applies events to it, and compiles a query into what the provider understands.

A definition names the entity, the fields the engine holds, the events that change it, and how to read the documents:

```ts title="src/search/brand.ts"
export const brandIndex = defineSearchIndex({
  name: "brand",
  entity: "brand",
  fields: search.define({
    id: search.keyword().filterable(),
    name: search.text().searchable({ weight: 3 }),
    country: search.keyword().filterable().facetable(),
  }),
  events: ["brand.created", "brand.updated"],
  async consume(event, { container }) {
    // return the documents to upsert or delete
  },
  async *seed({ container }) {
    // yield the documents that fill the index
  },
})
```

Refer to [Searching Custom Data Models](../page.mdx#searching-custom-data-models) for the full example.

Because the definition is declarative, the index schema, the field weights, and the sync logic all live in your repository and travel with a deployment. Switching providers doesn't change the definition either, so the same file runs against the PostgreSQL provider locally and against Medusa Search on Cloud.

### With Meilisearch

Medusa doesn't maintain a Search Module Provider for Meilisearch, so you build one. A [Search Module Provider](!resources!/infrastructure-modules/search/providers) implements the interface the Search Module calls, and it's the same interface the provider behind Medusa Search implements. Once you register yours, the module drives Meilisearch the way it drives any provider, so index definitions, event-driven sync, reindexing, and `query.search` all keep working, and admin dashboard search picks up your indexes.

That keeps search idiomatic in your project, and the provider itself is a project of its own. The interface is wide:

1. Create, migrate, and delete a physical index from an index definition, including translating each field type and modifier into Meilisearch's index settings.
2. Upsert and delete documents in batches, and delete by a filter.
3. Compile the Search Module's filter tree, including `$or`, `$not`, and several operators on one field, into a Meilisearch filter expression.
4. Compile facets, sorting, pagination, and search options into Meilisearch queries, and decide what to reject when the engine can't serve a request.
5. Map Meilisearch's response back into the shape the module expects, including the relevance score and the facet results.

Refer to [Search Module Providers](!resources!/infrastructure-modules/search/providers) for how the module loads and calls a provider, and to [Create Search Module Provider](!resources!/references/search/provider) for the interface to implement. [Medusa Search vs PostgreSQL](../postgres/page.mdx) shows how much behavior a provider decides, since the two providers Medusa ships answer the same request differently.

## Querying and Storefront Integration

{/* TODO update with instantsearch once we have the plugin */}

With Medusa Search, you query through [`query.search`](!docs!/learn/fundamentals/query/search) from an API route, which keeps the search credentials on the backend and gives the storefront one endpoint to call:

```ts title="src/api/search-brands/route.ts"
const { data, search_result } = await query.search({
  entity: "brand",
  fields: ["id", "name", "country"],
  filters: { q: req.query.q as string },
  pagination: { take: 20 },
})
```

The storefront then calls your route, so search results pass through the same layer as the rest of your commerce data. You can apply your own authorization, shape the response, and mix in data that isn't in the index.

With a provider in place, `query.search` reaches Meilisearch the same way, so the backend pattern is identical. Meilisearch also supports querying from the browser with a search-only key, which bypasses your provider entirely. Its client works with the InstantSearch component libraries, so a facet-and-pagination interface takes less code than building the same thing against your own API route.

The tradeoff is exposure and control:

- A browser-side key makes the index publicly readable, so anything you index becomes public. Tenant tokens can scope what a key returns, but that scoping lives in the token instead of your backend.
- A self-hosted instance queried from the browser has to accept public traffic, which is a network and rate-limiting decision you own.

Medusa Search has no browser-side mode, so it always runs behind your API routes. That costs you the direct browser queries and gives you one place to enforce authorization and shape results.

## Admin Dashboard Search

The Medusa admin dashboard's global search calls the `/admin/search` API route, which uses the Search Module for every entity that has an index and falls back to database queries for the rest. Declaring an index for an entity therefore improves admin search with no extra work.

Because a Meilisearch [Search Module Provider](!resources!/references/search/provider) sits inside the module, admin search uses it for every entity you index, the same way it uses Medusa Search. The difference is that the provider is yours, so an entity's admin search is only as good as the query compilation you wrote for it.

## Environments and Previews

Cloud gives each environment its own set of Medusa Search indexes, scoped by the environment's handle, so a preview environment never writes to production indexes. When you configure a base environment in the [shared previews settings](../../environments/preview/page.mdx#manage-shared-previews-settings), Cloud copies the base environment's indexes into the new preview environment along with its database.

With Meilisearch, index isolation is your responsibility, and you choose between two approaches:

- **One instance, an index prefix per environment.** Cheaper, but every environment shares the instance's resources, and a bad write in a preview can reach a production index if the prefix is wrong.
- **An instance per environment.** Fully isolated, and each instance costs infrastructure or a Meilisearch Cloud project.

Either way, a preview environment starts with an empty index and needs a full sync before search works.

Two things are worth checking before you commit:

- **The real cost of MeiliSearch self-hosting.** The engine is free, and the on-call rotation, the upgrade work, and the disk you size for the index are not. Compare against Meilisearch Cloud honestly, not against zero.

### Other Cloud Usage This Affects

Moving search to Meilisearch doesn't move it off your Cloud bill, it moves it to different metrics. Only Medusa Search counts toward the [Search](../../usage/page.mdx#usage-metrics-definitions) metric, so Meilisearch requests never appear there. They land here instead:

- **Data Transfer** covers external service communications, so every index write and every search your backend sends to Meilisearch counts toward it, along with the responses. This applies to a self-hosted instance and to Meilisearch Cloud alike, since both sit outside your Medusa server.
- **Compute** covers the indexing work, since the seed and the event handlers that write to Meilisearch run in your Medusa application.

Querying Meilisearch from the browser keeps those searches off your Data Transfer, since they never reach your Medusa server. Refer to [Usage](../../usage/page.mdx) to monitor both metrics.

## Which One to Choose

**Choose Medusa Search if:**

- Your project runs on Cloud and you want search without a service to provision, key, and operate.
- You want the index schema and the sync logic in your repository, reviewed and deployed with the rest of your code.
- Filters, facets, sorting, and weighted full-text search cover your requirements.
- You want admin dashboard search to improve as you index more entities.

**Choose Meilisearch if:**

- You want the same engine locally and in production, with identical relevance in both.
- You have a reason to keep search inside your own infrastructure, such as data residency.
- You have the capacity to operate the engine, or you're ready to pay for Meilisearch Cloud instead.

You can also use both. The Search Module accepts more than one provider, so you can keep admin search and most indexes on Medusa Search while a storefront index runs on Meilisearch through your own integration. Refer to [Configure the Search Module](!resources!/infrastructure-modules/search#configure-the-search-module) for how to register providers and set a default.
