# {metadata.title}

In this guide, you'll compare [Medusa Search](../page.mdx) to Algolia so you can decide which one to use for your Medusa project.

<Note title="Not a Cloud user yet?">

[Sign up for Cloud](../../sign-up/page.mdx) to use Medusa Search and other Cloud features.

## What is Medusa Search?

Medusa Search is a managed search service for Cloud projects. It stores your search indexes outside of your database and serves search queries for them, from full-text queries with relevance ranking to vector search over embeddings.

The [Search Module](!resources!/infrastructure-modules/search) drives it through a provider that ships with Medusa. Cloud registers and configures that provider for every environment, so Medusa Search needs no setup. You declare an index definition in your codebase, and query it with [`query.search`](!docs!/learn/fundamentals/query/search).

## Setup and Infrastructure

Medusa Search is part of Cloud, so there's nothing to provision. Cloud creates the search resources for every environment and passes the credentials to your Medusa application, which registers the provider for you.

Algolia takes considerably more work before you can run a single search. Algolia has no self-hosted option, so it operates the servers, but you configure and maintain everything around them:

1. Create an Algolia account and application.
2. Provision an index for every environment, and pick a naming scheme that keeps them apart.
3. Generate an admin key for writes and a search-only key for reads, then store both as environment variables in every Cloud environment.
4. Configure the index settings, including searchable attributes, faceting, ranking rules, and typo tolerance.
5. Repeat steps 2 to 4 for every environment you add, and keep the settings identical across all of them.

Step 4 is the one that keeps costing you. Index settings are dashboard configuration in Algolia by default, so they live outside your codebase and drift out of version control unless you push them through the API as part of a deployment.

Only after all of that do you connect Algolia to Medusa, which requires creating a Search Module Provider as explained in the [Integration with Medusa](#integration-with-medusa) section.

### Local Development

Medusa Search runs on Cloud only. In local development, Medusa registers the [PostgreSQL Search Module Provider](!resources!/infrastructure-modules/search/providers/postgres) instead, which indexes into your local database. You declare and test an index without running a search engine on your machine.

Algolia has no local engine, so local development points at a real Algolia index, usually a separate development one. Every developer either shares that index or gets their own, and both choices cost you records.

## Integration with Medusa

This is the largest difference between the two, since it decides how much search code you own.

### With Medusa Search

The [Search Module](!resources!/infrastructure-modules/search) is part of Medusa, and Medusa Search is one of its providers. By default, Medusa only declares an index for the `product` data model. You can also declare an [index](!resources!/infrastructure-modules/search/index-definitions) for other core or custom data models. Medusa creates the index, fills it, applies events to it, and compiles a query into what the provider understands.

A definition names the entity, the fields the engine holds, the events that change it, and how to read the documents:

```ts title="src/search/brand.ts"
export const brandIndex = defineSearchIndex({
  name: "brand",
  entity: "brand",
  fields: search.define({
    id: search.keyword().filterable(),
    name: search.text().searchable({ weight: 3 }),
    country: search.keyword().filterable().facetable(),
  }),
  events: ["brand.created", "brand.updated"],
  async consume(event, { container }) {
    // return the documents to upsert or delete
  },
  async *seed({ container }) {
    // yield the writes that fill the index
  },
})
```

Because the definition is declarative, the index schema, the field weights, and the sync logic all live in your repository and travel with a deployment. Switching providers doesn't change the definition either, so the same file runs against the PostgreSQL provider locally and against Medusa Search on Cloud.

<Note>

Refer to [Searching Custom Data Models](../page.mdx#searching-custom-data-models) for the full example.

</Note>

### With Algolia

Medusa doesn't maintain a Search Module Provider for Algolia, so you have to build a custom one. A [Search Module Provider](!resources!/infrastructure-modules/search/providers) implements the interface the Search Module calls. Once you register yours, the module drives Algolia the way it drives any provider, so index definitions, event-driven sync, reindexing, and `query.search` all keep working, and admin dashboard search picks up your indexes.

That keeps search idiomatic in your project, and the provider itself is a project of its own. The interface is wide:

1. Create, migrate, and delete a physical index from an index definition, including translating each field type and modifier into Algolia's index settings.
2. Upsert and delete documents in batches, and delete by a filter.
3. Compile the Search Module's filter tree, including `$or`, `$not`, and several operators on one field, into Algolia's filter syntax.
4. Compile facets, sorting, pagination, and search options into Algolia queries, and decide what to reject when Algolia can't serve a request.
5. Map Algolia's response back into the shape the module expects, including the relevance score and the facet results.

Refer to [Search Module Providers](!resources!/infrastructure-modules/search/providers) for how the module loads and calls a provider, and to [Create Search Module Provider](!resources!/references/search/provider) for the interface to implement.

## Querying and Storefront Integration

{/* TODO change information once we have the instantsearch plugin */}

With Medusa Search, you query through [`query.search`](!docs!/learn/fundamentals/query/search) from an API route, which keeps the search credentials on the backend and gives the storefront one endpoint to call:

```ts title="src/api/search-brands/route.ts"
const { data, search_result } = await query.search({
  entity: "brand",
  fields: ["id", "name", "country"],
  filters: { q: req.query.q as string },
  pagination: { take: 20 },
})
```

The storefront then calls your route, so search results pass through the same layer as the rest of your commerce data. You can apply your own authorization, shape the response, and mix in data that isn't in the index.

With a provider in place, `query.search` reaches Algolia the same way, so the backend pattern is identical. Algolia also supports querying from the browser with a search-only key, which bypasses your provider entirely. That's where its front-end libraries come in. InstantSearch gives you a search box, facet widgets, pagination, and highlighted results as components, so a rich instant-search interface takes far less code than building the same thing against your own API route.

The tradeoff is exposure and control:

- A browser-side key makes the index publicly readable, so anything you index becomes public. Secured API keys can scope what a key returns, but that scoping lives in Algolia's key configuration instead of your backend.
- Rate limiting moves to the key rather than your API route.
- Every keystroke that fires a query is a billed search request.

Medusa Search has no browser-side mode, so it always runs behind your API routes. That costs you the ready-made widgets and gives you one place to enforce authorization and shape results.

## Admin Dashboard Search

The Medusa admin dashboard's global search calls the `/admin/search` API route, which uses the Search Module for every entity that has an index and falls back to database queries for the rest. Declaring an index for an entity therefore improves admin search with no extra work.

Because an Algolia [Search Module Provider](!resources!/references/search/provider) sits inside the module, admin search uses it for every entity you index, the same way it uses Medusa Search. The difference is that the provider is yours, so an entity's admin search is only as good as the query compilation you wrote for it.

## Environments and Previews

Cloud gives each environment its own set of Medusa Search indexes, scoped by the environment's handle, so a preview environment never writes to production indexes. When you configure a base environment in the [shared previews settings](../../environments/preview/page.mdx#manage-shared-previews-settings), Cloud copies the base environment's indexes into the new preview environment along with its database.

With Algolia, index isolation is your responsibility. The usual approach is an index name prefix per environment, set through an environment variable, plus a decision about what a preview environment searches. A preview that points at the production index is a write risk, and a preview with an empty index needs a full sync before search works. Each environment's records also count toward your record allowance, so preview environments have a price.

Three things are worth checking before you commit:

- **Sorting.** Each sort order needs its own replica index in Algolia, and a standard replica holds its own copy of the records. Several sort orders on a large catalog multiply the records that Algolia bills you for.
- **Record count, not product count.** If you flatten variants or localized fields into separate records in Algolia, your record count grows much faster than your catalog does.
- **Search requests on either option.** A storefront that searches on every keystroke makes many more requests than one that searches on submit. Refer to [Usage](../../usage/page.mdx) to monitor your search requests on Medusa Search before you tune the storefront's behavior.

### Other Cloud Usage This Affects

Moving search to Algolia doesn't move it off your Cloud bill, it moves it to different metrics. Only Medusa Search counts toward the [Search](../../usage/page.mdx#usage-metrics-definitions) metric, so Algolia requests never appear there. They land here instead:

- **Data Transfer** covers external service communications, so every index write and every search your backend sends to Algolia counts toward it, along with the responses. A storefront that searches through your API routes puts every query on this metric.
- **Compute** covers the indexing work, since the seed and the event handlers that write to Algolia run in your Medusa application.

Querying Algolia from the browser keeps those searches off your Data Transfer, since they never reach your Medusa server. Refer to [Usage](../../usage/page.mdx) to monitor both metrics.

## Which One to Choose

**Choose Medusa Search if:**

- Your project runs on Cloud and you want search without a second vendor to provision, key, and bill.
- You want the index schema and the sync logic in your repository, reviewed and deployed with the rest of your code.
- Filters, facets, sorting, and weighted full-text search cover your requirements.
- You want admin dashboard search to improve as you index more entities.

**Choose Algolia if:**

- Relevance tuning is a core part of your product, and you want ranking rules, synonyms, and merchandising controls.
- You want built-in search analytics and A/B testing.
- You accept a second vendor, a second set of credentials, and the integration code that connects them.

Already using Algolia and moving to Medusa Search? Refer to [Migrate from Algolia to Medusa Search](../migrate-from-algolia/page.mdx) for the end-to-end steps.

You can also use both. The Search Module accepts more than one provider, so you can keep admin search and most indexes on Medusa Search while a storefront index runs on Algolia through your own integration. Refer to [Configure the Search Module](!resources!/infrastructure-modules/search#configure-the-search-module) for how to register providers and set a default.
