## Migrate with an AI Agent

If you use an AI agent, such as Claude Code or Codex, copy the following prompt into it to perform the migration in your project. Review the changes it makes, then follow the rest of this guide to validate and deploy them.

```md title="Migration Prompt" collapsed noLineNumbers
<role>
You are a senior Medusa developer migrating an existing
Medusa project from a custom Meilisearch integration to
Medusa Search, the managed search service of Cloud.
</role>

<task>
Replace this project's custom Meilisearch integration with
the Search Module and Medusa Search, keeping the storefront's
search behavior intact.
</task>

<context>
- Medusa Search is a provider of the Search Module, which
  ships with Medusa v2.20.0 and later. Cloud registers and
  configures it for every environment, so it needs no
  credentials or configuration in the project.
- Medusa creates a product index by default. A project only
  declares its own index definition for custom fields,
  custom index settings, or data models other than products.
- An index definition lives in a file under `src/search`,
  declares the fields the engine holds, fills the index with
  a `seed` async generator, and keeps it current with its
  `events` and `consume` properties.
- Queries run through `query.search` in an API route. Medusa
  Search has no browser-side querying and no search-only
  key, so a storefront that queries Meilisearch directly
  needs a new API route on the Medusa backend.
- Medusa Search does not support synonyms, custom stop-word
  lists, geo search, configurable ranking rules, engine-side
  embedders, or sorting alongside a text query. An index or a
  query that relies on them fails.
- Medusa Search supports typo tolerance and highlighting, but
  unlike Meilisearch both are opt-in per query through
  `search_options`. Pass them in the search route to keep the
  storefront's current behavior.
</context>

<steps>
1. Inspect the project and report what it has before you
   change anything: the Meilisearch module, the sync
   workflows and their steps, the subscribers, the admin sync
   route and UI route, the storefront's search client and
   search modal, and the Medusa version in `package.json`.
2. If the Medusa version is below v2.20.0, stop and tell the
   user to upgrade first.
3. List the fields the project indexes in Meilisearch, taken
   from the `fields` array of `syncProductsWorkflow`, and ask
   the user for the index settings of their Meilisearch
   instance. They can read them from
   `GET /indexes/{index}/settings`.
4. Decide whether the project needs its own index
   definition. If every indexed field and setting is covered
   by the default product index, skip to step 6 and say why.
5. Create the index definition under `src/search`. Map
   Meilisearch's `searchableAttributes` to `searchable()`
   fields with a weight, `filterableAttributes` to
   `facetable()` or `filterable()`, `sortableAttributes` to
   `sortable()`, and the attributes missing from
   `displayedAttributes` to `retrievable(false)`. Reproduce
   the project's indexing rules in `seed`, such as indexing
   published products only, and handle create, update, and
   delete events in `consume`.
6. Create a `POST /store/products/search` API route that
   calls `query.search`, with a Zod validation middleware for
   its body. The storefront queried Meilisearch from the
   browser, so this route is new rather than a rewrite.
7. Replace any manual sync trigger with a workflow step that
   calls the Search Module's `reindex` method.
8. Delete the Meilisearch module, the sync workflows and
   steps, the product subscribers, the module's entry in
   `medusa-config.ts`, and the `meilisearch` dependency.
   Leave the Meilisearch environment variables in place and
   tell the user to remove them after the cutover.
9. Update the storefront to call the new search route through
   the JS SDK instead of the Meilisearch client, debouncing
   the input, and read the route's response shape. Remove the
   `@meilisearch/instant-meilisearch` and `react-instantsearch`
   packages, the `searchClient` export, and the
   `NEXT_PUBLIC_MEILISEARCH_*` variables.
10. Run the project's type check and tests, and report the
    result.
</steps>

<constraints>
- Do not add a feature that Medusa Search does not support.
  When the project relies on one, report it and propose the
  closest alternative instead of implementing it silently.
- Do not delete the user's Meilisearch instance, indexes, or
  keys, and do not call the Meilisearch API.
- Do not expose the search index to the browser. Every query
  goes through an API route on the Medusa backend.
- Do not run a deployment or push to any branch.
- Consult the Medusa documentation at
  https://docs.medusajs.com or the Medusa MCP server for any
  API details you need, including the index definition
  properties, field types and modifiers, and the options of
  `query.search`.
</constraints>

<error_handling>
- If the project has no Meilisearch integration, report that
  and stop.
- If the integration differs from the files listed in step
  1, map each responsibility you find to its Search Module
  equivalent and report the mapping before you change code.
- If you cannot tell whether a field is searched, filtered,
  faceted, or only displayed, ask the user rather than
  guessing its modifiers.
- If a storefront feature has no Medusa Search equivalent,
  list it under manual follow-ups instead of removing the
  feature.
</error_handling>

<output_format>
Respond with the following markdown sections:

## Changes
A table of every file you created, modified, or deleted,
with one sentence on what changed in it.

## Behavior differences
Each Meilisearch behavior the project relied on that Medusa
Search does not support, and what you did about it.

## Manual follow-ups
The steps the user has to take themselves, such as removing
environment variables, validating relevance, and deploying.
</output_format>

<success_criteria>
- The project builds and type checks with no reference to
  `meilisearch`, `@meilisearch/instant-meilisearch`, or
  `react-instantsearch` left in the backend or the
  storefront.
- Every field the project indexed in Meilisearch is either
  held by the new index definition, covered by the default
  product index, or listed as an intentional removal.
- The storefront searches through the new API route, and no
  Meilisearch key reaches the browser.
- Every unsupported Meilisearch behavior appears under

</success_criteria>
```

## Who This Guide Is For

This guide assumes your project follows the [Integrate Meilisearch with Medusa](!resources!/integrations/guides/meilisearch) guide, which is the most common Meilisearch setup in Medusa projects. That setup has the following pieces:

- A Meilisearch Module in `src/modules/meilisearch` that wraps Meilisearch's client.
- A `syncProductsWorkflow` and its steps that index and delete products in Meilisearch.
- Subscribers on product events and a custom `meilisearch.sync` event.
- An admin UI route and API route that trigger a full sync.
- A storefront that queries Meilisearch directly from the browser with `@meilisearch/instant-meilisearch` and a search key.

If your integration differs, the mapping in the [Map Your Integration to Medusa Search](#map-your-integration-to-medusa-search) section still applies, since every Meilisearch integration owns the same responsibilities.

<Note title="Not sure whether to migrate?">

Refer to [Medusa Search vs Meilisearch](../meilisearch/page.mdx) for a feature-by-feature comparison, including the Meilisearch features that Medusa Search doesn't offer.

</Note>

## Map Your Integration to Medusa Search

Medusa creates the product index by default, so you don't have to declare one to search products.  You only need your own definition for custom fields or index configurations that the default index doesn't cover, or for data models other than products that you indexed in Meilisearch.

So, start by writing down what your Meilisearch index holds and how it's configured, since that's what your index definition has to reproduce. Take the record shape from the `fields` array of your `syncProductsWorkflow`, and the settings from your instance:

```bash
curl "$MEILISEARCH_HOST/indexes/$INDEX/settings" \
  -H "Authorization: Bearer $MEILISEARCH_API_KEY"
```

<Note title="Tip">

Save that response before you start. Meilisearch stores the settings on the instance rather than in your repository, so it's the only record of the relevance your customers search with today. You'll compare against it in [Step 8](#step-8-validate-before-the-cutover).

</Note>

## Step 1: Upgrade Your Medusa Application

Medusa Search requires [Medusa v2.20.0 or later](https://github.com/medusajs/medusa/releases/tag/v2.20.0). Upgrade your application, then confirm it starts locally before you change any search code.

## Step 2: Declare Your Index

Medusa creates the product index by default, so products are searchable on Medusa Search without any index definition. You only declare one in the following cases:

- Your Meilisearch documents hold custom fields that the default product index doesn't.
- You need index settings or field options that the default index doesn't apply, such as a different weight, a facetable field, or a [Medusa Search setting](../page.mdx#medusa-search-settings).
- You indexed data models other than products in Meilisearch, such as product categories.

Otherwise, skip to [Step 3](#step-3-add-the-search-api-route) and query the default index.

An [index definition](!resources!/infrastructure-modules/search/index-definitions) replaces your Meilisearch index's settings, holding the schema, the initial fill, and the event handling in one file that deploys with your code.

For example, the integration guide indexes each product's `id`, `title`, `description`, `handle`, `thumbnail`, `categories`, and `tags`, and it indexes published products only. To reproduce that, create the file `src/search/product.ts` with the following content:

export const definitionHighlights = [
  ["24", "title", "Outweighs the description in relevance."],
  ["27", "thumbnail", "Held by the index, but never searched or filtered."],
  ["28", "categories", "An array of objects, so a filter matches any category."],
  ["34", "facetable", "Powers the storefront's category filter counts."],
]

```ts title="src/search/product.ts" highlights={definitionHighlights}
import {
  defineSearchIndex,
  search,
} from "@medusajs/framework/utils"

const fields = [
  "id",
  "title",
  "description",
  "handle",
  "thumbnail",
  "categories.id",
  "categories.name",
  "categories.handle",
  "tags.id",
  "tags.value",
]

export const productIndex = defineSearchIndex({
  name: "product",
  entity: "product",
  fields: search.define({
    id: search.keyword().filterable(),
    title: search.text().searchable({ weight: 3 }),
    description: search.text().searchable(),
    handle: search.keyword().filterable(),
    thumbnail: search.keyword(),
    categories: search
      .object({
        id: search.keyword().filterable(),
        name: search
          .keyword()
          .searchable()
          .facetable(),
        handle: search.keyword().filterable(),
      })
      .array(),
    tags: search
      .object({
        id: search.keyword().filterable(),
        value: search
          .keyword()
          .searchable()
          .facetable(),
      })
      .array(),
  }),
  async *seed({ container, filters }) {
    const limit = 200
    let offset = 0

    while (true) {
      const { data } = await container.query.graph({
        entity: "product",
        fields,
        filters: {
          status: "published",
          ...filters,
        },
        pagination: { skip: offset, take: limit },
      })

      if (!data.length) {
        break
      }

      yield data

      offset += limit
    }
  },
})
```

The definition declares the fields the engine holds, then fills the index with the `seed` generator. Note the following about it:

- `title` carries a higher weight than `description`, so a product matching a query in its title outranks one matching only in its description. This replaces the ordered `searchableAttributes` list in Meilisearch, along with the `attribute` ranking rule that reads it.
- `thumbnail` is neither searchable nor filterable, since the storefront only displays it. Use the [`retrievable()`](!resources!/infrastructure-modules/search/index-definitions/modifiers#retrievable) modifier if you want the opposite, a field the engine matches on but never returns.
- `seed` yields products in batches of `200` instead of loading the whole catalog into memory, and it merges the `filters` it receives so a [partial reindex](!resources!/infrastructure-modules/search/reindexing#seeding-on-demand) works.
- `seed` filters on `status: "published"`, which is the check the `syncProductsWorkflow` performs in its `transform` function.

<Note>

Only add `facetable()` to a field whose counts your storefront shows. Meilisearch computes a facet distribution from `filterableAttributes` without a separate query, whereas every facet on Medusa Search shares a budget of 16 queries per search with the hits and the count.

</Note>

### Keep the Index Current

Your integration replaces two subscribers, `product-sync` and `product-delete`, with the `events` and `consume` properties of the definition. Medusa subscribes to the events you list and routes each one to `consume`.

Add the following properties to the `defineSearchIndex` call:

```ts title="src/search/product.ts"
export const productIndex = defineSearchIndex({
  // ...
  events: [
    "product.created",
    "product.updated",
    "product.deleted",
  ],
  async consume(event, { container }) {
    if (event.name === "product.deleted") {
      return [{
        action: "delete",
        filters: { id: [event.data.id] },
      }]
    }

    const { data } = await container.query.graph({
      entity: "product",
      fields: [...fields, "status"],
      filters: { id: event.data.id },
    })

    const [product] = data

    if (product?.status !== "published") {
      return [{
        action: "delete",
        filters: { id: [event.data.id] },
      }]
    }

    const { status, ...document } = product

    return [{ action: "upsert", documents: [document] }]
  },
})
```

`consume` returns the writes to apply for an event. It handles the three cases your subscribers handled:

1. A deleted product leaves the index.
2. A created or updated published product enters the index.
3. A product that's no longer published leaves the index, which is what the `deleteProductsFromMeilisearchStep` did for unpublished products.

Unlike the Meilisearch client, the Search Module doesn't hand you a task to wait on. A write that `consume` returns is applied before the query that follows it sees the index, so you no longer poll for a task's status after a product change.

```bash npm2yarn
npx medusa db:migrate
```

Then start your application. The Search Module fills the index when the application starts in worker or shared mode. You no longer need a Meilisearch instance running on your machine to develop against search.

## Step 3: Add the Search API Route

{/* TODO if we ship search api route by default, mention here */}

Your storefront queries Meilisearch straight from the browser, so there's no search route on your backend to rewrite. For Medusa Search, create a search route on your backend.

Create the file `src/api/store/products/search/route.ts` with the following content:

```ts title="src/api/store/products/search/route.ts"
import {
  MedusaRequest,
  MedusaResponse,
} from "@medusajs/framework/http"
import {
  ContainerRegistrationKeys,
} from "@medusajs/framework/utils"
import { z } from "@medusajs/framework/zod"

export const SearchSchema = z.object({
  query: z.string(),
  limit: z.number().optional().default(20),
  offset: z.number().optional().default(0),
})

type SearchRequest = z.infer<typeof SearchSchema>

export async function POST(
  req: MedusaRequest<SearchRequest>,
  res: MedusaResponse
) {
  const query = req.scope.resolve(
    ContainerRegistrationKeys.QUERY
  )

  const { query: q, limit, offset } = req.validatedBody

  const { data, search_result } = await query.search({
    entity: "product",
    fields: [
      "id",
      "title",
      "description",
      "handle",
      "thumbnail",
    ],
    filters: { q },
    pagination: { skip: offset, take: limit },
  })

  res.json({
    products: data,
    metadata: search_result.metadata,
  })
}
```

The route resolves [Query](!docs!/learn/fundamentals/query) from the Medusa container and searches the `product` index, which is the `name` of the definition you declared. Note the following about it:

- `fields` can include fields the index doesn't hold, such as `variants.*`. Query hydrates them from the database with the `entity` you declared in the definition, which is something a browser-side Meilisearch query couldn't do.
- The route returns the hydrated entities in `products` and the engine's own result in `metadata`, rather than Meilisearch's `hits` and `estimatedTotalHits`. Your storefront reads the new shape in [Step 7](#step-7-update-the-storefront).
- The route accepts pagination, since Medusa Search caps results at the 10,000th one and the storefront needs to page through matches.

Then, validate the request body with a [middleware](!docs!/learn/fundamentals/api-routes/middlewares). Add the following to `src/api/middlewares.ts`:

```ts title="src/api/middlewares.ts"
import {
  defineMiddlewares,
  validateAndTransformBody,
} from "@medusajs/framework/http"
import { SearchSchema } from "./store/products/search/route"

export default defineMiddlewares({
  routes: [
    {
      matcher: "/store/products/search",
      method: "POST",
      middlewares: [
        validateAndTransformBody(SearchSchema),
      ],
    },
  ],
})
```

### Add Filters, Facets, and Sorting

Your Meilisearch storefront builds a filter expression in the browser and reads the facet distribution from the engine's response. With Medusa Search, the API route builds both instead.

For example, to filter by category and return the category counts:

```ts title="src/api/store/products/search/route.ts"
const { data, search_result } = await query.search({
  entity: "product",
  fields: ["id", "title", "handle", "thumbnail"],
  filters: {
    q,
    "categories.handle": req.validatedBody.category,
  },
  search_options: {
    facets: ["categories.name"],
    disjunctive_facets: true,
  },
  pagination: { skip: offset, take: limit },
})
```

`disjunctive_facets` keeps the sibling category counts visible while a category filter is active, which is what a filter sidebar needs. Refer to [Search Queries](!docs!/learn/fundamentals/query/search) for every filter operator, facet type, and sorting option.

<Note>

Medusa Search can't sort by a field alongside a text query, which Meilisearch's `sort` parameter allows. If your storefront offers "sort by price" on a search results page, run the sorted listing as a separate query without a `q` filter.

</Note>

## Step 4: Replace the Manual Sync

The integration guide's admin page triggers a full sync through the `meilisearch.sync` event. You no longer need that sync for everyday changes:

1. Medusa fills the index on deployment.
2. Medusa keeps the index current from the `events` and `consume` properties of the index definition, applying every product change as it happens. This applies for both the product index Medusa creates by default or the custom definition you wrote in [Step 2](#step-2-declare-your-index).

A manual rebuild is only for repairing a diverged index, such as after a `consume` call failed or a change reached the database without emitting an event.

For a manual rebuild, you can drop the custom admin page entirely: admin users can rebuild any index from Settings -> Search in the Medusa Admin dashboard. Refer to the [Manage Search Indexes](!user-guide!/settings/search) user guide.

If you'd rather trigger the rebuild from your own code, replace the `syncProductsWorkflow` with a step that calls the Search Module's [`reindex`](!resources!/infrastructure-modules/search/reindexing#seeding-on-demand) method.

Create the file `src/workflows/steps/reindex-products.ts` with the following content:

```ts title="src/workflows/steps/reindex-products.ts"
import { Modules } from "@medusajs/framework/utils"
import {
  createStep,
  StepResponse,
} from "@medusajs/framework/workflows-sdk"

export const reindexProductsStep = createStep(
  "reindex-products",
  async (_, { container }) => {
    const searchModuleService = container.resolve(
      Modules.SEARCH
    )

    const result = await searchModuleService.reindex({
      index: "product",
    })

    return new StepResponse(result)
  }
)
```

Then, keep your admin UI route and its API route, and call a workflow that runs this step instead of emitting the `meilisearch.sync` event.

<Note>

`reindex` waits for the rebuild to finish before it resolves, so run it in a workflow rather than in the request handler of your admin API route. Refer to [Long-Running Workflows](!docs!/learn/fundamentals/workflows/long-running-workflow) if the rebuild outlasts your request timeout.

</Note>

## Step 7: Update the Storefront

{/* TODO update this section once the InstantSearch integration for Medusa Search ships */}

This is the largest change in the migration, since your storefront talks to the search engine itself today. Its `SearchModal` component renders `react-instantsearch` widgets against a `searchClient` from `@meilisearch/instant-meilisearch`, which sends every keystroke to your Meilisearch host with a search key. Three things change:

1. **Where the query goes.** The storefront calls your `/store/products/search` route instead of the engine, so the Meilisearch host and key leave the browser entirely.
2. **The response shape.** The route returns `products` and `metadata` instead of Meilisearch's `hits` and `estimatedTotalHits`. Each result is a hydrated product rather than an index document, so it can hold fields the index doesn't.
3. **The features behind the widgets.** Filters, facets, sorting, highlighting, and typo tolerance come from the query your API route builds rather than from a widget's parameters. Meilisearch applied typo tolerance and returned `_formatted` fields without being asked, so your route passes `typo_tolerance` and `highlight` to keep that behavior, and the storefront reads each hit's `highlights` instead of `_formatted`.

So update the storefront as follows:

1. Remove the `searchClient` export from `src/lib/config.ts`, along with the `@meilisearch/instant-meilisearch` and `react-instantsearch` dependencies and the `NEXT_PUBLIC_MEILISEARCH_*` variables.
2. Rewrite `src/modules/search/components/modal/index.tsx` to call your `/store/products/search` route with the [JS SDK](!resources!/js-sdk), debouncing the input so a query doesn't fire on every keystroke. Keep the modal, the button, and the `Hit` component's markup, since only the data source changes.
3. Render the results from the route's `products` array, and page through them with the `metadata` it returns.
4. Move each filter and facet the widgets provided into the request body, and read the counts from the facets your route returns.

<Note title="Tip">

Debouncing matters more than it did before. Every search now counts toward your Cloud [search request allowance](../page.mdx#medusa-search-usage), whereas browser-side Meilisearch queries never reached your Medusa backend. A modal that searched on every keystroke makes several times the requests of one that searches on a pause or on submit.

</Note>

<Note>

An InstantSearch integration for Medusa Search is in progress, which will let you keep the widget-based search UI in your storefront. This section will cover it once it ships.

</Note>

## Step 8: Validate Before the Cutover

Compare the two engines on the same environment before you point production at Medusa Search. Check the following:

- **Top queries.** Run the queries your customers search most through both engines and compare the top results. Weights are the only relevance control you have, so tune the `weight` values in the definition until the ordering holds up against the `searchableAttributes` order and `rankingRules` you saved earlier.
- **Misspelled queries.** Run the same queries with a typo and confirm your search route passes `typo_tolerance`, since Meilisearch applied it without being asked. Medusa Search ranks a fuzzy match below every exact match, so check that a correctly spelled query still returns the same top results.
- **Filters and facets.** Confirm every filter your storefront offers works, and that facet counts match the facet distribution Meilisearch reported for the same query.
- **Document count.** Compare the index's document count against the number of published products in your database. A mismatch means the `seed` filters differ from what you indexed in Meilisearch.
- **Event sync.** Create, update, unpublish, and delete a product, then search for it. Each change should reach the index within seconds, and without the task polling Meilisearch needed.
- **Admin search.** The admin dashboard's global search uses your indexes automatically, so check that searching products in the dashboard returns the results you expect.
