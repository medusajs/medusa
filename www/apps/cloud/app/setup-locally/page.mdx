## How Local Development Works with Cloud

A Cloud project is connected to a GitHub repository that holds your Medusa application's code. When you create a project from a [starter](../projects/page.mdx#1-create-project-from-a-starter), Cloud clones the starter's code into a GitHub repository in the account or organization you chose.

To customize your store, add features, or debug issues, you:

1. Clone the project's repository to your machine.
2. Run the Medusa application locally against resources on your machine, such as a local PostgreSQL database.
3. Push your changes to the repository. Cloud then deploys them.

<Note title="Tip">

If you'd rather not install PostgreSQL on your machine, refer to the [Set Up with Docker](./docker/page.mdx) guide instead.

</Note>

## 1. Clone the Repository

If you imported your own GitHub repository when you created the project and you already have its code on your machine, skip to the [next step](#2-install-dependencies).

To clone the repository linked to your project:

1. If you're in a different organization, [switch to the organization](../organizations/page.mdx#switch-organization) that the project belongs to.
2. Click **Projects** in the sidebar, then select your project. This opens the project's dashboard, with the project's name shown at the top left.
3. Click the **Repository** button at the top right to open the GitHub repository in a new tab.
4. On GitHub, click the **Code** button and copy the repository's URL.
5. In your terminal, clone the repository and change into its directory:

```bash
git clone <repository-url>
cd <repository-name>
```

Replace `<repository-url>` with the URL you copied, and `<repository-name>` with the name of the created directory.

## 2. Install Dependencies

Starters are monorepos that hold the Medusa application and the storefront as separate packages, under `apps/backend` and `apps/storefront`. Install the dependencies of all packages from the repository's root directory:

```bash npm2yarn
npm install
```

Starters use [pnpm](https://pnpm.io/installation) as their package manager by default. If you imported your own repository, use its package manager instead.

<Details summaryContent="Use Yarn or npm instead of pnpm">

To use Yarn or npm in a project created from a starter, make the following changes in the repository's root directory before you install the dependencies:

1. In both `package.json` and `apps/backend/package.json`, change the `packageManager` field to your package manager and its installed version, such as `yarn@4.9.1` or `npm@10.9.2`.
2. In `package.json`, add a `workspaces` field with the packages listed in `pnpm-workspace.yaml`:

```json title="package.json"
{
  "workspaces": [
    "apps/**",
    "!apps/backend/.medusa/**"
  ]
}
```

3. In the `scripts` of `package.json`, replace `pnpm -r <script>` with `turbo <script>`, and any other use of `pnpm` with your package manager. For example:

```json title="package.json"
{
  "scripts": {
    "dev": "turbo dev",
    "build": "turbo build"
  }
}
```

4. Delete the `pnpm-workspace.yaml` and `pnpm-lock.yaml` files.
5. Apply the changes specific to your package manager:
    - **Yarn v2+**: Create an empty `yarn.lock` file, and a `.yarnrc.yml` file with the following content:

    ```yaml title=".yarnrc.yml"
    nodeLinker: node-modules
    ```

    - **Yarn v1**: In `package.json`, add a `resolutions` field that sets `@types/node` to the version in `apps/backend/package.json`:

    ```json title="package.json"
    {
      "resolutions": {
        "@types/node": "^20.12.11"
      }
    }
    ```

    - **npm**: In `package.json`, add `ajv` as a dev dependency and override its version for ESLint:

    ```json title="package.json"
    {
      "devDependencies": {
        "ajv": "^8.13.0"
      },
      "overrides": {
        "eslint": {
          "ajv": "^6.12.4"
        },
        "@eslint/eslintrc": {
          "ajv": "^6.12.4"
        }
      }
    }
    ```

6. Install the dependencies with your package manager:

```bash
# Yarn
yarn

# npm
npm install --legacy-peer-deps
```

Then, commit the changes with the new lock file, so that Cloud uses the same package manager when it builds your project. Cloud supports the package managers listed in the [project prerequisites](../projects/prerequisites/page.mdx).

</Details>

## 3. Set Up Medusa Application's Environment Variables

On Cloud, you manage an environment's variables from its dashboard, and Medusa sets the variables of its resources, such as the database, for you. Learn more in the [Environment Variables](../environments/environment-variables/page.mdx) guide.

Those variables aren't in your repository, since they hold secrets that you can't commit to Git. So, for local development, either copy the `.env.template` file or create a `.env` file in the Medusa application's directory (`apps/backend`) that points to resources running on your machine:

```bash title="apps/backend/.env"
DATABASE_URL=postgres://localhost/medusa-local
REDIS_URL=redis://localhost:6379
JWT_SECRET=supersecret
COOKIE_SECRET=supersecret
STORE_CORS=http://localhost:8000
ADMIN_CORS=http://localhost:9000
AUTH_CORS=http://localhost:9000,http://localhost:8000
```

Replace the values with the ones matching your setup:

- `DATABASE_URL`: The connection string of a local PostgreSQL database. Create the database first if it doesn't exist.
- `REDIS_URL`: The connection string of a local Redis instance. Remove this variable if you don't run Redis locally, and Medusa falls back to in-memory modules.
- `JWT_SECRET` and `COOKIE_SECRET`: Any random strings. Use different values than the ones in your Cloud environments.
- `STORE_CORS`, `ADMIN_CORS`, and `AUTH_CORS`: The local URLs that can send requests to the Medusa application. Change `http://localhost:8000` if your storefront runs on another port.

Local resources keep your development work isolated, so you can seed and change data without affecting a deployed store.

<Note title="Tip" forceMultiline>

If you need your local setup to mirror a deployed environment, you can reuse that environment's variables instead. Either [export the variables](../environments/environment-variables/page.mdx#export-environment-variables-on-cloud) from the environment's dashboard and rename the downloaded `env.txt` file to `.env`, or run the following command with the [Cloud CLI](../cli/page.mdx):

```bash
mcloud variables list --reveal --dotenv > .env
```

Learn more in the [variables command reference](../cli/commands/variables/page.mdx#export-variables-to-a-env-file).

Since these variables point to the environment's database, Redis instance, and other resources, any change you make locally affects the deployed environment. Only reuse them for debugging, and prefer local resources for development.

</Note>

## 4. Run the Medusa Application

Change to the Medusa application's directory (`apps/backend`), then run the migrations to prepare your local database. In starters, the migrations also seed initial store data, such as regions:

```bash npx2yarn
npx medusa db:migrate
```

Then, start the Medusa application:

```bash npm2yarn
npm run dev
```

This runs your Medusa server at `http://localhost:9000`, and the Medusa Admin dashboard at `http://localhost:9000/app`.

![Diagram showcasing the server and application running when you start the Medusa application](https://res.cloudinary.com/dza7lstvk/image/upload/v1776755500/Medusa%20Book/start-overview_hqjexd.jpg)

The application restarts when you change code under the `src` directory. Admin customizations are hot-reloaded instead, so you see your changes without refreshing the browser.

## 5. Create Medusa Admin User

Your local database doesn't have the users of your Cloud environments. To log in to the Medusa Admin locally, create an admin user with Medusa's CLI tool.

Run the following command in your Medusa application's directory (`apps/backend`):

```bash npx2yarn
npx medusa user -e admin@medusajs.com -p supersecret
```

Replace `admin@medusajs.com` and `supersecret` with the user's email and password respectively.

You can then use the user's credentials to log in to the Medusa Admin dashboard at `http://localhost:9000/app`.

## 6. Set Up Storefront's Environment Variables

If your project doesn't have a storefront, skip to [Publish Local Changes to Cloud](#publish-local-changes-to-cloud).

The storefront needs a publishable API key to send requests to the Medusa application. You retrieve the key from the Medusa Admin, which is why you set up the storefront after running the Medusa application and creating an admin user.

To set up the storefront's environment variables:

1. In the repository's root directory, copy the storefront's `.env.template` file to a `.env` file.
2. Open the Medusa Admin at `http://localhost:9000/app` and log in with the admin user you created.
3. Go to Settings -> Publishable API Keys, then copy the key of a publishable API key. Learn more in the [Publishable API Keys](!user-guide!/settings/developer/publishable-api-keys) merchant guide.
4. Set the key and the Medusa application's URL in `apps/storefront/.env`:

```bash title="apps/storefront/.env"
NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY=pk_123...
NEXT_PUBLIC_MEDUSA_BACKEND_URL=http://localhost:9000
```

Make sure to use the correct variable names as specified in the `.env.template` file. The above are just examples.

Set the other variables in the file based on your setup. For example, set the keys of the payment provider you use.

<Note title="Tip">

To reuse the storefront variables of a deployed environment instead, run `mcloud variables list --reveal --dotenv --type storefront > .env` in the storefront's directory. Then, change the Medusa application's URL and the publishable API key to your local ones.

</Note>

---

## 7. Run the Storefront

While the Medusa application is running, open a new terminal. Then, change to the storefront's directory (`apps/storefront`) and start the storefront:

```bash npm2yarn
npm run dev
```

This runs the storefront at `http://localhost:8000`. Open it in your browser to browse the store's products and place orders.

## Publish Local Changes to Cloud

Cloud deploys your changes when you push them to the GitHub repository linked to your project:

- Push to the branch of a [long-lived environment](../environments/long-lived/page.mdx), such as the production environment, to deploy to that environment.
- Open a pull request to create a [preview environment](../environments/preview/page.mdx), where you can test your changes before merging them.

If your changes use new environment variables, [add them to the Cloud environment](../environments/environment-variables/page.mdx#add-environment-variables-on-cloud) before you push. Otherwise, the deployment runs without them.

Learn more about how Cloud builds and deploys your changes in the [Deployments](../deployments/page.mdx) guide.

## Project Files

Your Medusa application's project (`apps/backend`) has the following files and directories:

![Diagram of the files and directories in a Medusa application project](https://res.cloudinary.com/dza7lstvk/image/upload/v1732803813/Medusa%20Book/medusa-dir-overview_v7ks0j.jpg)

### src

This directory is the central place for your custom development. It includes the following subdirectories:

- `admin`: Holds your admin dashboard's custom [widgets](!docs!/learn/fundamentals/admin/widgets) and [UI routes](!docs!/learn/fundamentals/admin/ui-routes).
- `api`: Holds your custom [API routes](!docs!/learn/fundamentals/api-routes) that are added as endpoints in your Medusa application.
- `jobs`: Holds your [scheduled jobs](!docs!/learn/fundamentals/scheduled-jobs) that run at a specified interval during your Medusa application's runtime.
- `links`: Holds your [module links](!docs!/learn/fundamentals/module-links) that build associations between data models of different modules.
- `modules`: Holds your custom [modules](!docs!/learn/fundamentals/modules) that implement custom business logic.
- `scripts`: Holds your custom [scripts](!docs!/learn/fundamentals/custom-cli-scripts) to be executed using Medusa's CLI tool.
- `subscribers`: Holds your [event listeners](!docs!/learn/fundamentals/events-and-subscribers) that are executed asynchronously whenever an event is emitted.
- `workflows`: Holds your custom [workflows](!docs!/learn/fundamentals/workflows) that can be executed from anywhere in your application.

### medusa-config.ts

This file holds your [Medusa configurations](!docs!/learn/configurations/medusa-config), such as your PostgreSQL database configurations.

### .medusa

The `.medusa` directory holds types and other files that Medusa generates when you run the `build` command. Don't modify any files or commit them to your repository.

Refer to the [Automatically Generated Types](!docs!/learn/fundamentals/generated-types) guide for more information on generated types.
