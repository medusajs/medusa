# {metadata.title}

In this guide, you'll learn how to set up and run your Cloud project on your machine using Docker.

The [Set Up Medusa Locally](../page.mdx) guide requires you to install prerequisites like PostgreSQL on your machine. If you'd rather not install them, use this guide to run your project's Medusa application and storefront with Docker instead.

You can follow this guide on any operating system that supports Docker, including Windows, macOS, and Linux.

This guide assumes you created your project from a [starter](../../projects/page.mdx#1-create-project-from-a-starter), which is a monorepo with the Medusa application in `apps/backend` and the storefront in `apps/storefront`. If your repository has a different structure, change the paths in this guide to match it.

## 1. Clone the Project's Repository

To get started, clone the GitHub repository linked to your Cloud project:

1. If you're in a different organization, [switch to the organization](../../organizations/page.mdx#switch-organization) that the project belongs to.
2. Click **Projects** in the sidebar, then select your project. This opens the project's dashboard, with the project's name shown at the top left.
3. Click the **Repository** button at the top right to open the GitHub repository in a new tab.
4. On GitHub, click the **Code** button and copy the repository's URL.
5. In your terminal, clone the repository and change into its directory:

```bash
git clone <repository-url>
cd <repository-name>
```

Replace `<repository-url>` with the URL you copied, and `<repository-name>` with the name of the created directory.

You perform the rest of the steps inside this directory.

<Note>

Don't have a Cloud project? Clone the [DTC Starter](https://github.com/medusajs/dtc-starter) repository instead, then follow the rest of this guide.

</Note>

### Change Package Manager

Starters use [pnpm](https://pnpm.io/installation) as their package manager by default. If you imported your own repository, use its package manager instead.

To use Yarn or npm in a project created from a starter, follow the steps in the "Use Yarn or npm instead of pnpm" section of the [Set Up Medusa Locally](../page.mdx#2-install-dependencies) guide. Make sure to install the dependencies as its last step, since that generates the lock file that the `Dockerfile` copies in a later step.

Then, in the rest of this guide, choose your package manager's tab in the code snippets.

## 2. Create `docker-compose.yml`

In the cloned repository, create a file named `docker-compose.yml` with the following content:

```yaml title="docker-compose.yml"
services:
  # PostgreSQL Database
  postgres:
    image: postgres:15-alpine
    container_name: medusa_postgres
    restart: unless-stopped
    environment:
      POSTGRES_DB: medusa-store
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - medusa_network

  # Redis
  redis:
    image: redis:7-alpine
    container_name: medusa_redis
    restart: unless-stopped
    ports:
      - "6379:6379"
    networks:
      - medusa_network

  # Medusa Server
  # This service runs the Medusa backend application
  # and the admin dashboard.
  medusa:
    build: .
    container_name: medusa_backend
    restart: unless-stopped
    depends_on:
      - postgres
      - redis
    ports:
      - "9000:9000"
      - "5173:5173"
    environment:
      - NODE_ENV=development
      - DATABASE_URL=postgres://postgres:postgres@postgres:5432/medusa-store
      - REDIS_URL=redis://redis:6379
    env_file:
      - apps/backend/.env
    volumes:
      - .:/server
      - /server/node_modules
      - /server/apps/backend/node_modules
    networks:
      - medusa_network

  # Storefront
  # This service runs the Next.js Starter Storefront
  storefront:
    build: .
    container_name: medusa_storefront
    restart: unless-stopped
    depends_on:
      - medusa
    ports:
      - "8000:8000"
    environment:
      - NEXT_PUBLIC_MEDUSA_BACKEND_URL=http://medusa:9000
    env_file:
      - apps/storefront/.env
    volumes:
      - .:/server
      - /server/node_modules
      - /server/apps/backend/node_modules
      - /server/apps/storefront/node_modules
      - /server/apps/storefront/.next
    entrypoint: ["./start-storefront.sh"]
    networks:
      - medusa_network

volumes:
  postgres_data:

networks:
  medusa_network:
    driver: bridge
```

You define four services in this file:

- `postgres`: The PostgreSQL database service that stores your Medusa application's data.
- `redis`: The Redis service that stores session data.
- `medusa`: The Medusa service that runs the server and the admin dashboard. It connects to the PostgreSQL and Redis services.
- `storefront`: The Next.js Starter Storefront service. It connects to the Medusa service.
    - If you don't want to use the storefront, you can remove the `apps/storefront` directory and the `storefront` service from the `docker-compose.yml` file.

The `env_file` paths are relative to the project root: `apps/backend/.env` for the backend and `apps/storefront/.env` for the storefront.

The anonymous volumes for `node_modules` directories are required because pnpm workspaces create per-package `node_modules` directories with symlinks. Without these volumes, the Docker bind mount overwrites the installed dependencies. This configuration is essential for pnpm to work correctly in a monorepo Docker setup.

### Port Configuration Explained

The ports configuration maps container ports to host ports using the format `"host_port:container_port"`:

- `"5432:5432"`: PostgreSQL database accessible at `localhost:5432`
- `"6379:6379"`: Redis accessible at `localhost:6379`
- `"9000:9000"`: Medusa backend server accessible at `localhost:9000`
- `"5173:5173"`: Medusa Admin development server with Hot Module Replacement (HMR)
- `"8000:8000"`: Storefront accessible at `localhost:8000`

<Note>

If these ports conflict with other services on your host machine, change the host port (left side). For example, use `"9001:9000"` to access the Medusa backend at `localhost:9001` instead.

</Note>

### Recommendations for Multiple Local Projects

If this isn't the first Medusa project you're setting up with Docker on your machine, make sure to:

- Change the `container_name` for each service to avoid conflicts.
    - For example, use `medusa_postgres_myproject`, `medusa_redis_myproject`, `medusa_backend_myproject`, and `medusa_storefront_myproject` instead of the current names.
- Change the volume names to avoid conflicts.
    - For example, use `postgres_data_myproject` instead of `postgres_data`.
- Change the network name to avoid conflicts.
    - For example, use `medusa_network_myproject` instead of `medusa_network`.
- Change the ports to avoid conflicts with other projects. For example:
    - Use `"5433:5432"` for PostgreSQL.
    - Use `"6380:6379"` for Redis.
    - Use `"9001:9000"` for the Medusa server.
    - Use `"5174:5173"` for the Medusa Admin dashboard.
    - Use `"8001:8000"` for the storefront.
- Update the `DATABASE_URL` and `REDIS_URL` environment variables accordingly.

## 3. Create `start.sh`

Create a script file that [runs database migrations](!docs!/learn/fundamentals/data-models/write-migration) and starts the Medusa development server.

Create the file `start.sh` with the following content:

<CodeTabs group="npm2yarn" defaultValue="pnpm">
  <CodeTab value="pnpm" label="pnpm">
```shell title="start.sh"
#!/bin/sh
cd /server/apps/backend

echo "Running database migrations..."
pnpm medusa db:migrate

echo "Seeding database..."
pnpm seed || echo "Seeding failed, continuing..."

echo "Starting Medusa development server..."
pnpm dev
```
  </CodeTab>
  <CodeTab value="yarn" label="yarn">
```shell title="start.sh"
#!/bin/sh
cd /server/apps/backend

echo "Running database migrations..."
yarn medusa db:migrate

echo "Seeding database..."
yarn seed || echo "Seeding failed, continuing..."

echo "Starting Medusa development server..."
yarn dev
```
  </CodeTab>
  <CodeTab value="npm" label="npm">
```shell title="start.sh"
#!/bin/sh
cd /server/apps/backend

echo "Running database migrations..."
npx medusa db:migrate

echo "Seeding database..."
npm run seed || echo "Seeding failed, continuing..."

echo "Starting Medusa development server..."
npm run dev
```
  </CodeTab>
</CodeTabs>

<Note title="Windows Users">

Ensure that the `start.sh` file uses LF line endings instead of CRLF. Git on Windows can sometimes automatically convert line endings, which causes errors when running the script inside the Linux-based Docker container. Learn how to configure your environment to maintain LF line endings in [this guide from GitHub](https://docs.github.com/en/get-started/git-basics/configuring-git-to-handle-line-endings).

</Note>

## 5. Create `Dockerfile`

The `Dockerfile` defines how the Docker image is built. Both the `medusa` and `storefront` services reuse the same image, and the storefront overrides the entrypoint in `docker-compose.yml`.

Create a file named `Dockerfile` with the following content:

<CodeTabs group="npm2yarn" defaultValue="pnpm">
  <CodeTab value="pnpm" label="pnpm">
```dockerfile title="Dockerfile"
FROM node:22-alpine

WORKDIR /server

RUN npm install pnpm@10.11.1 -g

COPY package.json pnpm-lock.yaml pnpm-workspace.yaml turbo.json .npmrc ./
COPY apps/backend/package.json ./apps/backend/
COPY apps/storefront/package.json ./apps/storefront/

RUN pnpm install --frozen-lockfile

COPY . .

EXPOSE 9000 5173 8000

ENTRYPOINT ["./start.sh"]
```
  </CodeTab>
  <CodeTab value="yarn" label="yarn">
```dockerfile title="Dockerfile"
FROM node:22-alpine

WORKDIR /server

COPY package.json yarn.lock .yarnrc.yml turbo.json ./
COPY .yarn/releases .yarn/releases
COPY apps/backend/package.json ./apps/backend/
COPY apps/storefront/package.json ./apps/storefront/

RUN yarn install

COPY . .

EXPOSE 9000 5173 8000

ENTRYPOINT ["./start.sh"]
```
  </CodeTab>
  <CodeTab value="npm" label="npm">
```dockerfile title="Dockerfile"
FROM node:22-alpine

WORKDIR /server

COPY package.json package-lock.json turbo.json ./
COPY apps/backend/package.json ./apps/backend/
COPY apps/storefront/package.json ./apps/storefront/

RUN npm install --legacy-peer-deps

COPY . .

EXPOSE 9000 5173 8000

ENTRYPOINT ["./start.sh"]
```
  </CodeTab>
</CodeTabs>

In the `Dockerfile`, you use the `node:22-alpine` image as the base since Medusa requires Node.js v22.22.0 or later.

The workspace configuration files and all apps' `package.json` files are copied before installing dependencies so that the workspace dependency graph is resolved correctly. After installing dependencies, the rest of the source code is copied.

<Note>

While `/app` is a more common working directory, use `/server` for the Medusa service to avoid conflicts with Medusa Admin customizations. Learn more in [this troubleshooting guide](!resources!/troubleshooting/medusa-admin/no-widget-route#errors-in-docker).

</Note>

## 6. Update Scripts in `package.json`

Update the `scripts` section in the root `package.json` file to start and stop the Docker services.

Add the following scripts:

```json title="package.json"
{
  "scripts": {
    // Other scripts...
    "docker:up": "docker compose up --build -d",
    "docker:down": "docker compose down"
  }
}
```

Where:

- `docker:up` starts the development server in a Docker container as a background process.
- `docker:down` stops and removes the Docker containers.

## 7. Update Medusa Configuration

<Note type="warning">

Cloud deploys the `medusa-config.ts` file in your repository. So, only apply the configurations in this step in development, as shown in the snippets, to avoid changing how your application runs on Cloud.

</Note>

### Disable SSL for PostgreSQL Connection

If you try to run the Medusa application now with Docker, you'll encounter an SSL error as the server tries to connect to the PostgreSQL database.

To resolve the error, add the following configurations in `apps/backend/medusa-config.ts`:

```ts title="apps/backend/medusa-config.ts"
import { loadEnv, defineConfig } from "@medusajs/framework/utils"

loadEnv(process.env.NODE_ENV || "development", process.cwd())

const isDev = process.env.NODE_ENV === "development"

module.exports = defineConfig({
  projectConfig: {
    // ...
    databaseDriverOptions: isDev ? {
      ssl: false,
      sslmode: "disable",
    } : undefined,
  },
})
```

You add the [projectConfig.databaseDriverOptions](!docs!/learn/configurations/medusa-config#databasedriveroptions) to disable SSL for the PostgreSQL database connection. Since the `medusa` service in `docker-compose.yml` sets `NODE_ENV` to `development`, the configuration only applies when you run the application locally.

### Add Vite Configuration for Medusa Admin

To ensure that the Medusa Admin dashboard works correctly when running inside Docker, connects to the Medusa server, and reloads properly with Hot Module Replacement (HMR), add the following Vite configuration in `apps/backend/medusa-config.ts`:

```ts title="apps/backend/medusa-config.ts"
module.exports = defineConfig({
  // ...
  admin: {
    vite: (config) => {
      return {
        server: {
          host: "0.0.0.0",
          // Allow all hosts when running in Docker (development mode)
          // In production, this should be more restrictive
          allowedHosts: [
            "localhost",
            ".localhost",
            "127.0.0.1",
          ],
          hmr: {
            // HMR websocket port inside container
            port: 5173,
            // Port browser connects to (exposed in docker-compose.yml)
            clientPort: 5173,
          },
        },
      }
    },
  },
})
```

You configure the Vite development server to listen on all network interfaces (`0.0.0.0`) and set up HMR to work correctly within the Docker environment. These options only affect the admin's development server, so they don't change the admin that Cloud builds and deploys.

### Redis Configuration

If you encounter Redis connection issues, you may need to explicitly configure the Redis URL in your `medusa-config.ts` file:

```ts title="apps/backend/medusa-config.ts"
module.exports = defineConfig({
  projectConfig: {
    // ...
    redisUrl: process.env.REDIS_URL,
  },
})
```

This ensures the Redis URL from the environment variable is properly used by Medusa.

## 9. Set Up Environment Variables

On Cloud, you manage an environment's variables from its dashboard, and they aren't in your repository. Learn more in the [Environment Variables](../../environments/environment-variables/page.mdx) guide.

For local development, create environment files for the Medusa application and the storefront by copying from their templates.

### Medusa Application's Environment Variables

Copy the Medusa application's template:

```bash
cp apps/backend/.env.template apps/backend/.env
```

Update the values in the file as needed. The `medusa` service in `docker-compose.yml` already sets `DATABASE_URL` and `REDIS_URL` to the PostgreSQL and Redis services, so you don't need to set them in `apps/backend/.env`.

If you later add an environment variable that your customizations need, [add it to your Cloud environment](../../environments/environment-variables/page.mdx#add-environment-variables-on-cloud) first, then to the `.env` file.

### Storefront's Environment Variables

Copy the storefront's template:

```bash
cp apps/storefront/.env.template apps/storefront/.env
```

The `storefront` service in `docker-compose.yml` requires this file to exist. You set the publishable API key in it [in a later step](#12-set-up-storefronts-environment-variables), since you retrieve the key from the Medusa Admin.

## 10. Start the Medusa Application with Docker

All configurations are now ready. Start the Medusa application using Docker by running the following command:

```bash npm2yarn
npm run docker:up
```

Docker pulls the necessary images, starts the PostgreSQL and Redis services, builds the Medusa and storefront services, and runs them in Docker containers.

The `storefront` service exits with an error until you set its publishable API key in a later step. So, you can ignore its errors for now.

Check the logs to ensure everything is running smoothly:

```bash
docker compose logs -f
```

Once you see the following message, the Medusa server and admin are ready:

```shell
✔ Server is ready on port: 9000 - 3ms
info:    Admin URL → http://localhost:9000/app
```

You can now access the Medusa server at `http://localhost:9000` and the Medusa Admin dashboard at `http://localhost:9000/app`.

## 11. Create Medusa Admin User

Your local database doesn't have the users of your Cloud environments. To log in to the Medusa Admin locally, create an admin user by running the following command:

<CodeTabs group="npm2yarn" defaultValue="pnpm">

  </CodeTab>
  <CodeTab value="yarn" label="yarn">
```bash
docker compose exec medusa sh -c "cd /server/apps/backend && yarn medusa user -e admin@example.com -p supersecret"
```
  </CodeTab>
  <CodeTab value="npm" label="npm">

  </CodeTab>

Replace `admin@example.com` and `supersecret` with the user's email and password respectively.

You can then use the user's credentials to log in to the Medusa Admin dashboard at `http://localhost:9000/app`.

## 12. Set Up Storefront's Environment Variables

If your project doesn't have a storefront, skip to [Stop the Medusa Application Running in Docker](#stop-the-medusa-application-running-in-docker).

The storefront needs a publishable API key to send requests to the Medusa application. You retrieve the key from the Medusa Admin, which is why you set it after running the Medusa application and creating an admin user.

To set the publishable API key:

1. Open the Medusa Admin at `http://localhost:9000/app` and log in with the admin user you created.
2. Go to Settings -> Publishable API Keys, then copy the key of a publishable API key. Learn more in the [Publishable API Keys](!user-guide!/settings/developer/publishable-api-keys) guide.
3. Set the key in `apps/storefront/.env`:

```bash title="apps/storefront/.env"
NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY=pk_123...
```

The `storefront` service in `docker-compose.yml` already sets `NEXT_PUBLIC_MEDUSA_BACKEND_URL` to the `medusa` service's URL, so you don't need to set it. Set the other variables in the file based on your setup. For example, set the keys of the payment provider you use.

## 13. Run the Storefront

The storefront requires the publishable API key at startup. So, after you set the key, start the `storefront` service again:

```bash
docker compose up storefront -d
```

This runs the storefront at `http://localhost:8000`. Open it in your browser to browse the store's products and place orders.

## Stop the Medusa Application Running in Docker

To stop the Medusa application running in Docker, run the following command:

```bash npm2yarn
npm run docker:down
```

This command stops and removes the Docker containers created by the `docker-compose.yml` file.

This doesn't delete any data in your application or its database. Start the server again using the `docker:up` command.

## Troubleshooting

### start.sh Not Found Error

If you get the following error when starting the Medusa application with Docker:

```bash
medusa_backend exited with code 127 (restarting)
medusa_backend   | /usr/local/bin/docker-entrypoint.sh: exec: line 11: ./start.sh: not found
```

This is a common error for Windows users. It usually occurs when the `start.sh` file uses CRLF line endings instead of LF.

To fix this, ensure that the `start.sh` file uses LF line endings. You can configure Git to maintain LF line endings by following [this guide from GitHub](https://docs.github.com/en/get-started/git-basics/configuring-git-to-handle-line-endings).

### Couldn't Find X File or Directory Errors

If you encounter errors indicating that certain files or directories couldn't be found, make sure you're running the commands from the root directory of your Medusa application (the same directory where the `docker-compose.yml` file is located).

For example, if you run the `docker:up` command and see an error like this:

```bash
error Couldn't find a package.json file in "/"
```

Ensure that your terminal's current working directory is the root of your Medusa application, then try running the command again.

### Container Name Conflicts

If you're running multiple Medusa projects with Docker or have previously run this guide, you may encounter container name conflicts.

To resolve this, ensure that the `container_name` values in your `docker-compose.yml` file are unique for each project. You can modify them by appending a unique identifier to each name.

For example, change:

```yaml title="docker-compose.yml"
container_name: medusa_postgres
```

to

```yaml title="docker-compose.yml"
container_name: medusa_postgres_myproject
```

### Medusa Backend Returns "Cannot GET /" Error

If you access `http://localhost:9000` and see a "Cannot GET /" error, this usually means the Medusa backend started successfully but there's no route handler for the root path.

This is expected behavior. The Medusa backend API endpoints are available at paths like `/admin` and `/store`. To verify your installation:

1. Access the Medusa Admin dashboard at `http://localhost:9000/app`
2. Check the backend health at `http://localhost:9000/health`
3. Access the storefront at `http://localhost:8000` (if you kept the storefront service)

The "Cannot GET /" message doesn't indicate a problem. It means there's no content at the root URL.
