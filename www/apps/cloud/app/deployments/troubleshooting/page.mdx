In this guide, you'll find solutions to common issues that may arise when deploying your Medusa applications on Cloud.

## Troubleshooting Build and Deployment Issues with AI

When your build or deployment fails on Cloud, you can use the "Fix with AI" feature to troubleshoot and resolve the issue with the help of Cloud's support agent. The AI agent will analyze the deployment and build logs, identify the root cause of the issue, and provide you with actionable steps to resolve it.

Learn more in the [Fix Deployment and Build Issues with AI](../fix-with-ai/page.mdx) guide.

## Access Logs

When a deployment fails, you can see the [build](../../logs/page.mdx#view-build-logs-on-cloud) and [runtime logs](../../logs/page.mdx#view-runtime-logs-on-cloud) of your deployment to understand the cause of the failure.

Alternatively, you can install the [Cloud CLI](../../cli/page.mdx) and use it to check logs from your terminal or with the help of AI agents like Claude Code.

For example:

```bash
# Install the CLI
npm install @medusajs/mcloud -g

# Login
mcloud login

# Check logs of the latest deployment in the environment
mcloud logs --organization org_123 --project proj_123 --environment env_123

# Check logs of a specific deployment
mcloud logs --organization org_123 --project proj_123 --environment env_123 --deployment-id deploy_123
```

See the [Cloud CLI](../../cli/page.mdx) guide for more details on how to use the CLI to manage your Cloud resources and deployments.

## Files Not Found After Deployment

Before deploying your Medusa application on Cloud, Medusa runs the `build` script defined in your `package.json` file, then copies only the output of the [build process](!docs!/learn/build), which is the `.medusa/server` directory.

The `.medusa/server` directory holds the compiled JavaScript files of your project, the production build of the admin dashboard, and other necessary files to run your Medusa application in production.

If you have custom files needed at runtime, such as a `src/data` directory that holds JSON files, modify the `build` script in your `package.json` file to copy these files to the `.medusa/server` directory after the build process.

For example:

```json title="package.json"
{
  "scripts": {
    "postbuild": "cp -r src/data .medusa/server/src/data",
    "build": "medusa build && npm run postbuild"
  }
}
```

This script copies the `src/data` directory to the `.medusa/server` directory following the build process.

Learn more in the [Deployments Guide](../page.mdx#build-process-for-deployments).

<Note>

You can replace `npm run postbuild` with the appropriate command for your package manager, such as `yarn postbuild`.

</Note>

## Out of Memory (OOM) Build Failures

Exit code 137 indicates that your build process was killed by the system due to memory exhaustion. This commonly occurs with TypeScript-heavy monorepos during compilation.

### Diagnosing Exit Code 137

Check your build logs for these indicators:

- **Exit code 137** at the end of the build process
- **"Killed"** message during TypeScript compilation
- Build terminating unexpectedly without clear error messages
- Memory usage spikes in monitoring (if available)

### Why Medusa Builds Are Memory-Intensive

Medusa builds consume significant memory because:

- **Large TypeScript codebase**: Type checking requires keeping the entire project in memory
- **Multiple modules**: Each commerce module needs compilation and type checking
- **Complex dependency graph**: Medusa's interconnected modules increase memory overhead
- **Concurrent processes**: Build tooling may run multiple compilation tasks simultaneously

### Remediation Strategies

1. **Increase build memory allocation** (see [Node.js Heap Tuning](#nodejs-heap-tuning-for-large-builds) section)

2. **Optimize build configuration**:
   ```json title="tsconfig.json"
   {
     "compilerOptions": {
       "incremental": true,
       "tsBuildInfoFile": ".tsbuildinfo"
     }
   }
   ```

3. **Check for memory-intensive dependencies**:
   - Review your `package.json` for large or duplicate packages
   - Run `npm ls` to identify circular dependencies
   - Consider using `npm-check-duplicates` to find redundant packages

4. **Adjust monorepo structure**:
   - Split large modules into smaller ones
   - Use `tsconfig.json` `references` for better compilation isolation
   - Implement lazy loading where possible

## Node.js Heap Tuning for Large Builds

Large monorepos (especially TypeScript-heavy backends like Medusa) can run out of memory during builds, resulting in exit code 134 or "Reached heap limit" errors.

### Identifying Heap Issues

Look for these signs in your build logs:

- Exit code 134
- Messages like "Reached heap limit Allocation failed - JavaScript heap out of memory"
- Build process terminates unexpectedly during TypeScript compilation

### Increasing Node.js Heap Size

Add the `NODE_OPTIONS` environment variable to increase the heap size:

```bash
NODE_OPTIONS=--max-old-space-size=4096
```

Or modify your `package.json` build script:

```json title="package.json"
{
  "scripts": {
    "build": "NODE_OPTIONS=--max-old-space-size=4096 medusa build"
  }
}
```

### Recommended Heap Sizes

- **Small projects** (under 20 modules): 2048MB (`--max-old-space-size=2048`)
- **Medium projects** (20-50 modules): 4096MB (`--max-old-space-size=4096`)
- **Large projects** (50+ modules): 6144MB or 8192MB

### Alternative Optimization Strategies

- **Enable Turbo caching**: Add `turbo.json` to cache build outputs across deployments
- **Split builds**: Use incremental builds where possible
- **Remove unused dependencies**: Audit your `package.json` for packages you no longer need
- **Optimize TypeScript configuration**: Use stricter `include`/`exclude` patterns in `tsconfig.json`
