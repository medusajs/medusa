# {metadata.title}

In this guide, you'll learn how to move a self-hosted Medusa application to Cloud, including its code, database, files, and domains. The steps apply to any hosting setup, such as a virtual machine, a container platform, or a platform-as-a-service provider.

## Migration Overview

When you self-host, you manage the server, database, Redis, file storage, and deployment pipeline. On Cloud, Medusa provisions and manages all of them per environment, so a migration comes down to moving your code, data, and traffic:

Your Cloud project isn't live until you point your domain to it, so you can prepare and test everything on Cloud while your self-hosted application keeps serving traffic.

## Step 1: Create a Cloud Organization

An organization holds your Cloud projects, team members, and billing details. If you don't have one, [sign up for Cloud](../first-project/page.mdx) to create it.

## Step 2: Prepare Your Medusa Application

Cloud deploys from a GitHub repository. If your code is in another Git provider or only on your server, push it to a GitHub repository first.

To deploy your storefront with your Medusa application, both must be in the same repository as a monorepo. If they're in separate repositories, the [Prerequisites](../projects/prerequisites/page.mdx#prerequisites-for-medusa-application-with-storefront) guide explains how to set up the monorepo.

<Note>

Cloud requires Medusa v2.7.0 or later to configure the managed Redis and S3 resources. If your application uses an earlier version, update it first or contact support.

</Note>

Cloud also configures production infrastructure automatically, which can conflict with your self-hosted infrastructure configurations. Remove the following before you deploy.

### Remove Infrastructure Modules

Cloud registers the Redis and S3 modules for you. Remove any of the following from the `modules` array in `medusa-config.ts`:

- [Redis Event Module](!resources!/infrastructure-modules/event/redis)
- [Redis Caching Module Provider](!resources!/infrastructure-modules/caching/providers/redis), or the deprecated Redis Cache Module
- [Redis Locking Module Provider](!resources!/infrastructure-modules/locking/redis)
- [Redis Workflow Engine Module](!resources!/infrastructure-modules/workflow-engine/redis)
- [S3 File Module Provider](!resources!/infrastructure-modules/file/s3), or any other File Module Provider, unless you plan to [keep your own bucket](#step-6-migrate-files)

Remove these modules entirely instead of registering them conditionally, such as only when `REDIS_URL` is set. A conditional registration can still conflict with Cloud's modules and fail the deployment.

### Remove Database and Redis Connection Options

Cloud manages the database connection, SSL configuration, connection pooling, and Redis. Remove the `databaseUrl`, `databaseDriverOptions`, and `redisUrl` options from `projectConfig` in `medusa-config.ts`, since keeping them may cause deployment or migration failures. For example:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  projectConfig: {
    // remove databaseUrl, databaseDriverOptions,
    // and redisUrl
    http: {
      storeCors: process.env.STORE_CORS!,
      adminCors: process.env.ADMIN_CORS!,
      authCors: process.env.AUTH_CORS!,
      jwtSecret: process.env.JWT_SECRET,
      cookieSecret: process.env.COOKIE_SECRET,
    },
  },
  // remove the Redis and S3 modules from `modules`
})
```

### Remove Migrations from Your Scripts

Cloud [runs database migrations](../database/page.mdx#running-migrations-on-cloud) on every deployment. In your `package.json`:

- Remove `medusa db:migrate` from your `start` script.
- Remove the `predeploy` script if it only runs migrations.
- Keep a `build` script that runs `medusa build`, since Cloud uses it to build your application.

Cloud ignores host-specific deployment files, such as a Dockerfile or a process manager configuration, so you can remove them whenever you're ready after the migration.

### Check the Remaining Prerequisites

Refer to the [Prerequisites for New Projects](../projects/prerequisites/page.mdx) guide for the supported Node.js versions, the monorepo setup for deployments with storefronts, and more. Then, commit and push the changes to your GitHub repository.

<Note title="Tip">

After these changes, the branch may no longer run on your self-hosted setup. If your self-hosted pipeline deploys from the same repository, make the changes in a separate branch. You can [choose the branch](../projects/page.mdx#production-environments-branch) the Production environment deploys from when you create the project.

</Note>

## Step 3: Collect Your Environment Variables

Your Cloud project needs most of your self-hosted application's environment variables. Export them into a `.env` file, leaving out the ones Cloud manages or reserves, and add it when you create the project in the next step.

Leave out these variables, which Cloud sets for you:

- `DATABASE_URL` and `REDIS_URL`
- `NODE_ENV`, `PORT`, and `MEDUSA_WORKER_MODE`
- The connection variables of the Redis and S3 modules that you removed, such as `S3_BUCKET` or `CACHE_REDIS_URL`

Find the full list of reserved names in the [Environment Variables](../environments/environment-variables/page.mdx#restricted-environment-variable-names) guide.

Keep these variables:

- `JWT_SECRET` and `COOKIE_SECRET`. If you use the same values as your self-hosted application, existing customer and admin sessions remain valid after the switch.
- The variables of your third-party integrations, such as payment, fulfillment, tax, and ERP credentials.
- Any variables your customizations read.

Cloud configures Cross-Origin Resource Sharing (CORS) between your storefront and Medusa application. You only need `STORE_CORS`, `ADMIN_CORS`, and `AUTH_CORS` if other clients, such as a mobile app, send requests to your Medusa application.

### Storefront Environment Variables

Collect your storefront's environment variables in a separate `.env` file. Cloud [injects the backend URL, publishable API key, and storefront URL](../storefront/page.mdx#injected-environment-variables), so leave those out and keep the rest, such as analytics or payment provider keys.

## Step 4: Create the Cloud Project

<RolesBadge roles={["developer"]} />

Create a Cloud project from your GitHub repository by following the [Create Project from an Existing Application](../projects/page.mdx#2-create-project-from-an-existing-application) guide. Pay extra attention to these settings:

- **Region**: Choose the region closest to your customers. You can't change it later.
- **Project root directory** and **Storefront root directory**: Set these to the paths of your Medusa application and storefront in the monorepo.
- **Environment variables**: Paste or import the backend and storefront `.env` files from the previous step.

Medusa then provisions the project's resources and deploys your Medusa application and storefront to the Production environment, with an empty database that you fill in the next step.

If the deployment fails, refer to the [Troubleshooting](../deployments/troubleshooting/page.mdx) guide. After moving from self-hosting, the cause is often a leftover Redis or database configuration.

## Step 5: Migrate the Database

Your database holds your products, orders, customers, users, API keys, and settings. To move it, create a dump of the self-hosted database and import it into the Cloud environment's database.

<Note>

Cloud uses PostgreSQL v16, so the dump must come from a PostgreSQL v16 database with a matching [pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html) version. If your self-hosted database uses an earlier version, upgrade it first, or restore it into a local PostgreSQL v16 database and create the dump from there.

</Note>

### Create the Dump

Run `pg_dump` with the custom format against your self-hosted database. The machine you run it on must reach the database, so if it only accepts private connections, run the command from your server:

```bash
pg_dump -Fc \
  -d postgres://user:password@host:5432/medusa \
  -f medusa.dump
```

Replace the connection string with your database's connection string.

### Import the Dump

<RolesBadge roles={["developer"]} />

To import the dump into your Cloud environment:

1. Open the Production environment's dashboard, then click **Database** in the sidebar.
2. In the **Database dump** section, upload the dump file to import it.
3. After the import completes, [redeploy the environment's live deployment](../deployments/page.mdx#redeploy-a-deployment).

Learn more in the [Database](../database/page.mdx#importexport-cloud-database-dumps) guide.

<Note type="warning">

The import replaces the environment's database with the dump's data. It also drops and recreates the tables, so requests can fail until you redeploy.

</Note>

The redeployment also runs pending migrations, so if your Cloud deployment uses a newer Medusa version, Medusa updates the imported schema.

### Rehearse, Then Run the Final Import

Your self-hosted application keeps receiving orders after you create a dump, so the first import is outdated by the time you go live. Import the database twice:

1. **Rehearsal**: Import a dump now and [test the deployment](#step-7-test-the-cloud-deployment) to confirm the import works and see how long it takes.
2. **Final import**: During the switch in [Step 9](#step-9-switch-traffic-to-cloud), you stop writes to the self-hosted application, create a new dump, and import it again.

### Move Files with a Migration Script

A [data migration script](../database/page.mdx#run-one-off-data-scripts-on-cloud) lives in your application's `src/migration-scripts` directory. Cloud runs it once per environment during a deployment, which fits a one-time task like moving files.

An AI agent, such as Claude Code or Codex, can write the script for you. Connect it to the [Docs MCP server](../ai-toolkit/docs-mcp/page.mdx) first so the script follows Medusa's conventions, then give it a prompt like the following:

```md title="Example Prompt" noLineNumbers
Write a Medusa data migration script in
src/migration-scripts that moves this project's files to
the configured File Module Provider. The script must:

1. Find the records that store file URLs, such as product
   images and thumbnails, and the custom data models that
   reference files.
2. Skip the URLs that it already moved, so it's safe to
   run again.
3. Download each file from its current URL, and upload it
   with the uploadFilesWorkflow.
4. Update each record with the new file URL.
5. Process the records in batches, and log its progress.
```

When you deploy the commit that adds the script, Cloud runs it and uploads the files to the environment's managed storage. The script reads file URLs from the database, so deploy it after you [import the database](#step-5-migrate-the-database).

The final import replaces the database, including the updated file URLs and the record that the script ran. So, the script runs again in the next deployment and moves any files still at their previous URLs.

<Note title="Tip">

The script downloads the files from their current URLs, so your previous storage must stay reachable until the script finishes.

</Note>

<Note type="warning">

With the Local File Module Provider, your files are on the self-hosted server's disk and their URLs use its address. They become unavailable once you shut the server down, so move them with a migration script before then.

</Note>

If your storefront restricts which hosts it loads images from, such as with `remotePatterns` in Next.js, add the Cloud bucket's host from the [environment's S3 details](../s3/page.mdx#access-s3-configurations-on-cloud).

## Step 7: Test the Cloud Deployment

Before you switch traffic, verify that the Cloud deployment works with your imported data. Use the environment's default URLs, the `medusajs.app` URL for the backend and the `medusajs.site` URL for the storefront, both in the [environment's dashboard](../deployments/access/page.mdx). Check the areas a migration typically affects:

- Log in to the Medusa Admin with an existing admin user, and confirm that products, orders, and customers appear.
- Open the storefront, and confirm that it shows your products and their images.
- Place a test order in the storefront with your payment provider's test mode, if possible.
- Trigger an email, such as a password reset, and confirm you receive it.
- Check the [logs](../logs/page.mdx) for errors from subscribers, scheduled jobs, and third-party integrations.

### Update Third-Party Integrations

Some third-party services depend on your backend's address and may need an update before you go live:

- **Webhooks**: Update webhook URLs, such as a payment provider's, to the Cloud backend's URL. If you keep the same domain with a [backend custom domain](../environments/custom-domains/page.mdx#backend-custom-domains), the URL stays the same.
- **IP allowlists**: If a service or firewall only accepts requests from specific IP addresses, add [Cloud's outgoing IP addresses](../ip-addresses/page.mdx) to its allowlist.
- **Emails**: If you removed your email Notification Module Provider, Cloud sends emails with [Medusa Emails](../emails/page.mdx). To send from your domain, [add a sender domain](../emails/page.mdx#add-email-sender-domain-to-cloud). If you keep your provider, emails continue to go through it.

## Step 8 (Optional): Set Up Custom Domains

<RolesBadge roles={["developer"]} />

By default, Cloud serves your storefront from a `medusajs.site` subdomain and your backend from a `medusajs.app` subdomain. To keep your own domain, such as `shop.acme.com`, add it as a custom domain on Cloud.

<Note>

Storefront custom domains require the Launch plan or higher, and backend custom domains require the Scale plan or higher. Learn how to [change your plan](../billing/plans/page.mdx#change-plan).

</Note>

To add your storefront's domain:

1. In the Production environment's dashboard, click **Domains** in the sidebar.
2. Under the **Custom storefront domains** section, click **Add domain**.
3. Enter your domain name and click **Continue**.

Cloud then shows the DNS records to add at your domain provider. These records send your domain's traffic to Cloud, so if the domain currently serves your self-hosted store, wait to add them until the switch in the next step.

Follow the same steps for your backend's domain under the **Custom backend domains** section. The [Custom Domains](../environments/custom-domains/page.mdx) guide covers both in more detail.

<Note title="Tip">

Lower the TTL of your domain's existing DNS records a day before the switch so DNS changes take effect faster, shortening the maintenance window.

</Note>

If you skip this step, your store stays available at its `medusajs.site` and `medusajs.app` URLs, and you can add a custom domain later.

## Step 9: Switch Traffic to Cloud

Once you're happy with the Cloud deployment, switch your live traffic to it. You pause writes to the self-hosted application while moving the final data, so switch during a low-traffic period:

1. **Stop writes to the self-hosted application.** Put your self-hosted storefront in maintenance mode or stop the self-hosted server, so customers don't place orders that the final dump would miss.
2. **Let background work finish.** Since there's no Redis data to migrate, give in-progress workflows and queued events time to complete before you stop the server.
3. **Run the final import.** [Create a new dump and import it](#step-5-migrate-the-database), then redeploy the environment.
4. **Point your domains to Cloud.** If you [set up custom domains](#step-8-optional-set-up-custom-domains), add their DNS records at your domain provider. Otherwise, redirect your previous domain to the storefront's `medusajs.site` URL.
5. **Verify the live store.** Once the domain shows as verified, place an order in the storefront and confirm it appears in the Medusa Admin on Cloud.

Cloud connects the storefront to your Medusa application, so you don't change the storefront's backend URL. The exception is a backend custom domain: after its DNS changes take effect, [update the backend URL in the storefront's environment variables](../environments/custom-domains/page.mdx#update-backend-domain-in-storefront).

## Step 10: Clean Up After the Migration

Keep your self-hosted setup available, but stopped, for a few days after the switch, so you can point your domains back to it if needed. Orders placed on Cloud in the meantime don't exist in the self-hosted database.

Once you're confident in the Cloud deployment, wrap up the migration:

- Shut down the self-hosted server, worker, and Redis instances, along with the previous storefront hosting.
- Keep a final backup of the self-hosted database, then shut the database down.
- Shut down the previous file storage, as long as no records still reference its URLs.
- Remove the previous host's deployment pipeline, secrets, and configuration files from your repository.
- Rotate any credentials your previous host stored.
