# {metadata.title}

In this guide, you'll learn how to view and manage your Cloud environment's logs.

## Logs Overview

Logs are output messages from your Medusa application's build and runtime processes for a Cloud environment's deployments.

They include messages logged throughout your application's lifecycle, including messages during the build process, application startup, and runtime operations.

Logs are essential for monitoring your application's health and debugging issues that may arise during development, deployment, or when the application is running in production.

### Log Types

There are two types of logs for your environment's deployments:

- **Build logs**: Messages generated during the build process before deploying and starting the application. These logs are useful for debugging when a deployment's build fails.
- **Runtime logs**: Messages logged by the Medusa backend and storefront when they start and while they're running, such as informational startup messages, HTTP requests, errors, and more. These logs are useful for debugging the application's deployment and runtime errors.

---

## View Build Logs on Cloud

Build logs help you identify issues when a deployment fails with the status "Build failed". They can help you debug the build process and understand why the deployment didn't succeed.

You can view the build logs for any deployment in your environment, including older deployments.

To view the build logs for a deployment, go to the [deployment's details page](../deployments/page.mdx#find-deployment-details), where you can see the deployment's activity:

- **Backend build logs**: Logs for building the Medusa backend.
- **Storefront build logs**: If you deployed a storefront alongside the Medusa application, this shows the logs for building the storefront.

The build logs are updated in real time as the build process runs, so you can see the progress and any errors that occur during the build.

### Search Build Logs on Cloud

You can search the build logs (for backend and storefront) using the search bar at the top right of the logs. This is useful for finding specific messages or errors in the logs.

For example, you can search for keywords like "error" or "warning" to quickly locate issues in the build process.

When you enter the search term, you'll see how the results matching your search. You can move between the results using the up and down arrows next to the search bar. The matching text will be highlighted in the logs.

### Expand and Collapse Build Logs on Cloud

Logs for steps in the build process can be expanded or collapsed to improve readability. This is useful when you have many log messages and want to focus on specific parts of the build process.

By default, logs for all steps in the build process are expanded. You can collapse all logs by clicking the "Collapse all" button at the top right of the logs. This will hide all the detailed logs and only show the titles of each step.

You can also expand the logs of all steps in the build process by clicking the "Expand all" button at the top right. This will show all the detailed logs for each step.

In addition, you can expand or collapse individual steps by clicking the arrow next to a step's title. This gives you more control over which parts of the logs you want to see or hide.

### Pause Build Logs on Cloud

When you view the build logs while the build is still in progress, you can pause the logs to stop them from updating in real time. This is useful if you find a log message that you want to read more closely without it being pushed out of view by new log messages.

To pause the build logs, click the "Pause" button at the bottom right of the page. This button is only shown when there are incoming log messages. When you pause the logs, the button will change to "Resume", allowing you to resume the live log updates.

### Download Build Logs on Cloud

You can download the build logs as a `.log` file for offline analysis, sharing with your team, or sharing with Cloud support if you need help debugging a build issue.

To download build logs, click the <InlineIcon Icon={ArrowDownTray} alt="download" /> button at the top right of the logs. This will download the logs in a `.log` file format, which you can open with any text editor.

## View Runtime Logs on Cloud

Runtime logs are useful for debugging the live deployment of an environment's backend and storefront, especially when the deployment's status is "Deploy failed". They include logs for:

- Errors that occur during backend or storefront startup.
- Errors that occur when handling incoming HTTP requests in the backend, such as 404 errors or 500 server errors.
- Scheduled jobs, subscribers, and background workflow executions not working as expected (if they log informational or error messages).
- Other runtime issues that may occur while the backend or storefront are running.

You can only view the runtime logs of an environment's live deployment, as older deployments are no longer running and do not produce runtime logs.

To view the runtime logs for an environment's live deployment:

<Note title="Tip">

You can also navigate to an environment's runtime logs from the [command palette](../command-palette/page.mdx). Press <Kbd>{getOsShortcut()}</Kbd> + <Kbd>K</Kbd>, select **View Logs**, then choose a project.

</Note>

1. If you're in a different organization, [switch to the organization](../organizations/page.mdx#switch-organization).
2. Click **Projects** in the sidebar and select the project that contains the environment.
3. In the project's dashboard, click on the name of the environment. For example, "Production".
4. Click **Logs** in the sidebar.

This will open the runtime logs page, where you can see the logs for the live deployment of the environment.

### Switch Between Backend and Storefront Runtime Logs

The runtime logs page shows logs for both the Medusa backend and, if you deployed a storefront alongside the Medusa application, the storefront. You can switch between the two using the toggle at the top of the logs table:

- **Backend**: Logs from the Medusa backend application, such as HTTP requests, errors, and startup messages.
- **Storefront**: Logs from the storefront application. This option is only available if you deployed a storefront alongside the Medusa application.

### Search Runtime Logs

You can search the runtime logs using the search bar at the top of the Logs page. This is useful for finding specific messages or errors in the logs.

For example, you can search for keywords like "error" or an informational message that you log in your customizations to quickly locate issues in the runtime logs.

When you enter the search term, you'll only see the logs that match your search.

### Filter Runtime Logs

The Filters sidebar of the Logs page allows you to filter the runtime logs based on various criteria.

You can filter the runtime logs by:

- **Timeline**: Select a specific time range to view logs from that period. For example, you can view the logs from the last hour. You can also select a custom time range.
- **Level**: Filter logs by their severity level, such as "Info", "Warning", "Error", "Debug", or "HTTP". This helps you focus on specific types of logs that are relevant to your debugging needs.
- **Status Code**: Filter logs by HTTP status codes, such as "200" or "500". This is useful to find problematic API routes and resolve their errors.
- **Path**: Filter logs by an HTTP request path, such as `/admin/products`. This is useful to find logs related to specific API routes.

Apply filters from the "Filters" sidebar. You can select multiple filters at once to narrow down the logs further.

#### Time-Range Limits

When selecting a custom date range for the **Timeline** filter, the date picker enforces the following rules:

- The "from" date must be earlier than the "to" date.
- The range cannot start before your plan's data-retention boundary.
- The range cannot exceed the maximum query duration allowed by the API.

If any of these conditions are not met, a warning alert appears inside the date picker and the range is not applied until you correct it.

### Refresh Runtime Logs

You can refresh the runtime logs to fetch the latest logs from the live deployment or to update the view after applying filters or search terms.

To refresh the logs, click the <InlineIcon Icon={ArrowPath} alt="refresh" /> button at the top right of the Logs page. This will fetch the latest logs from the live deployment and update the view.

### View Log Details

When you click on a runtime log message, you can view its details and metadata in a sidebar on the right side of the Logs page. This includes information like the request size, timestamp, user agent, and more.

From the log details sidebar, you can also:

- Copy the log message to your clipboard by clicking the "Copy message" button at the top right of the sidebar.
- View the JSON log details by clicking the <InlineIcon Icon={Brackets} alt="brackets" /> icon at the top right of the sidebar. This will open a JSON viewer where you can see the log details in a structured format.

- Copy the log details in JSON format by clicking the "Copy as JSON" button at the bottom of the sidebar.

![Button at the bottom of the logs details sidebar](https://res.cloudinary.com/dza7lstvk/image/upload/v1750318514/Cloud/CleanShot_2025-06-19_at_10.33.22_2x_ra3gtg.png)

You can copy the log message or JSON details to share them with your team or the Cloud support.

### Filter by Log Metadata

When you [view a log's details](#view-log-details), you can click on any of its metadata values to filter the logs by that value. This gives you a quick way to find all logs that share the same metadata, such as the same user agent or client IP.

When you click on a metadata value, it will be added to the Filters sidebar, and the logs will be updated by that filter.

### Download Runtime Logs

You can download the runtime logs as a `.log` file for offline analysis, sharing with your team, or sharing with Cloud support if you need help debugging an issue.

To download runtime logs, click the <InlineIcon Icon={ArrowDownTray} alt="download" /> button at the top right of the Logs page. This will download the logs currently shown in a `.json` file format, which you can open with any text editor.

<Note title="Tip">

If you applied filters or search terms, only the logs shown that match those criteria will be downloaded. This allows you to download a specific subset of logs that are relevant to your debugging needs.

</Note>

## Correlate Runtime Errors with Requests

When an error appears in the backend runtime logs, trace it back to the request and API route that caused it. Some errors don't come from a request at all.

This section explains how the Medusa backend logs requests and errors, and how to use the runtime logs to connect them.

### How the Medusa Backend Logs Requests and Errors

In a Cloud environment, the Medusa backend writes each log as a JSON line. These logs fall into the following groups:

- **HTTP request logs**: The backend writes one log at the `http` level for each request after it sends the response. It holds the request's metadata, such as `method`, `path`, `status`, `duration`, `client_ip`, `user_agent`, and `request_id`. The `request_id` is the value of the request's `x-request-id` header, or a generated UUID if the request doesn't have that header.
- **Error logs**: When an API route or middleware throws an error, Medusa's error handler logs it before it sends the error response. The error handler logs errors that result in a `5xx` status code at the `error` level with the error message and stack trace. It logs errors that result in a `4xx` status code, such as validation or not-found errors, at the `info` level with the error message and without the stack trace.
- **Other logs**: Messages that your customizations log with the [Logger](!docs!/learn/debugging-and-testing/logging), and messages that Medusa logs during startup or background tasks.

For example, an error log for an API route that threw an unexpected error looks like this:

```json
{
  "level": "error",
  "message": "Cannot read properties of undefined",
  "stack": [
    {
      "fileName": "/app/src/api/store/custom/route.js",
      "lineNumber": 12,
      "functionName": "GET",
      "typeName": null,
      "methodName": null,
      "columnNumber": 34,
      "native": false
    }
  ],
  "timestamp": "2026-10-20 10:15:32"
}
```

Error logs don't include the `request_id`, `path`, or other request metadata. To find the request that caused an error, use the error's timestamp and stack trace. Then, find the HTTP request log that the backend writes right after the error, as explained in the next section.

The exception is errors that occur while the backend parses the request body. For example, the body isn't valid JSON, or the client aborted the request before sending its full body. The backend logs these errors with the request's path in the message, such as `Error 400 at /store/carts: request aborted`.

<Note>

Some messages bypass Medusa's logger, such as messages that third-party libraries print with `console.log` and uncaught exceptions or unhandled promise rejections. These messages are plain text instead of JSON, so they don't have a level or request metadata, and the Cloud logs may show a JSON parsing error for them.

</Note>

### Find the Request That Caused an Error

To find the request that caused an error in the backend runtime logs:

1. Find the error log. For example, set the **Level** filter to "Error", or [search](#search-runtime-logs) for the error's message.
2. [View the error's details](#view-log-details) and note its timestamp and stack trace.
3. Check the stack trace for files in your project, such as files under `src/api`, `src/workflows`, or `src/modules`. These files point to the API route, workflow, or module that threw the error.
4. Set the **Timeline** filter to a short custom range around the error's timestamp, and set the **Status Code** filter to the status code of the error. For example, "500" for unexpected errors.
5. Find the HTTP request log right after the error log. Since the backend logs the error before it sends the response, the request's log follows the error log.
6. View the HTTP request log's details to find the request's `path`, `method`, `request_id`, `user_agent`, and `client_ip`.

The [Cloud CLI](../cli/commands/logs/page.mdx) also finds these logs. For example, to find the requests that failed with a `500` status code within a minute of an error:

```bash
mcloud logs \
  --metadata status=500 \
  --from 2026-10-20T10:15:00Z \
  --to 2026-10-20T10:16:00Z
```

<Note title="Tip">

If your storefront or client application sends an `x-request-id` header with its requests, the backend uses that value as the request's `request_id`. Then, filter the HTTP request logs by the ID that your client logged for a failed request. For example, click the `request_id` value in the log's details, or pass `--metadata request_id=<id>` to `mcloud logs`.

</Note>

For deeper insights into each request, set up [instrumentation with OpenTelemetry](!docs!/learn/debugging-and-testing/instrumentation) and an error-tracking service like [Sentry](!resources!/integrations/guides/sentry). They show the route handler, middleware, workflows, and database queries that ran for a request, and the errors they threw.

### Errors Not Tied to a Request

Some runtime errors don't originate from an HTTP request, so they don't have a matching HTTP request log. For example:

- Errors in [scheduled jobs](!docs!/learn/fundamentals/scheduled-jobs), [subscribers](!docs!/learn/fundamentals/events-and-subscribers), or workflows running in the background.
- Errors from the backend connections to services like the database or Redis.

For example, you may see the following message in the backend runtime logs:

```text
Connection Error: Connection ended unexpectedly
```

The Medusa backend keeps a pool of database connections that it reuses across operations. Before the database library that manages the pool reuses an idle connection, it checks whether the database server or the network closed it. If so, it prints this message. The library then discards that connection and opens a new one, so the message alone doesn't mean that a request failed.

The library prints this message with `console.log` rather than Medusa's logger, so the message is plain text without request metadata. To check whether any request failed around the same time, set the **Timeline** filter to a short range around the message's timestamp and the **Status Code** filter to "500". If you find failed requests, use the steps in the [earlier section](#find-the-request-that-caused-an-error) to find their error logs and API routes.
