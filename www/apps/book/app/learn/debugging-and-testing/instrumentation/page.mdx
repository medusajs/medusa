In this chapter, you'll learn about observability in Medusa and how to configure instrumentation with OpenTelemetry.

## What is Instrumentation?

Instrumentation is the collection of data about your application's performance and errors. It helps you debug issues, monitor performance, and gain insights into how your application behaves in production.

Instrumentation and observability are crucial as you build customizations in your application. They allow you to optimize performance, identify bottlenecks, and ensure your application runs smoothly.

---

## Instrumentation and Observability with OpenTelemetry

Medusa uses [OpenTelemetry](https://opentelemetry.io/) for instrumentation and reporting. When configured, it reports traces for:

- HTTP requests
- Workflow executions
- Query usages
- Database queries and operations

It also supports metrics collection for:

- Node.js event loop performance
- Runtime metrics (memory usage, garbage collection)

### Install Dependencies

<Note>

As of [Medusa v2.11.0](https://github.com/medusajs/medusa/releases/tag/v2.11.0), OpenTelemetry dependencies are installed by default in new Medusa projects. If you're using an older version of Medusa, you need to install the `@opentelemetry/sdk-node`, `@opentelemetry/sdk-metrics`, `@opentelemetry/resources`, `@opentelemetry/sdk-trace-node`, and `@opentelemetry/instrumentation-pg` dependencies.

</Note>

Before you start, you must install the dependencies relevant for the exporter you use. If you're using Zipkin, install the following dependencies:

```bash npm2yarn
npm install @opentelemetry/exporter-zipkin @opentelemetry/exporter-prometheus
```

### Add instrumentation.ts

Next, create the file `instrumentation.ts` with the following content:

```ts title="instrumentation.ts"
import { registerOtel } from "@medusajs/medusa"
import { ZipkinExporter } from "@opentelemetry/exporter-zipkin"
import { PrometheusExporter } from "@opentelemetry/exporter-prometheus"

// If using an exporter other than Zipkin, initialize it here.
const exporter = new ZipkinExporter({
  serviceName: "my-medusa-project",
})

// Optional: metrics exporter for runtime and event loop metrics
const metricsExporter = new PrometheusExporter({
  port: 9090,
})

export function register() {
  registerOtel({
    serviceName: "medusajs",
    // pass exporter
    exporter,
    // pass metrics exporter (optional)
    metricsExporter,
    instrument: {
      http: true,
      workflows: true,
      query: true,
      runtime: true,     // Enable Node.js runtime metrics
      eventLoop: true,   // Enable event loop monitoring
    },
  })
}
```

In the `instrumentation.ts` file, you export a `register` function that uses Medusa's `registerOtel` utility function. You also initialize an instance of the exporter, such as Zipkin, and pass it to the `registerOtel` function.

`registerOtel` accepts an object where you can pass any [NodeSDKConfiguration](https://open-telemetry.github.io/opentelemetry-js/interfaces/_opentelemetry_sdk-node.NodeSDKConfiguration.html) property along with the following properties:

<Note>

The `NodeSDKConfiguration` properties are accepted since Medusa v2.5.1.

</Note>

## Runtime Metrics

When you enable `runtime` and `eventLoop` instrumentation, Medusa collects the following metrics:

### Runtime Metrics

- `nodejs_memory_heap_used_bytes`: V8 heap memory used
- `nodejs_memory_heap_total_bytes`: V8 heap memory total
- `nodejs_memory_rss_bytes`: Resident Set Size
- `nodejs_memory_external_bytes`: Memory used by C++ objects bound to JavaScript
- `nodejs_memory_array_buffers_bytes`: Memory allocated for ArrayBuffers and SharedArrayBuffers
- `nodejs_gc_duration_seconds`: Garbage collection duration

### Event Loop Metrics

- `nodejs_eventloop_delay_min_ms`: Minimum event loop delay
- `nodejs_eventloop_delay_mean_ms`: Mean event loop delay
- `nodejs_eventloop_delay_max_ms`: Maximum event loop delay
- `nodejs_eventloop_delay_stddev_ms`: Standard deviation of event loop delay
- `nodejs_eventloop_delay_p50_ms`: 50th percentile event loop delay
- `nodejs_eventloop_delay_p95_ms`: 95th percentile event loop delay
- `nodejs_eventloop_delay_p99_ms`: 99th percentile event loop delay
- `nodejs_eventloop_utilization_ratio`: Event loop utilization ratio (0-1)

## Medusa Cloud Integration

If you're using Medusa Cloud, instrumentation can be automatically configured using environment variables. Medusa will detect the cloud environment and export telemetry data to the configured endpoints.

The following environment variables are used for cloud configuration:

- `MEDUSA_CLOUD_OTLP_TRACES_EXPORTER_URL`: URL for exporting trace data
- `MEDUSA_CLOUD_OTLP_TRACES_EXPORTER_HEADERS`: JSON string of headers for trace export
- `MEDUSA_CLOUD_OTLP_METRICS_EXPORTER_URL`: URL for exporting metrics data  
- `MEDUSA_CLOUD_OTLP_METRICS_EXPORTER_HEADERS`: JSON string of headers for metrics export

When these environment variables are set in a Medusa Cloud environment, traces and metrics are automatically exported without additional configuration.

## Test it Out

To test it out, start your exporter, such as Zipkin.

Then, start your Medusa application:

```bash npm2yarn
npm run dev
```

Try to open the Medusa Admin or send a request to an API route.

If you check traces in your exporter, you'll find new traces reported.

### Trace Span Names

Trace span names start with the following keywords based on what it's reporting:

- `{methodName} {URL}` when reporting HTTP requests, where `{methodName}` is the HTTP method, and `{URL}` is the URL the request is sent to.
- `route:` when reporting route handlers running on an HTTP request.
- `middleware:` when reporting a middleware running on an HTTP request.
- `workflow:` when reporting a workflow execution.
- `step:` when reporting a step in a workflow execution.
- `query.graph:` when reporting Query usages.
- `pg.query:` when reporting database queries and operations.
