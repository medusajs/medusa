## Medusa Versioning

When Medusa puts out a new release, all packages are updated to the same version. This ensures that all packages are compatible with each other, and makes it easier for you to switch between versions.

<Note>

This doesn't apply to the design-system packages, including `@medusajs/ui`, `@medusajs/ui-presets`, and `@medusajs/ui-icons`. These packages are versioned independently. However, you don't need to install and manage them separately in your Medusa application, as they are included in the `@medusajs/admin-sdk`. If you're using them in a standalone project, such as a storefront or custom admin dashboard, refer to [this section in the Medusa UI documentation](!ui!/installation/standalone-project#updating-ui-packages) for update instructions.

</Note>

Medusa updates the version number `major.minor.patch` according to the following rules:

- **patch**: A patch release includes bug fixes and minor improvements. It doesn't include breaking changes. For example, if the current version is `2.0.0`, the next patch release will be `2.0.1`.
- **minor**: A minor release includes new features, fixes, improvements, and breaking changes. For example, if the current version is `2.0.0`, the next minor release will be `2.1.0`.
- **major**: A major release includes significant changes to the entire codebase and architecture. For those, the update process will be more elaborate. For example, if the current version is `2.0.0`, the next major release would be `3.0.0`.

## Check Installed Version

To check the currently installed version of Medusa in your project, run the following command in your Medusa application:

```bash npx2yarn
npx medusa -v
```

This will show you the installed version of Medusa and the [Medusa CLI tool](!resources!/medusa-cli), which should be the same.

## Check Latest Version

The documentation shows the current version at the top right of the navigation bar. When a new version is released, you'll find a blue dot on the version number. Clicking it will take you to the [release notes on GitHub](https://github.com/medusajs/medusa/releases).

You can also star the [Medusa repository on GitHub](https://github.com/medusajs/medusa) to receive updates about new releases on your GitHub dashboard. Our team also shares updates on new releases on our social media channels.

## Ensure Custom Migrations Have Rollback Methods

When you create custom migrations, include both `up` and `down` methods. The `up` method applies the changes to the database schema, and the `down` method reverses them. This lets you roll back database changes if you need to revert an update.

If you use the [db\:generate](!resources!/medusa-cli/commands/db#dbgenerate) command to generate migrations, it creates both methods for you. If you write migrations manually, learn more in the [Migrations](../fundamentals/data-models/write-migration/page.mdx) chapter.

## Update Medusa Application

<Note title="Agent Hand-off">

Your AI agent can perform the steps in this section. Run the following prompt in your agent from your Medusa application's directory:

```bash title="Prompt"
Fetch https://docs.medusajs.com/learn/update.md and update my Medusa application to the latest version
```

</Note>

You update your Medusa application [locally](!cloud!/setup-locally), then push the update to your [Cloud](!cloud!) project's repository. Cloud deploys it and migrates the environment's database.

Before updating a Medusa application, make sure to check the [release notes](https://github.com/medusajs/medusa/releases) for any breaking changes that require actions from your side.

### 1. Update Dependencies Locally

In your [local Medusa application](!cloud!/setup-locally), create a new branch for the update, or check out the branch of a [long-lived environment](!cloud!/environments/long-lived) such as Staging. You'll test the update on this branch before it reaches production.

Then, bump the version of all `@medusajs/*` dependencies in your `package.json`, and re-install dependencies:

```bash npm2yarn
npm install
```

This will update all Medusa packages to the latest version.

### 2. Run Migrations Locally

Releases may include changes to the database, such as new tables, updates to existing tables, updates after adding links, or data migration scripts.

So, after updating Medusa, run the following command to migrate the latest changes to your local database:

```bash npx2yarn
npx medusa db:migrate
```

This will run all pending migrations, sync links, and run data migration scripts.

<Note title="Prompt for link changes?">

If `medusa db:migrate` shows a "Select tables to act upon" prompt locally, the new version removed or changed links. Cloud deployments don't show this prompt. Cloud applies all link changes automatically, including deleting the tables of removed links. Learn more in the [Database](!cloud!/database#how-cloud-applies-link-changes) guide.

</Note>

### 3. Test the Update Locally

Start your Medusa application:

```bash npm2yarn
npm run dev
```

Then, check that the application and your customizations work with the new version:

- Check the terminal for errors or warnings while the application starts, such as deprecation warnings for APIs your customizations use.
- Open the Medusa Admin at `http://localhost:9000/app`, and check that your admin widgets and UI routes load.
- Send requests to your custom API routes, and test the flows that your workflows, subscribers, and scheduled jobs handle.
- If you have a storefront, run it against the local Medusa application and test the main flows, such as adding to the cart and checking out.
- If you have [integration tests](../debugging-and-testing/testing-tools/page.mdx), run them.

Fix any issues before you push the update.

### 4. Push and Test the Update in Cloud

Don't push an update directly to your production branch. While Medusa updates are generally safe and stable, test the update in a separate environment first to make sure your customizations and configurations work with the new version. Each environment has its own database, so testing in other environments doesn't affect your production data.

Push the changes in `package.json`, the lock file, and any other affected files to your branch:

- If you're on a long-lived environment's branch, such as Staging, Cloud deploys the changes to that environment.
- If you're on a new branch, open a pull request to the production branch. Cloud creates a [preview environment](!cloud!/environments/preview) for the pull request, and Medusa posts a comment on it with links to the preview.

![Diagram showcasing process of deploying to staging then production](https://res.cloudinary.com/dza7lstvk/image/upload/v1750334010/Cloud/deploy-to-staging_d4oyys.jpg)

If you deployed a storefront alongside your Medusa application, Cloud redeploys both the backend and storefront. Cloud also runs the migrations on the environment's database during the deployment.

Then, [access the environment's deployment](!cloud!/deployments/access) to test the update. Use the environment's [build and runtime logs](!cloud!/logs) to debug any issues.

### 5. Push the Update to Production

Once you've tested the update in a staging or preview environment, merge the changes into your production branch. Cloud deploys them to the production environment, which updates the production's code and database.

## Revert an Update

### Revert an Update in Cloud

If you encounter issues after deploying an update, [redeploy a previous deployment](!cloud!/deployments#redeploy-a-deployment) to roll back the code changes.

Redeploying a previous deployment doesn't roll back the database changes made by the update. If you need to roll back the database changes, contact support for assistance.

### Revert an Update Locally

Before reverting an update, if you already ran the migrations, you have to first identify the modules that had migrations. Then, before reverting, run the `db:rollback` command for each of those modules.

For example, if the version you updated to had migrations for the Cart and Product Modules, run the following command:

```bash npx2yarn
npx medusa db:rollback cart product
```

Then, revert the update by changing the version of all `@medusajs/*` dependencies in your `package.json` to the previous version and re-installing dependencies:

```bash npm2yarn
npm install
```

Finally, run the migrations to sync link changes:

```bash npx2yarn
npx medusa db:migrate
```

## Understanding Codebase Changes

In the Medusa codebase, our team uses the following [TSDoc](https://tsdoc.org/) tags to indicate changes made in the latest version for a specific piece of code:

- `@deprecated`: Indicates that a piece of code is deprecated and will be removed in a future version. The tag's message will include details on what to use instead. However, our updates are always backward-compatible, allowing you to update your codebase at your own pace.
- `@since`: Indicates the version when a piece of code was available from. A piece of code that has this tag will only be available starting from the specified version.

## Update Plugin Project

If you have a Medusa plugin project, you only need to update its `@medusajs/*` dependencies in the `package.json` file to the latest version. Then, re-install dependencies:

```bash npm2yarn
npm  install
```
