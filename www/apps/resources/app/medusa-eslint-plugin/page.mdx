# {metadata.title}

The Medusa ESLint Plugin is an official ESLint plugin that helps enforce Medusa's framework conventions across your project. It provides automated static analysis to ensure your code follows best practices for API routes, modules, workflows, subscribers, scheduled jobs, admin extensions, and module links.

## Installation

Install the plugin as a development dependency in your Medusa project:

```bash npm2yarn
npm install -D @medusajs/eslint-plugin eslint
```

Note that `eslint` is a peer dependency and must be installed in your project.

## Usage

The plugin supports ESLint's flat configuration format. Add it to your `eslint.config.js` file:

```js title="eslint.config.js"
import medusa from "@medusajs/eslint-plugin"

export default [...medusa.configs.recommended]
```

## Configurations

### Recommended

The `recommended` configuration is the default preset for Medusa projects. It includes:

- TypeScript parser configuration with project support
- Common file patterns to ignore (`.medusa/`, `dist/`, `node_modules/`, etc.)
- Base plugin setup for TypeScript and TSX files
- Essential service rules for module development
- Essential workflow rules that catch common errors and enforce best practices

```js title="eslint.config.js"
import medusa from "@medusajs/eslint-plugin"

export default [...medusa.configs.recommended]
```

### Strict

The `strict` configuration extends the recommended preset and enables additional rules that require TypeScript type information. These rules are more comprehensive but slower to run:

```js title="eslint.config.js"
import medusa from "@medusajs/eslint-plugin"

export default [...medusa.configs.strict]
```

Note: The strict configuration requires TypeScript type information, so ensure your `parserOptions.project` or `parserOptions.projectService` is properly configured in your ESLint setup.

## Available Rules

The plugin provides rules across different areas to catch common errors and enforce best practices:

### Service Rules (Recommended Configuration)

These rules enforce Medusa's service patterns for classes extending `MedusaService(...)` or classes with names ending in "Service":

- `medusa-context-on-context-param` - Ensures service method parameters typed `Context` are decorated with `@MedusaContext()` (warning level)
- `service-constructor-must-call-super` - Requires service constructors that extend `MedusaService(...)` to call `super(...arguments)`
- `service-methods-must-be-async` - Ensures all public methods on service classes are async or return a Promise
- `use-inject-manager-on-public-methods` - Ensures service methods that accept `Context` parameters use proper injection decorators: `@InjectManager()` for public methods, `@InjectTransactionManager()` for protected/private methods (warning level)

### Workflow Rules (Recommended Configuration)

- `no-async-workflow-constructor` - Prevents async functions in workflow constructors
- `no-conditional-expressions-in-workflow` - Disallows conditional expressions in workflow definitions
- `no-console-log-in-workflow` - Prevents console.log usage in workflows
- `no-direct-variable-mutation-in-workflow` - Prevents direct variable mutation in workflows
- `no-if-in-workflow-constructor` - Disallows if statements in workflow constructors
- `no-loops-in-workflow` - Prevents loops in workflow definitions
- `no-new-date-in-workflow` - Disallows `new Date()` calls in workflow constructors (use `transform` or `createStep` instead)
- `no-spread-in-workflow` - Prevents spread operators in workflow definitions
- `no-throw-in-transform` - Disallows throwing errors in transform functions
- `no-try-catch-in-workflow` - Prevents try-catch blocks in workflow constructors
- `step-id-kebab-case` - Ensures step IDs use kebab-case naming (warning level)
- `step-must-return-step-response` - Requires steps to return StepResponse objects
- `workflow-id-matches-export-or-filename` - Ensures workflow IDs match their export names or filenames (warning level)
- `workflow-must-return-workflow-response` - Requires workflows to return WorkflowResponse objects

### Type-Aware Rules (Strict Configuration Only)

- `no-workflow-call-without-container` - Warns when calling workflows without proper container setup (requires TypeScript type information)
- `no-non-serializable-step-return` - Prevents non-serializable types (Map, Set, WeakMap, WeakSet) in step returns (requires TypeScript type information, applies to workflow directories only)

### Planned Rules

Future releases will add additional rules for:

- **API Routes**: Enforce proper route structure, request/response typing, and error handling patterns
- **Additional Module Rules**: Extended validation for module patterns beyond basic service structure
- **Subscribers**: Verify event handling patterns and subscription setup
- **Scheduled Jobs**: Validate job configuration and execution patterns
- **Admin Extensions**: Enforce widget and UI route conventions
- **Module Links**: Ensure proper module linking and relationship definitions

## Migration from Legacy Configuration

If you're upgrading from ESLint's legacy configuration format, update your configuration to use the flat config format as shown in the usage examples above.

## Development

For contributors working on the plugin:

```bash
# Build the plugin
yarn workspace @medusajs/eslint-plugin build

# Run tests
yarn workspace @medusajs/eslint-plugin test

# Watch mode during development
yarn workspace @medusajs/eslint-plugin watch
```

## Troubleshooting

### TypeScript Project Detection

If you encounter issues with TypeScript project detection, ensure your `tsconfig.json` is properly configured and accessible from your ESLint configuration location. This is particularly important when using the `strict` configuration, which includes type-aware rules.

### Strict Configuration Performance

The strict configuration includes rules that require TypeScript type information. These rules are more thorough but can be slower to run on large codebases. If you experience performance issues, consider using only the `recommended` configuration for faster linting.

### Peer Dependency Warnings

Make sure you have compatible versions of the peer dependencies:
- ESLint v9.0.0 or higher
- TypeScript v4.8.0 or higher

For specific version compatibility, check the plugin's `package.json` file.
