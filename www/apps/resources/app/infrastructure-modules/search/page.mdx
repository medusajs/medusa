## What is the Search Module?

The Search Module provides full-text search functionality in your Medusa application. It indexes your data in a search engine, then serves queries with relevance ranking, filters, facets, highlighting, and vector search.

For example, you can use the Search Module to power a storefront's product search with typo tolerance and category facets, or to let admin users find orders by customer name.

The Search Module writes to and reads from the search engine you integrate, such as [PostgreSQL](./providers/postgres/page.mdx) or [Medusa Search](!cloud!/search) for Cloud users. This gives you flexibility in choosing the search infrastructure that matches your performance and scalability requirements.

### How the Search Module Works

The Search Module has two parts that you control:

- **Search Module Providers**: they implement the logic of talking to a search engine. Learn more in the [Search Module Providers guide](./providers/page.mdx).
- **Search index definitions**: you declare which entity to index, which fields the engine holds, and how to fill the index. Learn more in the [Search Index Definitions guide](./index-definitions/page.mdx).

The Search Module handles everything between the two. It creates and migrates the physical indexes, fills them when they are empty, applies events to keep them current, and compiles a search query into whatever the provider's engine understands.

It also keeps a version per physical index it builds, so a definition change builds a new version alongside the one serving reads and only makes it active once it's filled. Every provider rebuilds an index that way, so a schema change costs no downtime whichever one you use.

Learn how the module builds an index, fills it, and rebuilds it when a definition changes in the [Reindexing and Migrations guide](./reindexing/page.mdx).

## Configure the Search Module

The Search Module is registered by default in your Medusa application with the [PostgreSQL Search Module Provider](./providers/postgres/page.mdx), so you can define an index and start searching without extra configuration. On Cloud, [Medusa Search](!cloud!/search) is registered by default instead.

### Change Default Configuration

To change its configuration or use a different provider, add the Search Module to the `modules` property of the exported object in `medusa-config.ts`:

```ts title="medusa-config.ts"
// To register only for development. This is necessary to use Medusa Search in Cloud
const isDev = process.env.NODE_ENV !== "production"

module.exports = defineConfig({
  // ...
  modules: [
    isDev && {
      resolve: "@medusajs/medusa/search",
      options: {
        index_prefix: "prod_",
        providers: [
          {
            resolve: "@medusajs/medusa/search-postgres",
            id: "search-postgres",
          },
        ],
      },
    },
  ].filter(Boolean),
})
```

<Note>

The Search Module requires at least one Search Module Provider once you declare a search index. If no provider is registered, it throws an error while it initializes.

</Note>

### Run Migrations

If you added the Search Module to an existing Medusa application, run the following command to create the necessary database tables for the module and its provider:

```bash npm2yarn
npx medusa db:migrate
```

## Search Module Providers

A Search Module Provider implements the logic of indexing and searching documents in a search engine. The Search Module uses the provider that each index definition resolves to.

Medusa ships the [PostgreSQL Search Module Provider](./providers/postgres/page.mdx), and [Medusa Search](!cloud!/search) that's available for Cloud users only. You can also create your own.

Providers don't back the same set of features, so the provider you pick decides which index definitions you can declare and which query features you can pass. Refer to [Medusa Search vs PostgreSQL](!cloud!/search/postgres) for what each provider does with every feature they treat differently.

Refer to the [Search Module Providers guide](./providers/page.mdx) to learn how to register providers, choose a default, and point an index at a specific provider.

## Search Products

Medusa declares a `product` index by default, and its storefront API has a `GET /store/products/search` endpoint that searches it. So, products are searchable without an index definition or an API route of your own.

The endpoint accepts a `q` parameter and the same pagination and field selection as `GET /store/products`, and it returns the products in the same shape:

```bash
curl "http://localhost:9000/store/products/search?q=shirt" \
  -H "x-publishable-api-key: pk_123"
```

You'll receive a JSON response like the following:

```json
{
  "products": [
    {
      "id": "prod_01KXR3J9J610DT161E2E4ZS6P1",
      "title": "Medusa T-Shirt",
      "handle": "t-shirt"
    }
  ],
  "count": 1,
  "offset": 0,
  "limit": 20
}
```

The endpoint narrows the search to published products in the request's sales channel, so it returns what a storefront can show as-is.

<Note title="Tip">

To build the search experience in your storefront, use the [InstantSearch adapter](../../instantsearch/page.mdx). It turns InstantSearch widgets, such as a search box, facet filters, and pagination, into Medusa search queries.

</Note>

### Override the Default Product Index

An index definition named `product` replaces the one Medusa declares by default, so your definition alone decides the fields the engine holds, how they're filled, and the settings applied to them. Declare it as explained in [Create a Custom Search Index](#create-a-custom-search-index).

Override the index when it doesn't hold a field your storefront searches, filters, or facets on, or when you need index settings that it doesn't apply. Keep the fields that `GET /store/products/search` filters by, which are `status` and `sales_channel_ids`, along with any of `handle`, `collection_id`, `type_id`, `category_ids`, and `tag_ids` that your storefront passes.

## Create a Custom Search Index

To search data other than products, such as the custom data models of your own modules, declare a search index for it.

### 1. Define a Search Index

Define a search index in a file under the `src/search` directory. An index definition names the entity to index, the fields the engine holds, a `seed` that fills the index, and the events that keep it up-to-date.

For example, to index a custom `brand` data model, create the file `src/search/brand.ts`:

export const definitionHighlights = [
  ["11", "name", "The index name that a search query resolves against."],
  ["12", "entity", "The Query entity used to hydrate non-indexed fields."],
  ["13", "fields", "The fields the search engine holds."],
  ["19", "events", "The events that change the data the index holds."],
  ["24", "consume", "Turns each of those events into document writes."],
  ["25", "seed", "Fills the index with every brand."],
]

```ts title="src/search/brand.ts" highlights={definitionHighlights}
import {
  defineSearchIndex,
  graphConsume,
  graphSeed,
  search,
} from "@medusajs/framework/utils"

const fields = ["id", "name", "country", "created_at"]

export const brandIndex = defineSearchIndex({
  name: "brand",
  entity: "brand",
  fields: search.define({
    id: search.keyword().filterable(),
    name: search.text().searchable({ weight: 3 }),
    country: search.keyword().filterable().facetable(),
    created_at: search.date().sortable(),
  }),
  events: [
    "brand.created",
    "brand.updated",
    "brand.deleted",
  ],
  consume: graphConsume({ fields }),
  seed: graphSeed({ fields }),
})
```

`seed` fills the index in full when Medusa creates or rebuilds it, and Medusa routes each of the workflow events in `events` to `consume`, so the index reflects changes as they happen.

[`graphSeed`](./index-definitions/page.mdx#graphseed-options) and [`graphConsume`](./index-definitions/page.mdx#graphconsume-options) are helpers that read the data with [Query](!docs!/learn/fundamentals/query). `graphSeed` reads the entity's records to fill the index for the first time, and `graphConsume` provides the index changes, such as creating or deleting records, as the events in `events` arrive.

<Note title="Tip">

[Write `seed` and `consume` yourself](./index-definitions/page.mdx#write-seed-and-consume-yourself) when the index's data doesn't come from Query. Learn more about each property, and about the helpers, in the [Search Index Definitions guide](./index-definitions/page.mdx).

</Note>

### 2. Run Migrations

If you're using the PostgreSQL provider (default) or another provider that requires modifications to the database when you make changes to an index definition, run the migrations command to create or update the physical index:

```bash npm2yarn
npx medusa db:migrate
```

Learn more about index migrations in the [Reindexing and Migrations guide](./reindexing/page.mdx).

### 3. Search the Index

Then, run a search with the `search` method of [Query](!docs!/learn/fundamentals/query).

For example, create the [API route](!docs!/learn/fundamentals/api-routes) `src/api/search-brands/route.ts`:

export const searchHighlights = [
  ["10", "query", "Resolve Query from the Medusa container."],
  ["12", "search", "Returns the hydrated entities and the engine's result."],
  ["13", "entity", "The name of the index to search."],
  ["14", "fields", "The fields to return on every result."],
  ["16", "q", "The free-text query, passed among the filters."],
]

```ts title="src/api/search-brands/route.ts" highlights={searchHighlights}
import {
  MedusaRequest,
  MedusaResponse,
} from "@medusajs/framework/http"

export const GET = async (
  req: MedusaRequest,
  res: MedusaResponse
) => {
  const query = req.scope.resolve("query")

  const { data, search_result } = await query.search({
    entity: "brand",
    fields: ["id", "name", "country"],
    filters: {
      q: req.query.q as string,
    },
    pagination: { take: 20 },
  })

  res.json({
    brands: data,
    metadata: search_result.metadata,
  })
}
```

Then, send a `GET` request to the route:

```bash
curl "http://localhost:9000/search-brands?q=acme"
```

You'll receive a JSON response like the following:

```json
{
  "brands": [
    {
      "id": "brand_01KXR3J9J610DT161E2E4ZS6P1",
      "name": "Acme",
      "country": "us"
    }
  ],
  "metadata": {
    "skip": 0,
    "take": 20,
    "count": 1,
    "query": "acme",
    "processing_time_ms": 9
  }
}
```

Learn about filters, facets, highlighting, and vector search in the [Search Queries guide](!docs!/learn/fundamentals/query/search).

### 4. Keeping Indexes Up to Date

To ensure the search provider has the latest data, you need to specify the events that trigger updates in your index definitions, and how those events are handled. Those are defined in the `events` and `consume` properties of an index definition.

Learn more in the [Search Index Definitions guide](./index-definitions/page.mdx#keep-an-index-up-to-date).

To refill an index whose data drifted, such as after a bulk import that emitted no events, rebuild it from the Medusa Admin dashboard. Refer to [Reindex from the Dashboard](./reindexing/page.mdx#reindex-from-the-dashboard).
