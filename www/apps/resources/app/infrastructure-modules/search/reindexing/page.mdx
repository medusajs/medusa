## Index Migrations

A [search index definition](../index-definitions/page.mdx) declares what an index should look like. The physical index in the search engine is a separate thing, so the [Search Module](../page.mdx) has to bring the two in line. It does that with an index migration.

Index migrations run as part of the `db:migrate` command:

```bash npm2yarn
npx medusa db:migrate
```

<Note title="Tip">

You can pass `--skip-search` to `db:migrate` to skip search migrations.

</Note>

You can also run them on their own with the following command:

```bash npm2yarn
npx medusa db:migrate:search
```

The command plans the actions first, then prints what it did:

```bash
info:    Migrating search indexes...
┌────────────────────────────────────┐
│                                    │
│   Created following search indexes │
│     - product (product)            │
│                                    │
└────────────────────────────────────┘
info:    Search indexes migrated. They are filled when the application starts
```

Every action is idempotent, so running it twice is a no-op. When the physical indexes already match every definition, the command prints `Search indexes already up-to-date` and changes nothing.

### How Index Changes Are Handled

An index name, such as `product`, isn't one physical index. The Search Module keeps a version per physical index it has ever built for that name, and one of them is the index's active version. A query resolves the name to the active version, so which physical index answers a search can change without your code changing.

That's what makes a schema change zero-downtime. When a definition changes, the module builds a new version alongside the active one, fills it, then makes the new version active. Reads keep hitting the old version throughout and never see a half-built one. A version that fails to fill stays behind without ever going live, so the active version keeps answering queries.

A version is also what lets an index move between providers. Setting a different `provider` on a definition makes the module build the new version on that provider, and the old provider's data only gets dropped once the new version is active.

<Note title="Warning" type="warning">

The module only fills a new version in worker or shared mode. An application running in server mode never seeds, so the new version stays inactive until a worker or shared process runs, or until you rebuild the index [on demand](#seeding-on-demand).

</Note>

## Seeding at Application Start

When your application starts in worker or shared mode, the Search Module checks every index and fills the ones that need data. An application running in server mode skips this entirely, so at least one worker or shared process has to run for an index to be filled.

The module seeds an index for one of the following reasons:

1. A migration created the index and nothing has filled it yet.
2. The index exists and holds no documents, such as after an engine restart wiped it.
3. A migration built a new version of the index, which the module fills and then makes active.
4. The previous seed didn't complete, so the module resumes it.

The module records every seed run, so an interrupted run passes its `last_key` back to the definition's `seed` function and resumes where it stopped. Refer to [Fill the Index with `seed`](../index-definitions/page.mdx#fill-the-index-with-seed).

Once a full seed finishes, the module runs the definition's `seed` function once more as a catch-up pass, so a record that changed while the seed was writing still lands in the index. Refer to [The Catch-Up Pass](#the-catch-up-pass).

## Seeding on Demand

You can rebuild an index manually from the Medusa Admin dashboard, or programmatically with the `reindex` method of the Search Module's service.

### Reindex from the Dashboard

The quickest way to rebuild your index is from the admin dashboard. Refer to the [Manage Search Indexes](!user-guide!/settings/search) user guide for the steps to do that.

### Reindex Programmatically

You can also use the `reindex` method of the Search Module's service to rebuild an index in your own code.

For example, the following workflow step rebuilds only the published products in the `product` index:

export const highlights = [
  ["15", "index", "The indexes to rebuild. Defaults to every index."],
  ["16", "filters", "Passed to the definition's `seed` function."],
]

```ts title="src/workflows/steps/reindex-products.ts" highlights={highlights}
import { Modules } from "@medusajs/framework/utils"
import {
  createStep,
  StepResponse,
} from "@medusajs/framework/workflows-sdk"

export const reindexProductsStep = createStep(
  "reindex-products",
  async (_, { container }) => {
    const searchModuleService = container.resolve(
      Modules.SEARCH
    )

    const result = await searchModuleService.reindex({
      index: "product",
      filters: { status: "published" },
    })

    return new StepResponse(result)
  }
)
```

`reindex` accepts the following input:

It returns the names of the indexes it rebuilt, and a `job_id`. The method waits for every index to finish before it resolves, so there's nothing to poll.

The Search Module records the run in its `search_index_sync` table, stamping every row with the `job_id`. Each row holds the run's status, how many documents it wrote, its `last_key`, and the error if it failed. A run that ends with a [catch-up pass](#the-catch-up-pass) gets a second row under the same `job_id` for that pass. The module exposes no method to read those rows, so query the table directly when you need them.

A row points at the index version it filled rather than at the index, so join `search_index_sync` to `search_index_version`, then to `search_index`, to find the runs of a given index.

### Reindex Strategies

You can specify how the module rebuilds an index with the `strategy` option. The two strategies are:

  <Table.Header>
    <Table.Row>
      <Table.HeaderCell>
        Strategy
      </Table.HeaderCell>
      <Table.HeaderCell>
        Description
      </Table.HeaderCell>
    </Table.Row>
  </Table.Header>
  <Table.Body>
    <Table.Row>
      <Table.Cell>
        `swap`
      </Table.Cell>
      <Table.Cell>
        Fills a new version of the index, then makes it the active one. The version already serving reads keeps doing so throughout. This is the default.
      </Table.Cell>
    </Table.Row>
    <Table.Row>
      <Table.Cell>
        `in_place`
      </Table.Cell>
      <Table.Cell>
        Writes into the version already serving reads, rather than building a new one. Cheaper, but the index serves partial data while the seed runs.
      </Table.Cell>
    </Table.Row>
  </Table.Body>
</Table>

<Note title="Tip">

Use `swap` when your index must keep answering queries correctly throughout the rebuild, which is the reason it's the default.

Passing `filters` always rebuilds in place, even if you set `strategy` to `swap`. A partial rebuild would only hold the filtered slice, so making it the active version would drop every other document.

</Note>

A full `in_place` rebuild clears the index before it seeds, so a document the seed no longer produces doesn't survive as stale data. A filtered rebuild doesn't clear anything, since the filters select the records to read rather than the documents to remove.

## The Catch-Up Pass

A full run reads your data while your application keeps writing to it, so a record that changes mid-run can land in the index stale, or not at all. To close that gap, the module runs the definition's `seed` function a second time as soon as the run finishes, passing to it `catchup.since`, which is the time the run started. The pass writes into the same index, and a swap only makes that index active once the pass finishes.

The pass runs after a full seed at application start and after a full reindex, under either strategy. The module skips it for a filtered reindex, since a partial rebuild is already scoped to what you asked for, and catching up on everything that changed would write more than that.

Since the pass calls the same `seed` function, your definition decides what it costs: read the `catchup` property to narrow your query and to yield a `delete` write for a record deleted mid-run. Refer to [Catch Up on Changes During a Run](../index-definitions/page.mdx#catch-up-on-changes-during-a-run) for how to handle it.

## Keeping Indexes in Sync

An index holds a copy of your data, so it can fall behind the database. The [`events` and `consume`](../index-definitions/page.mdx#keep-an-index-up-to-date) properties of an index definition close that gap as changes happen, and a reindex repairs it when the gap grows too wide.

### Recover with a Reindex

A reindex is the repair path for a diverged index, since it rebuilds documents from the definition's `seed` function rather than from an event. Refer to [Seeding on Demand](#seeding-on-demand) for how to call it.

Two details matter when you reindex to recover:

- Pass `filters` to rebuild only the affected slice. A filtered run costs less than a full rebuild, and it always writes in place, so the documents outside the slice keep serving reads.
- Omit `filters` for a full repair. Both strategies then rebuild every document from the seed, and either one drops what the seed no longer produces. Keep the default `swap` if the index must keep answering queries while it rebuilds.

<Note title="Tip">

Query the `search_index_sync` table to find out whether a run succeeded, how many documents it wrote, and the error it failed with.

</Note>
