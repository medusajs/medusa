# {metadata.title}

Medusa's testing framework provides database snapshot utilities that significantly improve test performance by allowing you to save and restore database states instead of recreating them for each test.

## Overview

Database snapshots work by:

1. **Creating a snapshot** once per test suite after setting up the database (migrations, links, etc.)
2. **Restoring from snapshot** in each test's `beforeEach` hook instead of recreating data

This approach can provide approximately **30% faster test runs** compared to traditional setup/teardown patterns.

## Automatic Snapshot Management

The Medusa test runner automatically handles snapshots for you:

- `snapshot()` runs once after the complete database setup
- `restore()` runs in `beforeEach` to reset the database to the snapshot state

```ts
import { medusaIntegrationTestRunner } from "@medusajs/test-utils"

medusaIntegrationTestRunner({
  testSuite: ({ api, getContainer, dbUtils }) => {
    // The test runner automatically creates a snapshot after setup
    // and restores from it before each test

    describe("My Test Suite", () => {
      it("should test something", async () => {
        // Database is automatically restored to snapshot state
        // Your test code here
      })
    })
  },
})
```

## Manual Snapshot Optimization

For even faster tests, you can optimize by moving data seeding from `beforeEach` to `beforeAll` and creating your own snapshot:

```ts
import { medusaIntegrationTestRunner } from "@medusajs/test-utils"

medusaIntegrationTestRunner({
  testSuite: ({ api, getContainer, dbUtils }) => {
    describe("Optimized Test Suite", () => {
      beforeAll(async () => {
        const container = getContainer()
        const productModule = container.resolve("productModuleService")
        
        // Seed test data once
        await productModule.createProducts([
          {
            title: "Test Product 1",
            handle: "test-product-1",
          },
          {
            title: "Test Product 2", 
            handle: "test-product-2",
          }
        ])

        // Create snapshot with seeded data
        await dbUtils.snapshot()
      })

      it("should find products", async () => {
        // Database already contains seeded products from snapshot
        const response = await api.get("/store/products")
        expect(response.data.products).toHaveLength(2)
      })

      it("should handle product operations", async () => {
        // Each test starts with the same snapshot state
        const response = await api.get("/store/products/test-product-1")
        expect(response.data.product.title).toBe("Test Product 1")
      })
    })
  },
})
```

## Snapshot Methods

The database utilities (`dbUtils`) provide snapshot methods:

### `snapshot()`

Creates a snapshot of the current database state.

```ts
await dbUtils.snapshot()
```

### `restore()`

Restores the database to the last snapshot state.

```ts
await dbUtils.restore()
```

<Note>

The snapshot is automatically created after the initial test suite setup. You only need to call `snapshot()` manually if you want to create a new snapshot with additional seeded data.

</Note>

## Migration from Traditional Patterns

### Before: Traditional `beforeEach` Pattern

```ts
// ❌ Slower approach
describe("Product Tests", () => {
  beforeEach(async () => {
    // Recreate data for every test
    await productModule.createProducts([...])
  })

  afterEach(async () => {
    // Clean up after every test
    await productModule.deleteProducts([...])
  })
})
```

### After: Snapshot-Optimized Pattern

```ts
// ✅ Faster approach
describe("Product Tests", () => {
  beforeAll(async () => {
    // Create data once
    await productModule.createProducts([...])
    await dbUtils.snapshot() // Save this state
  })
  
  // Database automatically restores before each test
  // No need for cleanup - snapshot restoration handles it
})
```

## Potential Issues During Migration

When upgrading to snapshot-enabled test utilities, you might encounter issues if your tests:

1. **Break module encapsulation** - Tests that directly access internal module state may need adjustment
2. **Rely on incorrect behaviors** - Some test bugs may surface when the database state is properly isolated
3. **Have timing dependencies** - Tests that depend on specific timing between database operations

<Note>

If you encounter test failures after enabling snapshots, review your test logic rather than disabling snapshots. The failures often indicate existing test issues that snapshots help expose.

</Note>

## Best Practices

1. **Move seeding to `beforeAll`**: Create test data once and snapshot it
2. **Minimize database operations**: Reduce the number of create/delete cycles in tests
3. **Use descriptive test names**: Clear names help identify which snapshot state tests expect
4. **Group related tests**: Keep tests that use similar data together in `describe` blocks
5. **Avoid stateful operations across tests**: Each test should be independent

## Performance Impact

- **Without snapshots**: Each test recreates database state (~100ms per test)
- **With automatic snapshots**: Each test restores from snapshot (~30ms per test)  
- **With optimized snapshots**: Seeded data is restored instantly (~10ms per test)

The performance improvement is most noticeable in test suites with many tests or complex data setup requirements.
