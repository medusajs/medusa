# {metadata.title}

In this guide, you’ll learn about the GitHub Auth Module Provider and how to configure it.

The GitHub Auth Module Provider allows you to authenticate users with their GitHub account.

To use the GitHub Auth Module Provider, add the module to the array of providers passed to the Auth Module in your `medusa-config.ts`:

```ts title="medusa-config.ts"
import { Modules, ContainerRegistrationKeys } from "@medusajs/framework/utils"

// ...

module.exports = defineConfig({
  // ...
  modules: [
    {
      resolve: "@medusajs/medusa/auth",
      dependencies: [Modules.CACHE, ContainerRegistrationKeys.LOGGER],
      options: {
        mfa: {
          encryption_key: process.env.AUTH_MFA_ENCRYPTION_KEY,
        },
        providers: [
          // other providers...
          {
            resolve: "@medusajs/medusa/auth-github",
            id: "github",
            options: {
              clientId: process.env.GITHUB_CLIENT_ID,
              clientSecret: process.env.GITHUB_CLIENT_SECRET,
              callbackUrl: process.env.GITHUB_CALLBACK_URL,
            },
          },
        ],
      },
    },
  ],
})
```

### Environment Variables

Set the `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, and `GITHUB_CALLBACK_URL` environment variables:

1. In Cloud, add the variables in your environment's [Environment variables settings](!cloud!/environments/environment-variables#add-environment-variables-on-cloud).
    - Mark `GITHUB_CLIENT_SECRET` as **Sensitive**, and enable the **Build** toggle for all variables, since `medusa-config.ts` reads them during the build.
    - Set `GITHUB_CALLBACK_URL` to a page of your deployed frontend, such as your storefront.
2. For local development, add the variables to your `.env` file, with `GITHUB_CALLBACK_URL` set to a page of your local frontend:

```bash title=".env"
GITHUB_CLIENT_ID=<YOUR_GITHUB_CLIENT_ID>
GITHUB_CLIENT_SECRET=<YOUR_GITHUB_CLIENT_SECRET>
GITHUB_CALLBACK_URL=<YOUR_GITHUB_CALLBACK_URL>
```

Make sure to add both callback URLs to your GitHub app's allowed callback URLs.

### Deploy to Cloud

Commit the changes to `medusa-config.ts` and push them to the branch that your Cloud environment tracks. Cloud then [creates a deployment](!cloud!/deployments#how-are-deployments-created) that registers the GitHub Auth Module Provider. Add the environment variables in Cloud before you push, so the deployment uses them.

## Allow the GitHub Provider for Customers

By default, customers and other custom actor types can authenticate with any registered Auth Module Provider, whereas admin users can only authenticate with the `emailpass` provider. If you deploy your application to Cloud, admin users can also authenticate with their Cloud account.

To specify the actor types that can use the GitHub Auth Module Provider, set the [authMethodsPerActor configuration](!docs!/learn/configurations/medusa-config#httpauthMethodsPerActor) in `medusa-config.ts`:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  projectConfig: {
    http: {
      authMethodsPerActor: {
        user: ["emailpass"],
        customer: ["emailpass", "github"],
      },
      // ...
    },
    // ...
  },
  // ...
})
```

This configuration allows customers to authenticate with their email and password or with GitHub, and admin users to authenticate with their email and password only.

<Note title="Warning" type="warning">

Don't add `github` to the `user` actor type. Any GitHub account can authenticate with this provider, and it doesn't have an option to restrict the accounts that can authenticate. So, if you allow the `user` actor type to use it, anyone with a GitHub account can become an admin user of your store. Learn more in the [Auth Module Provider](../page.mdx#public-auth-providers-for-admin-users) guide.

</Note>

## Override Callback URL During Authentication

In many cases, you may have different callback URLs for actor types. For example, you may redirect admin users to a different URL than customers after authentication.

The [Authenticate or Login API Route](../../authentication-route/page.mdx#login-route) accepts a `callback_url` body parameter to override the provider's `callbackUrl` option. Learn more in the [Auth Flows with Routes guide](../../authentication-route/page.mdx#login-route).

## Access GitHub Tokens

<Note>

This feature is available since [Medusa v2.23.1](https://github.com/medusajs/medusa/releases/tag/v2.23.1).

</Note>

If you need the user's GitHub tokens, for example, to send requests to the GitHub API on their behalf, set the `storeTokens` option to `false` and consume the `authCallbackValidated` hook of the [validateAuthCallbackWorkflow](/references/medusa-workflows/validateAuthCallbackWorkflow). The workflow runs when the frontend sends a request to the `/auth/{actor_type}/github/callback` route.

The hook receives a `provider_data` property with the following data:

- `token`: The response of GitHub's token exchange, which holds the access and refresh tokens.
- `user`: The response of GitHub's `GET /user` request.

For example:

```ts title="src/workflows/hooks/auth-callback-validated.ts"
import { 
  validateAuthCallbackWorkflow,
} from "@medusajs/medusa/core-flows"

validateAuthCallbackWorkflow.hooks.authCallbackValidated(
  async (
    { auth_identity, auth_provider, provider_data },
    { container }
  ) => {
    if (auth_provider !== "github") {
      return
    }
    // TODO store provider_data.token, encrypted,
    // in your own storage
  }
)
```

`provider_data` is secret, so don't log it. Learn more about the hook in the [Auth Flows with Routes](../../authentication-route/page.mdx#access-the-providers-data-after-validation) guide.
