# {metadata.title}

In this guide, you’ll learn about the Google Auth Module Provider and how to install and use it in the Auth Module.

The Google Auth Module Provider allows you to authenticate users with their Google account.

To use the Google Auth Module Provider, add the module to the array of providers passed to the Auth Module in your `medusa-config.ts`:

```ts title="medusa-config.ts"
import { Modules, ContainerRegistrationKeys } from "@medusajs/framework/utils"

// ...

module.exports = defineConfig({
  // ...
  modules: [
    // ...
    {
      resolve: "@medusajs/medusa/auth",
      dependencies: [Modules.CACHE, ContainerRegistrationKeys.LOGGER],
      options: {
        mfa: {
          encryption_key: process.env.AUTH_MFA_ENCRYPTION_KEY,
        },
        providers: [
          // other providers...
          {
            resolve: "@medusajs/medusa/auth-emailpass",
            id: "emailpass",
          },
          {
            resolve: "@medusajs/medusa/auth-google",
            id: "google",
            options: {
              clientId: process.env.GOOGLE_CLIENT_ID,
              clientSecret: process.env.GOOGLE_CLIENT_SECRET,
              callbackUrl: process.env.GOOGLE_CALLBACK_URL,
            },
          },
        ],
      },
    },
  ],
})
```

### Environment Variables

Set the `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `GOOGLE_CALLBACK_URL` environment variables:

1. In Cloud, add the variables in your environment's [Environment variables settings](!cloud!/environments/environment-variables#add-environment-variables-on-cloud).
    - Mark `GOOGLE_CLIENT_SECRET` as **Sensitive**, and enable the **Build** toggle for all variables, since `medusa-config.ts` reads them during the build.
    - Set `GOOGLE_CALLBACK_URL` to a page of your deployed frontend, such as your storefront.
2. For local development, add the variables to your `.env` file, with `GOOGLE_CALLBACK_URL` set to a page of your local frontend:

```bash title=".env"
GOOGLE_CLIENT_ID=<YOUR_GOOGLE_CLIENT_ID>
GOOGLE_CLIENT_SECRET=<YOUR_GOOGLE_CLIENT_SECRET>
GOOGLE_CALLBACK_URL=<YOUR_GOOGLE_CALLBACK_URL>
```

Make sure to add both callback URLs to the **Authorized redirect URIs** of your Google OAuth client.

### Deploy to Cloud

Commit the changes to `medusa-config.ts` and push them to the branch that your Cloud environment tracks. Cloud then [creates a deployment](!cloud!/deployments#how-are-deployments-created) that registers the Google Auth Module Provider. Add the environment variables in Cloud before you push, so the deployment uses them.

## Allow the Google Provider for Customers

By default, customers and other custom actor types can authenticate with any registered Auth Module Provider, whereas admin users can only authenticate with the `emailpass` provider. If you deploy your application to Cloud, admin users can also authenticate with their Cloud account.

To specify the actor types that can use the Google Auth Module Provider, set the [authMethodsPerActor configuration](!docs!/learn/configurations/medusa-config#httpauthMethodsPerActor) in `medusa-config.ts`:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  projectConfig: {
    http: {
      authMethodsPerActor: {
        user: ["emailpass"],
        customer: ["emailpass", "google"],
      },
      // ...
    },
    // ...
  },
  // ...
})
```

This configuration allows customers to authenticate with their email and password or with Google, and admin users to authenticate with their email and password only.

<Note title="Warning" type="warning">

Don't add `google` to the `user` actor type. Any Google account can authenticate with this provider, and it doesn't have an option to restrict the accounts that can authenticate. So, if you allow the `user` actor type to use it, anyone with a Google account can become an admin user of your store. Learn more in the [Auth Module Provider](../page.mdx#public-auth-providers-for-admin-users) guide.

</Note>

## Override Callback URL During Authentication

In many cases, you may have different callback URLs for actor types. For example, you may redirect admin users to a different URL than customers after authentication.

The [Authenticate or Login API Route](../../authentication-route/page.mdx#login-route) can accept a `callback_url` body parameter to override the provider's `callbackUrl` option. Learn more in [this documentation](../../authentication-route/page.mdx#login-route).

## Access Google Tokens

<Note>

This feature is available since [Medusa v2.23.1](https://github.com/medusajs/medusa/releases/tag/v2.23.1).

</Note>

If you need the user's Google tokens, for example, to send requests to Google APIs on their behalf, consume the `authCallbackValidated` hook of the [validateAuthCallbackWorkflow](/references/medusa-workflows/validateAuthCallbackWorkflow). The workflow runs when the frontend sends a request to the `/auth/{actor_type}/google/callback` route.

The hook receives a `provider_data` property with the following data:

- `token`: The response of Google's token exchange, which holds the access, refresh, and ID tokens.
- `claims`: The claims of the verified ID token.

For example:

```ts title="src/workflows/hooks/auth-callback-validated.ts"
import { 
  validateAuthCallbackWorkflow,
} from "@medusajs/medusa/core-flows"

validateAuthCallbackWorkflow.hooks.authCallbackValidated(
  async (
    { auth_identity, auth_provider, provider_data },
    { container }
  ) => {
    if (auth_provider !== "google") {
      return
    }
    // TODO store provider_data.token, encrypted,
    // in your own storage
  }
)
```

`provider_data` is secret, so don't log it. Learn more about the hook in the [Auth Flows with Routes](../../authentication-route/page.mdx#access-the-providers-data-after-validation) guide.
