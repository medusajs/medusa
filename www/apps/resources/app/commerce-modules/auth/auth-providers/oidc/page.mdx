# {metadata.title}

In this guide, you'll learn about the OpenID Connect (OIDC) Auth Module Provider and how to install and use it in the Auth Module.

<Note>

The OIDC Auth Module Provider is available since Medusa [v2.19.0](https://github.com/medusajs/medusa/releases/tag/v2.19.0).

</Note>

The OIDC Auth Module Provider allows you to authenticate users with any identity provider (IdP) that complies with the OpenID Connect specification, such as Okta, Microsoft Entra ID, Auth0, Keycloak, or Google Workspace.

The provider resolves the identity provider's configuration from its discovery document, and it secures the authentication flow with PKCE (S256), a nonce, and full ID token validation.

## Register the OIDC Auth Module Provider

  items={[

      text: "Create an OIDC application (client) in your identity provider. Set its redirect URI to a URL in your frontend (for example, the storefront or the Medusa Admin) that later uses Medusa's callback route to validate the authentication.",

To use the OIDC Auth Module Provider, add the module to the array of providers passed to the Auth Module in your `medusa-config.ts`. You can register the provider multiple times, once per identity provider, with a different `id` for each registration:

export const highlights = [
  ["17", `"okta"`, "The ID of the provider used in the authentication routes."],
]

```ts title="medusa-config.ts" highlights={highlights}
module.exports = defineConfig({
  // ...
  modules: [
    // ...
    {
      resolve: "@medusajs/medusa/auth",
      options: {
        providers: [
          // other providers...
          {
            resolve: "@medusajs/medusa/auth-emailpass",
            id: "emailpass",
          },
          {
            resolve: "@medusajs/medusa/auth-oidc",
            id: "okta",
            options: {
              issuer: process.env.OKTA_ISSUER,
              client_id: process.env.OKTA_CLIENT_ID,
              client_secret: process.env.OKTA_CLIENT_SECRET,
              callback_url: process.env.OKTA_CALLBACK_URL,
              display_name: "Okta",
            },
          },
        ],
      },
    },
  ],
})
```

The `id` of each registration becomes part of the authentication routes. For example, with the above configuration, customers authenticate through the `/auth/customer/okta` route.

<Note title="Tip">

When you override the `providers` option of the Auth Module, the default `emailpass` provider is no longer registered. Make sure to add it again if you still need it.

</Note>

### Environment Variables

Make sure to add the necessary environment variables for the above options in `.env`:

```plain
OKTA_ISSUER=<YOUR_OKTA_ISSUER_URL>
OKTA_CLIENT_ID=<YOUR_OKTA_CLIENT_ID>
OKTA_CLIENT_SECRET=<YOUR_OKTA_CLIENT_SECRET>
OKTA_CALLBACK_URL=<YOUR_OKTA_CALLBACK_URL>
```

## Authentication Flow

The OIDC Auth Module Provider supports authentication only. It doesn't support the registration route, since users are registered in the identity provider.

The authentication flow is:

1. The frontend sends a request to the [Authenticate or Login API Route](../../authentication-route/page.mdx#login-route) at `/auth/{actor_type}/{id}`. The route returns a `location` URL in the identity provider.
2. The frontend redirects the user to the `location` URL to log in with the identity provider.
3. After the user logs in, the identity provider redirects them to the callback URL.
4. The frontend sends all query parameters it received to the [Validate Callback API Route](../../authentication-route/page.mdx#validate-callback-route) at `/auth/{actor_type}/{id}/callback`. On success, the route returns a JWT token.

On the first login, the provider creates an auth identity whose `entity_id` is the value of the `sub` claim by default. On every following login, the provider updates the auth identity's `user_metadata` with the latest claims from the ID token.

### Troubleshooting Authentication Errors

To avoid leaking sensitive details, the provider always returns a generic `Authentication failed` error to the client when authentication fails. The Medusa application logs the actual cause with the `[auth-oidc]` prefix, so check the logs when debugging a failed login.

For example, if the identity provider can't be reached or rejects the token request, the logs contain the reason and, when available, the identity provider's error code and description.

---

## Override Callback URL During Authentication

In many cases, you may have different callback URLs for actor types. For example, you may redirect admin users to a different URL than customers after authentication.

The [Authenticate or Login API Route](../../authentication-route/page.mdx#login-route) can accept a `callback_url` body parameter to override the provider's `callback_url` option. To restrict which URLs are accepted, set the `allowed_callback_urls` option.
