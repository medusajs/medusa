# {metadata.title}

In this guide, you'll learn how to handle the `auth.password_reset` event to send a reset password email (or other notification type) to users.

<Note title="Looking for no-code docs?">

Refer to this [Merchant Guide](!user-guide!/reset-password) to learn how to reset your user admin password using the dashboard.

</Note>

## Reset Password Flow Overview

![Diagram showcasing the reset password flow detailed below](https://res.cloudinary.com/dza7lstvk/image/upload/v1754050032/Medusa%20Resources/reset-password_qheixj.jpg)

Users of any actor type (admin, customer, or custom actor type) can request to reset their password. The flow for resetting a password is as follows:

1. The user requests to reset their password either through the frontend (for example, [Medusa Admin](!user-guide!/reset-password)) or the [Generate Reset Password Token API route](../authentication-route/page.mdx#generate-reset-password-token-route).
2. The Medusa application generates a secure, single-use password reset token and emits the `auth.password_reset` event.
    - The token is cryptographically secure and expires automatically (default: 15 minutes).
    - Each new password reset request invalidates any previous tokens for the same user.
    - At this point, you can handle the event to send a notification to the user with instructions on how to reset their password.
3. The user receives the notification and clicks on the link to reset their password.
    - The user can reset their password either through the frontend (for example, [Medusa Admin](!user-guide!/reset-password)) or the [Reset Password API route](../authentication-route/page.mdx#reset-password-route).
    - The token is automatically consumed and deleted upon successful password reset, preventing reuse.

In this guide, you'll implement a subscriber that handles the `auth.password_reset` event to send an email notification to the user with instructions on how to reset their password.

After adding the subscriber, you will have a complete reset password flow you can utilize using the Medusa Admin, storefront, or API routes.

## Prerequisites: Email Sending

To send an email to the user, you need a Notification Module Provider registered for the `email` channel.

Cloud projects send notifications of the `email` channel with [Medusa Emails](!cloud!/emails), Cloud's built-in email service. Medusa Emails is enabled by default, so you don't need to configure a Notification Module Provider or add API keys.

<Note>

Without a verified sender domain, Medusa Emails only sends emails to addresses of users in your Cloud organization. To send reset password emails to other email addresses, [add an email sender domain](!cloud!/emails#add-email-sender-domain-to-cloud) to your Cloud project.

</Note>

If you're not using Cloud, you can use another [Notification Module Provider](../../../infrastructure-modules/notification/page.mdx#what-is-a-notification-module-provider) for the `email` channel, or [create your own custom provider](/references/notification-provider-module).

### Testing with the Local Notification Module Provider

Medusa Emails isn't available when you run the Medusa application locally. So, register the [Local Notification Module Provider](../../../infrastructure-modules/notification/local/page.mdx) for the `email` channel during development by adding this to your `medusa-config.ts`:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  // ...
  modules: [
    {
      resolve: "@medusajs/medusa/notification",
      options: {
        providers: [
          // ...
          {
            resolve: "@medusajs/medusa/notification-local",
            id: "local",
            options: {
              channels: [
                process.env.NODE_ENV === "development"
                  ? "email"
                  : "feed",
              ],
            },
          },
        ],
      },
    },
  ],
})
```

The Local provider logs email details to your terminal instead of sending actual emails, which is useful for development and testing. It handles the `email` channel only in development, so Medusa Emails sends the emails in your Cloud environments.

## Create the Reset Password Subscriber

To create a [subscriber](!docs!/learn/fundamentals/events-and-subscribers) that handles the `auth.password_reset` event, create the file `src/subscribers/password-reset.ts` with the following content:

export const highlights=[
  ["11", "data", "The data payload of the event."],
  ["12", "entity_id", "The user's identifier, which is the email when using the `emailpass` provider."],
  ["13", "token", "The password reset token."],
  ["14", "actor_type", "The user's actor type."],
  ["25", "urlPrefix", "Set the page's URL based on the user's actor type."],
  ["36", "resetUrl", "The frontend URL to redirect the user to reset their password."],
  ["39", "createNotifications", "Send a notification to the user."],
  ["41", `"email"`, "The channel to send the notification through."],
  ["42", "content", "The email's subject and HTML content."]
]

```ts title="src/subscribers/handle-reset.ts" highlights={highlights} collapsibleLines="1-9" expandMoreLabel="Show Imports"
import {
  SubscriberArgs,
  type SubscriberConfig,
} from "@medusajs/medusa"
import {
  Modules,
  ContainerRegistrationKeys,
} from "@medusajs/framework/utils"

export default async function resetPasswordTokenHandler({
  event: { data: {
    entity_id: email,
    token,
    actor_type,
  } },
  container,
}: SubscriberArgs<{ entity_id: string, token: string, actor_type: string }>) {
  const notificationModuleService = container.resolve(
    Modules.NOTIFICATION
  )
  const config = container.resolve(
    ContainerRegistrationKeys.CONFIG_MODULE
  )

  let urlPrefix = ""

  if (actor_type === "customer") {
    urlPrefix = config.admin.storefrontUrl || "https://storefront.com"
  } else {
    const backendUrl = config.admin.backendUrl !== "/" ? config.admin.backendUrl :
      "http://localhost:9000"
    const adminPath = config.admin.path
    urlPrefix = `${backendUrl}${adminPath}`
  }

  const resetUrl = `${urlPrefix}/reset-password` +
    `?token=${token}&email=${email}`

  await notificationModuleService.createNotifications({
    to: email,
    channel: "email",
    content: {
      subject: "Reset your password",
      html: `<p>Click <a href="${resetUrl}">here</a> to reset your password.</p>`,
    },
  })
}

export const config: SubscriberConfig = {
  event: "auth.password_reset",
}
```

The subscriber receives the following data through the event payload:

- `entity_id`: The identifier of the user. When using the `emailpass` provider, it's the user's email.
- `token`: The token to reset the user's password.
- `actor_type`: The user's actor type. For example, if the user is a customer, the `actor_type` is `customer`. If it's an admin user, the `actor_type` is `user`.

<Note>

This event's payload previously had an `actorType` field. It was renamed to `actor_type` after [Medusa v2.0.7](https://github.com/medusajs/medusa/releases/tag/v2.0.7).

</Note>

### Reset Password URL

Based on the user's actor type, you set the URL prefix to redirect the user to the appropriate frontend page to reset their password:

- If the user is a customer, you set the URL prefix to the storefront URL.
- If the user is an admin, you set the URL prefix to the backend URL, which is constructed from the `config.admin.backendUrl` and `config.admin.path` values.

Note that the Medusa Admin has a reset password form at `/reset-password?token={token}&email={email}`.

### Notification Configurations

For the notification, you can configure the following fields:

- `to`: The identifier to send the notification to, which in this case is the email.
- `channel`: The channel to send the notification through, which in this case is email.
- `content`: The email's subject and HTML content, which includes the link to reset the password. On Cloud, Medusa Emails sends this content to the user.
    - Refer to the [Use a React Email Template](#use-a-react-email-template) section below to build a richer email template.

### Test It Out

After you set up the Local Notification Module Provider and create the subscriber, you can test the reset password flow.

Start the Medusa application with the following command:

```bash npm2yarn
npm run dev
```

Then, open the Medusa Admin (locally at `http://localhost:9000/app`) and click on "Reset" in the login form. Then, enter the email of the user you want to reset the password for.

Once you reset the password, you should see that the `auth.password_reset` event is emitted in the server's logs:

```bash
info:    Processing auth.password_reset which has 1 subscribers
```

The Local provider logs the email details in your terminal. After you deploy the subscriber to Cloud, Medusa Emails sends the reset password email to the user's inbox. You can track its delivery on the [Email Activity page](!cloud!/emails#monitor-email-sending-activity-on-cloud) of your Cloud project.

## Next Steps: Implementing Frontend

In your frontend, you must have a page that accepts `token` and `email` query parameters.

The page shows the user password fields to enter their new password, then submits the new password, token, and email to the [Reset Password Route](../authentication-route/page.mdx#reset-password-route).

The Medusa Admin already has a reset password page at `/reset-password?token={token}&email={email}`. So, you only need to implement this page in your storefront or custom admin dashboard.

## Use a React Email Template

The subscriber sends a basic HTML email. To build a richer email template, use [React Email](https://react.email) to create the template as a React component, then render it to an HTML string in the subscriber.

The [Set Up React Email Templates](!cloud!/emails/react-email) guide explains how to install React Email in your Medusa project. It also includes a [reset password email template](!cloud!/emails/react-email#reset-password-email-template) with a subscriber that sends it.
