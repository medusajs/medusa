# {metadata.title}

Learn about the key concepts and components of Medusa's Role-Based Access Control (RBAC) system.

## What is RBAC?

Role-Based Access Control (RBAC) is a security model that controls access to resources based on user roles. In Medusa, RBAC provides fine-grained permission management for admin users, allowing you to control who can perform specific operations on different resources.

## Core Components

### Roles

A **role** is a collection of permissions that can be assigned to users. Roles define what a user is allowed to do within the system.

```ts
{
  id: "role_123",
  name: "Product Editor",
  description: "Can create and edit products",
  parent_id: null,
  policies: [...]
}
```

### Policies

A **policy** defines a specific permission using the format `resource:operation`. Policies are the atomic units of permission in the RBAC system.

```ts
{
  id: "policy_123", 
  key: "product.read",
  resource: "product",
  operation: "read",
  name: "View Products",
  description: "Allows viewing product information"
}
```

### Permissions

**Permissions** are the actual access grants that result from the combination of roles and policies. They follow the format `resource:operation`.

Examples:
- `product:read` - Can view products
- `customer:create` - Can create customers  
- `order:*` - Full order management access
- `*:*` - Complete system access (super admin)

## Permission System

### Resource Types

Medusa RBAC supports permissions for all major commerce resources:

- **Products**: `product`, `product_category`, `product_collection`, `product_tag`, `product_type`
- **Orders**: `order`, `payment`, `fulfillment`, `return`
- **Customers**: `customer`, `customer_group`
- **Inventory**: `inventory`, `stock_location`, `reservation`
- **Admin**: `user`, `api_key`, `workflow`
- **Store Setup**: `region`, `store`, `sales_channel`, `shipping_option`
- **Marketing**: `promotion`, `campaign`, `price_list`

### Operations

Standard operations available for most resources:

- `read` - View/list resources
- `create` - Create new resources
- `update` - Modify existing resources  
- `delete` - Remove resources
- `*` - Wildcard for all operations

### Wildcards

The RBAC system supports wildcards (`*`) for flexible permission assignment:

- `*:read` - Read access to all resources
- `product:*` - Full access to products
- `*:*` - Complete system access

Wildcards are expanded at resolution time, so a user with `product:*` automatically gets `product:read`, `product:create`, `product:update`, and `product:delete` permissions.

## Policy Inheritance

Roles can be organized hierarchically using parent-child relationships. Child roles inherit all policies from their parent roles.

```ts
// Parent role
const managerRole = {
  name: "Manager",
  policies: ["product:read", "customer:read"],
}

// Child role inherits parent policies
const seniorManagerRole = {
  name: "Senior Manager", 
  parent_id: managerRole.id,
  policies: ["order:*"], // Gets product:read, customer:read, order:*
}
```

## Permission Guards

Medusa provides React components and hooks for implementing permission-based UI in admin extensions.

### PermissionGuard Component

Conditionally render UI based on user permissions:

```tsx
import { PermissionGuard } from "@medusajs/dashboard"

<PermissionGuard permissions={["product:create"]}>
  <CreateProductButton />
</PermissionGuard>
```

### Permission Hooks

```tsx
import { usePermissions } from "@medusajs/dashboard"

function ProductActions() {
  const { can } = usePermissions()
  
  return (
    <div>
      {can("product", "create") && <CreateButton />}
      {can("product", "update") && <EditButton />} 
      {can("product", "delete") && <DeleteButton />}
    </div>
  )
}
```

### Route Protection

Protect entire routes based on permissions:

```tsx
import { RoutePermissionGuard } from "@medusajs/dashboard"

<RoutePermissionGuard 
  permissions={["product:read"]} 
  fallback={<AccessDenied />}
>
  <ProductListPage />
</RoutePermissionGuard>
```

## Runtime Policies

Unlike code-defined policies, runtime policies can be created dynamically through the admin interface or API. This allows for flexible permission management without code changes.

```ts
// Create a custom policy at runtime
const { policy } = await sdk.admin.rbacPolicy.create({
  key: "custom_resource.manage",
  resource: "custom_resource", 
  operation: "manage",
  name: "Custom Resource Management",
  description: "Manage custom business resources",
})
```

## Permission Resolution

The RBAC system provides a `resolvePermissions` function that returns a flat list of granted permissions with wildcards already expanded. This is useful for client-side permission checking:

```ts
const permissions = await sdk.admin.rbacRole.mePermissions()
// Returns: ["product:read", "product:create", "customer:read", ...]

// Client can do simple lookups
const canEditProducts = permissions.includes("product:update")
```

## Best Practices

1. **Principle of Least Privilege**: Grant users only the minimum permissions needed for their role
2. **Role Hierarchy**: Use parent-child relationships to organize permissions logically
3. **Granular Permissions**: Prefer specific permissions over broad wildcards when possible
4. **Regular Audits**: Periodically review and clean up unused roles and policies
5. **Clear Naming**: Use descriptive names and descriptions for roles and policies

## Integration with Workflows

RBAC permissions can be checked within workflows and steps:

```ts
import { hasPermission } from "@medusajs/framework"

const checkPermissionStep = createStep(
  "check-permission",
  async ({ userId, resource, operation }, { container }) => {
    const hasAccess = await hasPermission({
      roles: userId,
      action: { resource, operation },
      container,
    })
    
    if (!hasAccess) {
      throw new Error("Insufficient permissions")
    }
    
    return new StepResponse({ authorized: true })
  }
)
```
