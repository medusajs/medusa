# {metadata.title}

<EnterpriseNotice beta />

In this guide, you'll learn about the RBAC API routes, how to authenticate against them, and how to use them for actor types of your own, such as a `vendor_admin` on a marketplace.

<Note>

These routes are added by Medusa's HTTP layer, not the RBAC Module. They only exist when the RBAC Module is installed, as explained in the [RBAC Module](../page.mdx#how-to-use-the-rbac-module) overview.

</Note>

## The /rbac Prefix

The RBAC routes live under the `/rbac` prefix, and they aren't admin routes. They don't restrict authentication to the `user` actor type the way the `/admin` routes do.

The Medusa Admin dashboard consumes them, so they use the admin CORS configuration by default. To allow other origins, such as a vendor dashboard, set the `http.rbacCors` configuration. It replaces the admin CORS configuration for the `/rbac` routes, so include the admin dashboard's origin in it. Learn more in the [Module Options](../module-options/page.mdx#rbaccors-configuration) guide.

This is what makes them reusable: the same routes that manage the roles of admin users also manage the roles of a `vendor_admin`, a `supplier`, or any other actor type of your own. You don't build a second set of role management routes for each actor type.

The routes fall into five groups:

- [Role routes](#role-routes) that manage roles and their policies.
- [Policy routes](#policy-routes) that manage policies.
- [Role assignment routes](#role-assignment-routes) that grant roles to entities of any type.
- [Role user routes](#role-user-routes) that grant roles to admin users.
- [Introspection routes](#introspection-routes) that tell a client what the authenticated actor can do.

The RBAC Module also adds [admin routes](#admin-user-role-routes) that manage the roles of a single admin user, and a `roles` parameter to the [Create Invite route](#assign-roles-to-invites). These routes are under the `/admin` prefix, so only admin users can send requests to them.

<Note>

The [JS SDK](../../../js-sdk/page.mdx) exposes these routes under `sdk.admin`, since the dashboard consumes them. The methods work for any allowed actor type, as the underlying routes aren't restricted to admin users.

</Note>

## Configure Authentication Actor Types

The `/rbac` routes accept a [bearer token](!api!/admin/authentication) or a session, the same as the tokens you obtain from the [authentication routes](../../../commerce-modules/auth/authentication-route/page.mdx). They don't accept secret API keys, since those authenticate as the `user` actor type only.

Only the actor types in the `http.rbacActorTypes` configuration reach these routes. It defaults to `["user"]`, so an admin user works out of the box, and a request authenticated as any other actor type fails with a `401` error.

To allow a custom actor type, add it to the configuration in `medusa-config.ts`:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  projectConfig: {
    http: {
      rbacActorTypes: ["user", "vendor_admin"],
    },
    // ...
  },
  // ...
})
```

Learn more about this configuration, including how to allow every actor type, in the [Module Options](../module-options/page.mdx#rbacactortypes-configuration) guide.

A `vendor_admin` that manages its own team therefore needs a role granting at least `rbac_role:read`, `rbac_role_assignment:read`, `rbac_role_assignment:create`, and `rbac_role_assignment:delete`. It must also hold every policy of the roles it grants, as explained in the [Create Role Assignments route](#create-role-assignments-route).

You create that role once with the [Create Role route](#create-role-route), then grant it to each vendor's owner as you onboard them with the [role assignment routes](#role-assignment-routes). To do either in your own customizations instead, use the [RBAC workflows](../workflows/page.mdx), such as the `assignRolesWorkflow` explained in the [RBAC Concepts](../concepts/page.mdx#assign-a-role) guide.

## Role Routes

These routes manage roles and the policies each role grants.

### List Roles Route

The Medusa application defines an API route at `/rbac/roles` that lists the roles in your application.

```bash
curl 'http://localhost:9000/rbac/roles?limit=20' \
-H 'Authorization: Bearer {token}'
```

In the JS SDK, use the [rbacRole.list](/references/js_sdk/admin/RbacRole/methods/js_sdk.admin.RbacRole.list) method.

### Create Role Route

The Medusa application defines an API route at `/rbac/roles` that creates a role, optionally granting it policies at the same time.

```bash
curl -X POST http://localhost:9000/rbac/roles \
-H 'Content-Type: application/json' \
-H 'Authorization: Bearer {token}' \
--data-raw '{
  "name": "Vendor Owner",
  "description": "Manages the vendor'\''s team",
  "policy_ids": ["rpol_123", "rpol_456"]
}'
```

In the JS SDK, use the [rbacRole.create](/references/js_sdk/admin/RbacRole/methods/js_sdk.admin.RbacRole.create) method.

#### Request Body Parameters

The route only accepts the following parameters, and rejects any other parameter with a `400` error:

<TypeList
  types={[
    {
      name: "name",
      type: "`string`",
      optional: false,
      description: "The role's unique name."
    },
    {
      name: "description",
      type: "`string`",
      optional: true,
      description: "A description of the role's purpose."
    },
    {
      name: "policy_ids",
      type: "`string[]`",
      optional: true,
      description: "The IDs of the policies to grant. You can also add them later with the [Add Role Policies route](#add-role-policies-route)."
    },

    }
  ]}
/>

#### Response Fields

The response body has a `role` field holding the created role:

```json
{
  "role": {
    "id": "role_123",
    "name": "Vendor Owner",
    "description": "Manages the vendor's team",
    "metadata": null,
    "created_at": "2025-01-01T00:00:00.000Z",
    "updated_at": "2025-01-01T00:00:00.000Z"
  }
}
```

<Note>

Medusa rejects the request with a `403` error if the authenticated actor doesn't hold every policy in the `policy_ids` body parameter. This prevents an actor from creating a role that grants more access than they have.

</Note>

### Delete Role Route

The Medusa application defines an API route at `/rbac/roles/{id}` that deletes a role. Deleting a role removes it from every entity it was assigned to.

The authenticated actor must hold every policy of the role, otherwise the request fails with a `403` error. You also can't delete the [Super Admin role](../concepts/page.mdx#super-admin-role).

```bash
curl -X DELETE http://localhost:9000/rbac/roles/{id} \
-H 'Authorization: Bearer {token}'
```

### Remove Role Policy Route

The Medusa application defines an API route at `/rbac/roles/{id}/policies/{policy_id}` that removes a single policy from a role. The policy itself isn't deleted.

## Introspection Routes

These routes tell a client what the authenticated actor can do. Use them to build a dashboard that hides the actions an actor can't perform.

The [Authenticated Actor's Permissions route](#authenticated-actors-permissions-route) only requires authentication, so any allowed actor type reaches it without holding an RBAC policy. The [List Assignable Roles](#list-assignable-roles-route) and [List Assignable Policies](#list-assignable-policies-route) routes require `rbac_role:read` and `rbac_policy:read`, respectively.

### Introspect Within a Scope

The [Authenticated Actor's Permissions](#authenticated-actors-permissions-route), [List Assignable Roles](#list-assignable-roles-route), and [List Assignable Policies](#list-assignable-policies-route) routes accept the optional `scope` and `scope_id` query parameters. Pass both to evaluate the actor's privileges within that scope. The result then includes the actor's assignments in that scope along with their unscoped assignments. Without a scope, Medusa only considers the actor's unscoped assignments.

For example, a vendor owner switching between two vendors in your dashboard requests the permissions of the vendor they're viewing:

```bash
curl -G http://localhost:9000/rbac/me/permissions \
-H 'Authorization: Bearer {token}' \
-d scope=vendor \
-d scope_id=ven_123
```

Passing only one of the two parameters has no effect, and Medusa falls back to the scope of the request, if your application sets one in a middleware.

### Authenticated Actor's Permissions Route

The Medusa application defines an API route at `/rbac/me/permissions` that returns the effective permissions of the authenticated actor, with wildcards expanded into literal `resource:operation` strings.

```bash
curl http://localhost:9000/rbac/me/permissions \
-H 'Authorization: Bearer {token}'
```

In the JS SDK, use the [rbacRole.mePermissions](/references/js_sdk/admin/RbacRole/methods/js_sdk.admin.RbacRole.mePermissions) method. The method doesn't accept query parameters, so send a request to the route directly to pass a scope.

#### Query Parameters

This route accepts the optional `scope` and `scope_id` parameters explained in the [Introspect Within a Scope](#introspect-within-a-scope) section.

#### Response Fields

<TypeList
  types={[
    {
      name: "permissions",
      type: "`string[]`",
      optional: false,
      description: "The permissions the actor's roles grant, each in the `resource:operation` format. Since Medusa expands wildcards, a client can check literal membership rather than matching patterns."

      name: "roles",

      optional: false,
      description: "The roles assigned to the actor.",

        {
          name: "id",

In the JS SDK, use the [user.removeRoles](/references/js_sdk/admin/User/methods/js_sdk.admin.User.removeRoles) method.

#### Path Parameters

<TypeList
  types={[
    {
      name: "id",
      type: "`string`",
      optional: false,
      description: "The admin user's ID."
    }
  ]}
/>

#### Request Body Parameters

This route accepts the same `assignments` parameter as the [Add User Roles route](#add-user-roles-route). For each item, pass the `scope` and `scope_id` to remove only the assignment stored with that scope. Omitting them removes all the user's assignments of that role, both scoped and unscoped.

You can't remove the Super Admin role from the last admin user holding it without a scope. The request fails with a `400` error instead.

#### Response Fields

The response contains the IDs of the removed roles, along with a deletion status:

```json
{
  "ids": ["role_123"],
  "object": "user_role",
  "deleted": true
}
```

### Remove User Role Route

The Medusa application defines an API route at `/admin/users/{id}/roles/{role_id}` that removes a single role from an admin user.

```bash
curl -X DELETE \
http://localhost:9000/admin/users/{id}/roles/{role_id} \
-H 'Authorization: Bearer {token}'
```

In the JS SDK, use the [user.removeRole](/references/js_sdk/admin/User/methods/js_sdk.admin.User.removeRole) method.

### Assign Roles to Invites

The [Create Invite](!api!/admin#invites_postinvites) route accepts a `roles` body parameter when the RBAC Module is installed. Medusa grants these roles to the admin user created when someone accepts the invite.

```bash
curl -X POST http://localhost:9000/admin/invites \
-H 'Content-Type: application/json' \
-H 'Authorization: Bearer {token}' \
--data-raw '{
  "email": "staff@example.com",
  "roles": [
    {
      "role_id": "role_123",
      "scopes": [{ "type": "vendor", "id": "ven_123" }]
    }
  ]
}'
```
