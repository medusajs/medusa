# {metadata.title}

<EnterpriseNotice beta featureFlag="rbac" featureFlagHref="../page.mdx#how-to-use-the-rbac-module" />

In this guide, you'll learn about the RBAC API routes, how to authenticate against them, and how to use them for actor types of your own, such as a `vendor_admin` on a marketplace.

<Note>

These routes are added by Medusa's HTTP layer, not the RBAC Module. They only exist when the `rbac` feature flag is enabled.

</Note>

## The /rbac Prefix

The RBAC routes live under the `/rbac` prefix, and they aren't admin routes. The Medusa Admin dashboard consumes them, so they reuse the admin CORS configuration, but they don't restrict authentication to the `user` actor type the way the `/admin` routes do.

This is what makes them reusable: the same routes that manage the roles of admin users also manage the roles of a `vendor_admin`, a `supplier`, or any other actor type of your own. You don't build a second set of role management routes for each actor type.

The routes fall into five groups:

- [Role routes](#role-routes) that manage roles and their policies.
- [Policy routes](#policy-routes) that manage policies.
- [Role assignment routes](#role-assignment-routes) that grant roles to entities of any type.
- [Role user routes](#role-user-routes) that grant roles to admin users.
- [Introspection routes](#introspection-routes) that tell a client what the authenticated actor can do.

<Note>

The [JS SDK](../../../js-sdk/page.mdx) exposes these routes under `sdk.admin`, since the dashboard consumes them. The methods work for any allowed actor type, as the underlying routes aren't restricted to admin users.

</Note>

## Configure Authentication Actor Types

The `/rbac` routes accept a [bearer token](!api!/admin/authentication) or a session, the same as the tokens you obtain from the [authentication routes](../../../commerce-modules/auth/authentication-route/page.mdx). They don't accept secret API keys, since those authenticate as the `user` actor type only.

Only the actor types in the `http.rbacActorTypes` configuration reach these routes. It defaults to `["user"]`, so an admin user works out of the box, and a request authenticated as any other actor type fails with a `401` error.

To allow a custom actor type, add it to the configuration in `medusa-config.ts`:

```ts title="medusa-config.ts"
module.exports = defineConfig({
  projectConfig: {
    http: {
      rbacActorTypes: ["user", "vendor_admin"],
    },
    // ...
  },
  // ...
})
```

Learn more about this configuration, including how to allow every actor type, in the [Module Options](../module-options/page.mdx#rbacactortypes-configuration) guide.

## Role Routes

These routes manage roles and the policies each role grants.

### List Roles Route

The Medusa application defines an API route at `/rbac/roles` that lists the roles in your application.

```bash
curl 'http://localhost:9000/rbac/roles?limit=20' \
-H 'Authorization: Bearer {token}'
```

In the JS SDK, use the [rbacRole.list](/references/js_sdk/admin/RbacRole/methods/js_sdk.admin.RbacRole.list) method.

### Create Role Route

The Medusa application defines an API route at `/rbac/roles` that creates a role, optionally granting it policies at the same time.

```bash
curl -X POST http://localhost:9000/rbac/roles \
-H 'Content-Type: application/json' \
-H 'Authorization: Bearer {token}' \
--data-raw '{
  "name": "Vendor Owner",
  "description": "Manages the vendor'\''s team",
  "policy_ids": ["pol_123", "pol_456"]
}'
```

In the JS SDK, use the [rbacRole.create](/references/js_sdk/admin/RbacRole/methods/js_sdk.admin.RbacRole.create) method.

#### Request Body Parameters

    {

      name: "parent_id",

#### Response Fields

The response body has a `role` field holding the created role:

```json
{
  "role": {
    "id": "role_123",
    "name": "Vendor Owner",
    "description": "Manages the vendor's team",
    "parent_id": null,
    "metadata": null,
    "created_at": "2025-01-01T00:00:00.000Z",
    "updated_at": "2025-01-01T00:00:00.000Z"
  }
}
```

<Note>

Medusa rejects the request with a `403` error if the authenticated actor doesn't hold every policy in the `policy_ids` query parameter. This prevents an actor from creating a role that grants more access than they have.

</Note>

## Role Assignment Routes

A role assignment grants a role to an entity, identified by its type and ID rather than a link to a specific data model. This is what lets one set of routes grant roles to admin users, pending invites, and your own entities alike.

Use these routes for an actor type of your own. The `/rbac/roles/{id}/users` routes, covered in the [Role User Routes](#role-user-routes) section, only accept admin users.

### List Role Assignments Route

The Medusa application defines an API route at `/rbac/roles/{id}/assignments` that lists the entities a role is granted to.

```bash
curl -G \
```

## Introspection Routes

These routes tell a client what the authenticated actor can do. They only require authentication, so any allowed actor type reaches them without holding an RBAC policy. Use them to build a dashboard that hides the actions an actor can't perform.

### Introspect Within a Scope

The [Authenticated Actor's Permissions](#authenticated-actors-permissions-route), [List Assignable Roles](#list-assignable-roles-route), and [List Assignable Policies](#list-assignable-policies-route) routes accept the optional `scope` and `scope_id` query parameters. Pass both to evaluate the actor's privileges within that scope instead of across all of their assignments.

For example, a vendor owner switching between two vendors in your dashboard requests the permissions of the vendor they're viewing:

```bash
curl -G http://localhost:9000/rbac/me/permissions \
-H 'Authorization: Bearer {token}' \
-d scope=vendor \
-d scope_id=ven_123
```

Passing only one of the two parameters has no effect, and Medusa falls back to the scope of the request, if your application sets one in a middleware.

### Authenticated Actor's Permissions Route

The Medusa application defines an API route at `/rbac/me/permissions` that returns the effective permissions of the authenticated actor, with wildcards expanded into literal `resource:operation` strings.

```bash
curl http://localhost:9000/rbac/me/permissions \
-H 'Authorization: Bearer {token}'
```

In the JS SDK, use the [rbacRole.mePermissions](/references/js_sdk/admin/RbacRole/methods/js_sdk.admin.RbacRole.mePermissions) method.

#### Query Parameters

This route accepts the optional `scope` and `scope_id` parameters explained in the [Introspect Within a Scope](#introspect-within-a-scope) section.

#### Response Fields

<TypeList
  types={[
    {
      name: "permissions",
      type: "`string[]`",
      optional: false,
      description: "The permissions the actor's roles grant, each in the `resource:operation` format. Since Medusa expands wildcards, a client can check literal membership rather than matching patterns."
    },
    {
      name: "roles",
      type: "`object[]`",
      optional: false,
      description: "The roles assigned to the actor.",
      children: [
        {
          name: "id",
          type: "`string`",
          optional: false,
          description: "The role's ID."
        },
        {
          name: "name",
          type: "`string`",
          optional: false,
          description: "The role's name."
        }
      ]
    },
    {
      name: "covered_roles",
      type: "`string[]`",
      optional: false,
      description: "The names of the roles whose permissions are a subset of the actor's own. A Super Admin covers every role without holding any assignment, which makes this the useful check for role-based interface guards."
    }
  ]}
/>

For example:

```json

  "permissions": ["product:read", "product:update"],
  "roles": [
    { "id": "role_123", "name": "Vendor Owner" }
  ],
  "covered_roles": ["Vendor Staff"]
}
```

An actor without an entry in the RBAC Module's [actors option](../module-options/page.mdx#actors) receives empty arrays rather than an error.
